# AI 驱动开发质量方法论

通用质量规则，适用于所有项目。具体业务规则（领域 review 规则、测试用例、eval 数据）由各项目自行编写。

## 1. 代码结构健康

- 单个文件不超过 1000 行。PR 把文件从 <1000 行推到 ≥1000 行时，应先拆再合入
- 对 if/else 链条追问：是否存在让分支不需要存在的设计（code-judo 导向——能用策略模式、查表、多态消除的条件分支就消除）
- 新增的公共函数必须有 docstring 或类型注解

## 2. 测试标准

- 每个 API 端点至少 3 条测试：正常路径、异常路径、边界条件
- 测试用 in-process 方式调用（如 TestClient），不起真端口
- LLM 输出类测试用 pass^k 方法：同一输入跑 k 次（推荐 k=5），全部一致才通过
- eval 断言优先用集合比较（该出的出了吗 / 不该出的出了没），不用 LLM-as-judge 做门禁
- E2E 测试脚本不依赖 LLM 的具体输出内容，用拦截/注入方式做确定性执行

## 3. 外部工具版本治理

- 所有外部工具（测试框架、eval runner、虚拟化工具、浏览器引擎等）必须 pin 精确版本号
- 版本升级必须作为独立 MR/PR，说明默认行为有无变化
- 升级 MR 需要 diff review：对比旧版/新版在同一输入下的行为差异

## 4. AI Review 规范

- review finding 必须标注来源归因：`source: static`（来自 linter/bandit 等）、`ai`（来自模型推理）、`static+ai`（交叉验证）
- 按 diff 大小分级审查深度，不对 10 行 typo fix 和 500 行重构花同样力气
- 内容指纹缓存：相同输入不重复付费审查
- review 结论三态：approved / issues / failed-to-review（模型超时或拒绝不算通过）

## 5. 上游 API 隔离

- CI 测试不调用真实第三方 API，用录制回放（simulate 模式）
- 定期（推荐 nightly）对真实沙箱跑一次，逐字段比对回放数据是否过期（diff 模式）
- 录制数据脱敏：过滤 Authorization、Cookie、API-Key 等 header

## 6. AI 探索式测试

- AI 驱动的浏览器探索不进 CI，人工触发，设月度上限
- 每次探索必须产出 trace 文件：时间戳、动作序列、截图、发现的异常、是否产生副作用
- 涉及写操作必须记录补偿动作（如撤单、删除测试数据）

## 7. 事故闭环

- 每个生产事故必须有出口：一条测试 或 一条编码约定
- 出口未闭环时 CI 报警
- 已修 bug 回溯根因后产出 review 规则，下次 review 自动读到（learn-from-fix 循环）

## 8. 不做的事

- 不用 LLM-as-judge 做 CI 门禁（概率偏差不适合阻断合入）
- AI 浏览器探索不当回归基线（路径复现率 ~20%，成本高）
- 不在 CI 起全栈环境（多服务链路超 pipeline 超时限制时，用 mock/stub 替代）
