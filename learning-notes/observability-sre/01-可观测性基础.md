## 1. 什么是可观测性

**可观测性**（Observability）来自控制论，指"能否从外部输出推断出系统内部状态"。放到软件上就是：生产环境出问题时，你**不改一行代码、不加一条日志、不重新部署**，就能定位根因。

```
┌────────── 监控 vs 可观测性 ──────────┐
│                                       │
│  监控（Monitoring）                    │
│  ├─ 预设好"我想知道什么"               │
│  ├─ 回答已知问题（CPU 高不高、RT 高不高） │
│  └─ 本质：断言检查                     │
│                                       │
│  可观测性（Observability）             │
│  ├─ 面对"未知的未知"                   │
│  ├─ 回答临时提出的问题                 │
│  └─ 本质：通过遥测数据推断内部状态     │
│                                       │
│  结论：监控是可观测性的子集            │
└───────────────────────────────────────┘
```

## 2. 三支柱（Three Pillars）

```
┌───────── 传统三支柱 ─────────┐
│                               │
│  Metrics（指标）               │
│  ├─ 数值型聚合数据              │
│  ├─ 低成本、高基数 → 爆炸       │
│  └─ 适合告警、趋势分析           │
│                               │
│  Logs（日志）                  │
│  ├─ 离散的文本/结构化事件        │
│  ├─ 存储成本高、查询慢          │
│  └─ 适合事后排查、审计           │
│                               │
│  Traces（追踪）                │
│  ├─ 请求在多服务间的执行路径      │
│  ├─ 采样是常态                  │
│  └─ 适合定位性能瓶颈、链路故障    │
└───────────────────────────────┘
```

### 2.1 Metrics：四种类型

```python
# Prometheus/OpenTelemetry 通用四类
Counter    # 只增不减：请求总数、错误数
Gauge      # 可增可减：当前连接数、CPU 使用率
Histogram  # 分布统计：请求时延分布（p50/p95/p99）
Summary    # 客户端计算分位数（不推荐，无法跨实例聚合）
```

**常见误用**：把"请求时延"做成 Gauge。正确做法是 Histogram，然后在查询时用 `histogram_quantile` 计算分位数。

### 2.2 Logs：结构化日志是基本功

```python
# ❌ 不推荐：文本日志
logger.info(f"user {user_id} login from {ip}")

# ✅ 推荐：结构化日志（JSON）
logger.info("user_login", extra={
    "user_id": user_id,
    "ip": ip,
    "trace_id": get_trace_id(),  # 关联 Trace
    "method": "oauth",
})
```

结构化日志让你可以按字段查询、聚合，并且容易与 Trace 关联。

### 2.3 Traces：理解 Span 和 Context

```
一个分布式请求：
                       ┌─────────┐
Client ──→ API GW ──→  │ Auth    │ ──→ DB
                       └─────────┘
                            ↓
                       ┌─────────┐
                       │ Order   │ ──→ Cache
                       └─────────┘

对应的 Trace：
Span[ API GW ]
├─ Span[ Auth ]
│   └─ Span[ DB Query ]
└─ Span[ Order ]
    └─ Span[ Cache Get ]

每个 Span 有：trace_id、span_id、parent_span_id、name、attributes、events、status
```

**关键原则**：trace_id 必须在所有服务间传递（W3C Trace Context 标准），否则 Trace 是断的。

## 3. 2026 年的新支柱：Events 与 Profiles

```
┌─────── 扩展的五支柱 ───────┐
│                             │
│  Metrics                    │
│  Logs                       │
│  Traces                     │
│  ├─ 以上是传统三支柱          │
│                             │
│  Events（事件）              │
│  ├─ 有业务语义的离散事件      │
│  ├─ 部署、配置变更、告警触发   │
│  └─ 帮助关联"业务动作 → 技术变化" │
│                             │
│  Profiles（性能剖析）         │
│  ├─ CPU/内存/锁的函数级剖析   │
│  ├─ eBPF + Parca/Pyroscope  │
│  └─ 常驻生产环境，低开销      │
└─────────────────────────────┘
```

持续性能剖析（Continuous Profiling）在 2024-2026 年快速普及，Grafana Pyroscope、Parca、Polar Signals 等工具让"哪个函数在吃 CPU"可以像查 Metrics 一样简单。

## 4. OpenTelemetry 成为事实标准

2026 年的共识：**除非有特殊理由，否则遥测数据收集统一走 OpenTelemetry**。

```
OTel 的三个价值：
├─ 统一 API / SDK：代码只依赖 OTel API，后端随时换
├─ 统一协议（OTLP）：所有主流后端都能收
└─ 统一语义约定（Semantic Conventions）：跨工具可分析
```

常见后端组合：

| 组合 | 特点 |
|------|------|
| OTel + Prometheus + Grafana + Loki + Tempo | 全开源自建，Grafana 一站式 |
| OTel + Datadog / New Relic / Honeycomb | SaaS 方案，省运维 |
| OTel + Jaeger + Prometheus | 经典组合，只要 Trace + Metrics |
| OTel + ClickHouse + 自定义可视化 | 大规模、低成本（SigNoz、Uptrace 走这条路线） |

## 5. 生产级原则

### 5.1 USE 和 RED 方法

```
USE（资源视角）— Brendan Gregg：
  Utilization 利用率
  Saturation  饱和度（排队）
  Errors      错误

  用途：看底层资源（CPU、磁盘、网络）

RED（服务视角）— Tom Wilkie：
  Rate        请求速率
  Errors      错误率
  Duration    响应时间

  用途：看每个服务的黄金指标
```

### 5.2 基数爆炸是头号杀手

```python
# ❌ 灾难：把 user_id 作为标签
http_requests_total{user_id="12345", ...}
# 1 亿用户 = 1 亿时间序列，Prometheus 直接 OOM

# ✅ 正确：只放有界的枚举值
http_requests_total{method="GET", status="200", route="/api/orders"}
# user_id 放到 Trace 的 attributes 里，或 Logs 里
```

**经验法则**：任何标签的基数（distinct 值的数量）应该在 1000 以内，理想在 100 以内。

### 5.3 采样策略

```
Trace 采样：
├─ Head-based（头部采样）
│   ├─ 入口处决定是否采样，一整条 Trace 要么全采要么全不采
│   └─ 简单，但会错过"罕见但重要的"慢请求
│
└─ Tail-based（尾部采样）
    ├─ Collector 收到全部 Span 后再决定
    ├─ 可以按"错误""慢请求"等条件决定
    └─ 需要 OTel Collector 做缓冲
```

生产建议：默认 1% 头部采样 + 尾部采样（错误和慢请求 100% 留下）。

### 5.4 数据保留策略

```
Metrics：
├─ 原始精度 15 天（Prometheus）
├─ 降采样后 1 年（Thanos/Mimir/VictoriaMetrics）

Traces：
├─ 原始 7-14 天，不建议更长
├─ 采样过的 1%-10%

Logs：
├─ 热：7 天（查询需求高）
├─ 温：30 天（合规要求）
└─ 冷：1-3 年（归档，S3 Glacier）
```

## 6. 可观测性的成本权衡

```
成本来自：
├─ 采集：SDK/Collector CPU 和内存
├─ 传输：网络带宽
├─ 存储：SaaS 按 GB 计费很快上千美元/月
└─ 人力：自建方案的运维

常见优化：
├─ 日志分级：INFO 采样、ERROR 全量
├─ Trace 尾部采样 + 智能过滤
├─ 高基数字段放 Trace 不放 Metric
└─ 长周期数据降采样归档
```

## 7. 2026 年趋势

### 7.1 eBPF 原生可观测性

无侵入、无 SDK，内核层面直接采集。代表项目：Cilium Tetragon、Pixie、Beyla、Parca Agent。适合"不改代码也能看"的场景。

### 7.2 LLM 可观测性独立成学科

Agent 时代新增的观测维度（见 [07-AI-Agent可观测性.md](./07-AI-Agent可观测性.md)）：
- Token 消耗（输入/输出分开）
- 模型版本、温度、推理时间
- Prompt 模板变化的影响
- Agent 工具调用的成功率

### 7.3 统一语义约定扩展到 AI 领域

OpenTelemetry 在 2026 年为 GenAI 引入了标准语义约定（`gen_ai.*` 命名空间），让不同 LLM 框架产生的 Trace 可以互相对比。

### 7.4 Declarative Configuration 稳定版

OTel 2026 年发布了声明式配置第一个 stable 版，用 YAML 定义采集管道，让可观测性配置能像 K8s 资源一样被 GitOps 管理。来源：[OpenTelemetry Datadog Roundup Feb 2026](https://opensource.datadoghq.com/otel-news/2026/02/)
