## 1. 为什么要分布式追踪

微服务环境下，一个用户请求会经过 5-20 个服务。任何一个慢或错，最终用户看到的都是"系统挂了"。追踪解决：

```
没有追踪：
  "订单下单失败" → 在 10 个服务的日志里 grep 一小时

有追踪：
  点开这个失败的 trace → 看到它在支付服务超时 → 支付服务内部调用卡在第三方网关
  耗时：10 秒
```

## 2. 核心概念回顾

```
Trace ─── 一次完整请求的所有操作
  │
  ├── Span（根 Span，入口服务）
  │    ├── Span（下游调用）
  │    │    ├── Span（DB 查询）
  │    │    └── Span（缓存查询）
  │    └── Span（另一下游）
  │
每个 Span：
  trace_id       同一条链路的标识
  span_id        当前操作
  parent_span_id 父操作
  name           操作名
  start / end    时间
  attributes     键值对（http.method、db.statement、user.id）
  events         Span 内的离散时间点（如"开始重试"）
  status         OK / ERROR
  links          与其他 Span 的关联（异步场景）
```

## 3. W3C Trace Context 传播

**核心规则**：任何跨进程/线程/消息的调用都必须把 trace context 传下去，否则链路断裂。

### 3.1 HTTP 场景（自动）

OTel SDK 会自动往 HTTP 请求头注入：

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
tracestate: ...（可选，vendor 扩展）
```

### 3.2 消息队列场景（手动）

Kafka、RabbitMQ 不会自动传，必须手动注入到 message header：

```python
# Producer
from opentelemetry.propagate import inject

def publish(event: dict):
    headers = {}
    inject(headers)  # 把当前 span 的 context 写入 headers
    producer.produce(
        topic="orders",
        value=json.dumps(event),
        headers=[(k, v.encode()) for k, v in headers.items()],
    )

# Consumer
from opentelemetry.propagate import extract
from opentelemetry import trace, context

def consume(msg):
    # 从 headers 提取 context
    headers = {k: v.decode() for k, v in msg.headers() or []}
    ctx = extract(headers)

    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("process_order", context=ctx):
        # ... 业务逻辑
        pass
```

### 3.3 异步任务场景

Celery、RQ 等也要显式传播：

```python
# 在发任务时捕获 context
from opentelemetry import trace, context
from opentelemetry.propagate import inject

@app.task
def process_order(order_id, carrier):
    """Celery 任务。"""
    ctx = extract(carrier)
    tracer = trace.get_tracer(__name__)
    with tracer.start_as_current_span("process_order_task", context=ctx):
        # ...
        pass

def enqueue_order(order_id):
    carrier = {}
    inject(carrier)
    process_order.delay(order_id, carrier)
```

## 4. 采样策略

### 4.1 头部采样（Head-based）

入口决定整条 Trace 是否采样，**不采样的整条链路都不产生数据**。

```python
# Python SDK
from opentelemetry.sdk.trace.sampling import ParentBased, TraceIdRatioBased

sampler = ParentBased(root=TraceIdRatioBased(0.1))  # 10% 采样
```

优点：决策快、数据量可预测。
缺点：错误和慢请求按概率被丢弃。

### 4.2 尾部采样（Tail-based）

Collector 缓冲一段时间的 Span，整条 Trace 收完后再决定。错误和慢请求 100% 保留。

```yaml
# OTel Collector
processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 100000
    policies:
      - name: errors
        type: status_code
        status_code: {status_codes: [ERROR]}

      - name: slow-requests
        type: latency
        latency: {threshold_ms: 1000}

      - name: interesting-endpoints
        type: string_attribute
        string_attribute:
          key: http.route
          values: [/api/payment, /api/orders]

      - name: rest-10-percent
        type: probabilistic
        probabilistic: {sampling_percentage: 10}
```

2026 年生产推荐：**头部 100% 采样 → Collector 尾部决策**。这样错误和慢请求不会丢。

### 4.3 动态采样

根据流量实时调整采样率。Grafana Tempo 和 Jaeger 都有 remote sampling 配置。

## 5. Span 的最佳实践

### 5.1 命名规范

```
❌ "db-call"、"/api/v1/user/123"（带变量）、"function_foo"

✅ 动词 + 宾语 + 具体资源：
   "HTTP GET /users/:id"
   "SELECT users"
   "Redis GET"
   "Kafka publish orders-topic"
```

### 5.2 属性添加

```python
with tracer.start_as_current_span("create_order") as span:
    # 使用 OTel 标准语义约定
    span.set_attribute("http.method", "POST")
    span.set_attribute("http.route", "/orders")
    span.set_attribute("http.status_code", 200)

    # 自定义业务属性
    span.set_attribute("order.amount", order.amount)
    span.set_attribute("order.user_id", order.user_id)
    span.set_attribute("order.payment_method", "credit_card")

    try:
        # ...
        span.set_status(trace.Status(trace.StatusCode.OK))
    except Exception as e:
        span.record_exception(e)
        span.set_status(trace.Status(trace.StatusCode.ERROR, str(e)))
        raise
```

**反模式**：把整个 JSON body 放进属性（有些字段 > 8KB 直接把 Span 搞成 bomb）。

### 5.3 Span Events

想在 Span 中记录时间点而不开新 Span：

```python
with tracer.start_as_current_span("process_payment") as span:
    span.add_event("payment.request_sent", {"gateway": "stripe"})
    # ... 调用支付网关
    span.add_event("payment.response_received", {"duration_ms": 234})
```

## 6. TraceQL（Tempo 的查询语言）

2026 年 Grafana Tempo 的 TraceQL 功能日益成熟：

```traceql
# 找所有错误且耗时 > 1s 的 Trace
{ status = error && duration > 1s }

# 找支付服务且金额 > 10000 的请求
{ service.name = "payment" && span.order.amount > 10000 }

# 复杂条件
{ service.name = "api-gateway" }
  >> { service.name = "order" && status = error }
  | count() > 3

```

## 7. OpenTelemetry GenAI 扩展（2026）

OTel 为 LLM 应用引入了 `gen_ai.*` 语义约定：

```python
with tracer.start_as_current_span("chat.completion") as span:
    span.set_attribute("gen_ai.system", "openai")
    span.set_attribute("gen_ai.request.model", "gpt-5.5")
    span.set_attribute("gen_ai.request.temperature", 0.7)
    span.set_attribute("gen_ai.request.max_tokens", 1024)

    # Events 记录每次调用
    span.add_event("gen_ai.content.prompt", {
        "gen_ai.prompt": prompts,
    })

    response = client.chat.completions.create(...)

    span.set_attribute("gen_ai.response.id", response.id)
    span.set_attribute("gen_ai.response.model", response.model)
    span.set_attribute("gen_ai.usage.input_tokens", response.usage.prompt_tokens)
    span.set_attribute("gen_ai.usage.output_tokens", response.usage.completion_tokens)
    span.set_attribute("gen_ai.response.finish_reasons", [c.finish_reason for c in response.choices])
```

有了标准命名，Langfuse、Phoenix、Datadog、Grafana 都能无缝识别 LLM 调用。见 [07-AI-Agent可观测性.md](./07-AI-Agent可观测性.md)。

## 8. 生产检查清单

```
☐ OTel SDK 初始化在应用最早阶段
☐ W3C propagator 默认启用（不要用老的 B3、Jaeger 格式）
☐ 消息队列/Celery/异步任务手动传递 context
☐ 入口 100% 采样 + Collector 尾部采样
☐ 敏感字段脱敏（在 Collector 做）
☐ 错误必须 record_exception + set_status(ERROR)
☐ 标准语义约定（http.*、db.*、gen_ai.*）
☐ Span 属性有界（不存大 Body）
☐ Exemplars 配置（Metric ↔ Trace 跳转）
☐ 监控 Collector 自身的 dropped_spans 指标
```

## 9. 常见问题诊断

```
现象："链路只看到入口，下游全部断了"
原因：下游服务没注入 propagator 或者用了老 b3 格式
检查：curl -v 看请求头是否带 traceparent

现象："Span 数量远超预期"
原因：自动埋点 + 手动埋点重复
解决：Collector 去重 Processor，或者代码里把某个 instrumentation suppress 掉

现象："Grafana Tempo 很多 Trace 找不到"
原因：头部采样率太低 + 没配尾部采样
解决：启用尾部采样保留错误和慢请求

现象："CPU 飙升是 OTel 自己干的"
原因：BatchSpanProcessor 队列堆积 + 同步导出
解决：调整 max_queue_size、max_export_batch_size、schedule_delay
```

## 10. Tracing 后端选型（2026-05 更新）

> 🔄 更新于 2026-05-22

<!-- version-check: Jaeger v2.18, Tempo 2.10, checked 2026-05-22 -->

后端选型几个关键变化：

| 后端 | 当前版本 | 重要变化 |
|------|---------|---------|
| **Jaeger** | v2.18 | **v1 已 EOL（2025-12-31）**，不再接受任何更新；新部署必须使用 v2，v2 默认基于 OTel Collector，原生支持 OTLP |
| **Grafana Tempo** | 2.10 | TraceQL 持续增强，新增 Metrics Generator 支持 RED 指标自动生成 |
| **OpenTelemetry Collector** | v0.151 | 推荐作为 Tracing/Metrics/Logs 的统一接收层（详见 `02-OpenTelemetry完全指南.md`） |

**Jaeger v2 与 v1 的关键差异**：

```
Jaeger v1（EOL 2025-12-31）：
├─ 自定义 collector / agent 二进制
├─ 自有协议 Thrift / Jaeger gRPC
├─ 自带的存储抽象层
└─ ⚠️ 不再接收任何更新（包括 CVE 修复）

Jaeger v2（推荐）：
├─ 基于 OpenTelemetry Collector 构建
├─ 原生 OTLP 协议（也兼容 Jaeger 旧协议）
├─ 复用 OTel 生态的 Processor / Exporter
└─ 配置文件向后兼容，迁移成本低
```

**升级建议**：

```
仍在 Jaeger v1：
└─ 立即制定 v2 迁移计划，参考官方迁移指南
   https://www.jaegertracing.io/docs/2.0/upgrade/

新项目：
└─ 直接选 Jaeger v2 或 Grafana Tempo（任选其一即可，OTLP 协议互换）

已用 OTel Collector：
└─ 后端可在 Jaeger / Tempo / 厂商方案间无缝切换
```
