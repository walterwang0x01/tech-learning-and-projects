## 1. 什么是零信任

```
传统边界安全（City Wall）：
  "进了防火墙就是自己人"
  问题：一旦 VPN 被攻破，内网全部暴露

零信任（Zero Trust）：
  "永不信任，始终验证"
  每次请求都要证明身份 + 有权限
  不依赖网络位置
```

Google 2014 的 **BeyondCorp** 论文是里程碑，后来成为 NIST 零信任架构标准。

## 2. 三个支柱

```
┌───────── 零信任三支柱 ─────────┐
│                                 │
│  身份（Identity）                │
│  ├─ 用户身份（SSO / MFA / Passkey）│
│  ├─ 设备身份（MDM 证书 / TPM）    │
│  └─ 服务身份（SPIFFE / mTLS）    │
│                                 │
│  访问策略（Policy）              │
│  ├─ 基于身份 + 上下文（设备、位置、时间）│
│  ├─ 最小权限                     │
│  └─ Just-In-Time（按需提权）      │
│                                 │
│  可见性（Visibility）            │
│  ├─ 所有访问审计                  │
│  ├─ 异常检测                     │
│  └─ 持续验证（不只是登录时验证）    │
└─────────────────────────────────┘
```

## 3. BeyondCorp 式访问

身份感知代理（IAP）代替 VPN 成为企业接入主流：**Google IAP**、**AWS Verified Access**、**Cloudflare Access**、**Pomerium**（开源）、**Teleport**（开源）。

```
传统 VPN：              BeyondCorp：
员工 → VPN → 内网       员工 → IAP → 应用
1 次认证                每次请求认证 + 授权
访问所有内网            只能访问该应用
```

## 4. mTLS：服务间认证

内部服务之间不再相信"同 VPC"。mTLS 双向证书：

```
没有 mTLS：A ──HTTP──> B（B 不知道对面是不是 A）
有 mTLS：  A ──TLS(双向证书)──> B（B 验证 A 的证书）
```

## 5. SPIFFE / SPIRE：工作负载身份

SPIFFE（Secure Production Identity Framework for Everyone）给每个工作负载发唯一 ID：

```
SPIFFE ID：spiffe://prod.example.com/ns/payment/sa/api

SPIRE 架构：
  SPIRE Server（根证书、颁发 SVID）
    ↓
  SPIRE Agent（每节点、验证工作负载、分发 SVID）
    ↓
  工作负载（用 SVID 做 mTLS）
```

集成到 Go 应用：

```go
import "github.com/spiffe/go-spiffe/v2/workloadapi"

x509Source, _ := workloadapi.NewX509Source(ctx)

tlsConfig := tlsconfig.MTLSClientConfig(
    x509Source, x509Source,
    tlsconfig.AuthorizeAny(),
)

client := &http.Client{
    Transport: &http.Transport{TLSClientConfig: tlsConfig},
}
```

应用代码不用管密钥轮换。

## 6. Service Mesh：零信任的底座

Istio / Linkerd 把 mTLS 和授权策略做成 Sidecar 或 Ambient 层，应用无感知：

```yaml
# Istio 策略：只允许 order-service 调用 payment 的 pay 接口
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: payment-allow-order
  namespace: payment
spec:
  selector:
    matchLabels: {app: payment}
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/order/sa/order-service"]
      to:
        - operation:
            methods: ["POST"]
            paths: ["/pay"]
```

2026 年 **Istio Ambient Mode** 默认推荐，对比 Sidecar 模式资源开销降低 90%（见 [architecture/02-微服务架构模式.md](../architecture/02-微服务架构模式.md#10-2026-年服务网格演进)）。

## 7. Kubernetes 下的零信任

```
K8s 原生：
├─ ServiceAccount：Pod 身份
├─ RBAC：API 访问授权
├─ NetworkPolicy：L3/L4 流量控制
└─ Pod Security Admission：容器权限限制

补齐零信任：
├─ Istio / Linkerd：L7 mTLS + 策略
├─ Cilium：eBPF 网络 + 身份感知策略
├─ Kyverno / OPA：策略即代码
└─ Falco：运行时异常检测
```

### NetworkPolicy 示例（默认禁止，白名单放行）

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  podSelector:
    matchLabels: {app: backend}
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: {app: frontend}
      ports:
        - protocol: TCP
          port: 8080
```

## 8. 凭证的短生命周期

零信任的核心是**短期凭证**：

```
传统：Long-lived API Key → 泄露 = 长期风险
零信任：
  ├─ 应用通过身份协议（OIDC / SPIFFE）换取短期 Token
  ├─ Token 10-15 分钟过期
  └─ 持续轮换
```

### AWS IAM Roles for Service Accounts（IRSA）

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/S3ReaderRole
```

应用 SDK 自动拿到 15 分钟有效的临时凭证。

### HashiCorp Vault Dynamic Secrets

```
应用 → Vault（K8s SA 认证）
Vault → 生成 DB 账号（10 分钟有效）
应用 → 用临时账号连 DB
10 分钟后 → Vault 自动删除账号
```

应用代码里从来没出现长期 DB 密码。

## 9. 对 AI Agent 的零信任

```
Agent 时代新问题：
├─ Agent 代表谁访问什么？
├─ Agent 的身份如何颁发？
├─ Agent 操作如何审计？

2026 年方案：
├─ SPIFFE for Agents：每个 Agent 唯一 SVID
├─ Delegation Token：代表用户时
├─ Tool Authorization：工具调用要现场授权
└─ HIL + 审计跟踪
```

## 10. 成熟度路径

```
阶段 1：SSO + MFA + 关键服务 mTLS
阶段 2：SPIFFE/Service Mesh + NetworkPolicy + 动态凭证 + 全面审计
阶段 3：上下文感知策略 + UEBA + Red Team + Agent 级零信任
```

## 11. 反模式

```
❌ 上了零信任就以为安全
   → 零信任是持续过程

❌ 只对外部零信任，内部仍互信
   → 横向移动是多数事故的根源

❌ 策略爆炸，规则没人维护
   → Policy as Code 集中管理

❌ 用户体验差到员工绕过
   → Passkey + IAP + SSO 可以比 VPN 更顺

❌ 完全无 VPN
   → 某些遗留协议仍需要网络隔离，混合更现实
```
