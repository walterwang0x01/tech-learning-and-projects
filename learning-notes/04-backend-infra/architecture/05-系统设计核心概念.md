### 一致性哈希

```
传统哈希的问题：
  hash(key) % N → 节点增减时，几乎所有 key 都要重新映射

一致性哈希：
  将节点和 key 都映射到一个环上，key 顺时针找到最近的节点

       Node A
        ╱  ╲
      ╱      ╲
  Node D      Node B
      ╲      ╱
        ╲  ╱
       Node C

  增加 Node E：只影响 E 和相邻节点之间的 key
  删除 Node B：只影响 B 的 key 迁移到下一个节点

  虚拟节点：每个物理节点映射多个虚拟节点，解决数据倾斜
```

## 3. 缓存

```
┌─────────── 缓存策略 ───────────┐
│                                 │
│  Cache-Aside（旁路缓存）⭐ 最常用│
│  读：先查缓存 → 未命中 → 查 DB → 写缓存
│  写：更新 DB → 删除缓存          │
│                                 │
│  Read-Through（读穿透）          │
│  缓存层自动从 DB 加载            │
│                                 │
│  Write-Through（写穿透）         │
│  写缓存时同步写 DB               │
│                                 │
│  Write-Behind（写回）            │
│  写缓存后异步批量写 DB           │
│  性能最好，但有数据丢失风险       │
└─────────────────────────────────┘
```

### 缓存常见问题

```python
# 缓存穿透：查询不存在的数据，每次都打到 DB
# 解决：布隆过滤器 + 缓存空值
def get_user(user_id: str):
    # 布隆过滤器快速判断是否存在
    if not bloom_filter.might_contain(user_id):
        return None

    cached = redis.get(f"user:{user_id}")
    if cached is not None:
        return json.loads(cached) if cached != "NULL" else None

    user = db.find_user(user_id)
    if user:
        redis.setex(f"user:{user_id}", 3600, json.dumps(user))
    else:
        redis.setex(f"user:{user_id}", 300, "NULL")  # 缓存空值，短过期
    return user


# 缓存雪崩：大量 key 同时过期，请求全打到 DB
# 解决：过期时间加随机偏移
import random

def cache_with_jitter(key: str, value: str, base_ttl: int = 3600):
    jitter = random.randint(0, 600)  # 0~10 分钟随机偏移
    redis.setex(key, base_ttl + jitter, value)


# 缓存击穿：热点 key 过期瞬间，大量请求打到 DB
# 解决：互斥锁（只允许一个请求回源）
def get_hot_data(key: str):
    cached = redis.get(key)
    if cached:
        return json.loads(cached)

    # 互斥锁：只有一个请求去查 DB
    lock_key = f"lock:{key}"
    if redis.set(lock_key, "1", nx=True, ex=10):
        try:
            data = db.query(key)
            redis.setex(key, 3600, json.dumps(data))
            return data
        finally:
            redis.delete(lock_key)
    else:
        time.sleep(0.1)
        return get_hot_data(key)  # 等待后重试
```

## 4. 限流

```
┌─────────── 限流算法 ───────────┐
│                                 │
│  1. 固定窗口                     │
│     每分钟最多 100 次            │
│     问题：窗口边界突发            │
│                                 │
│  2. 滑动窗口                     │
│     统计过去 60 秒的请求数       │
│     更平滑，但内存开销大          │
│                                 │
│  3. 令牌桶（Token Bucket）⭐     │
│     固定速率放入令牌              │
│     请求消耗令牌，桶空则拒绝      │
│     允许突发流量（桶内有存量）     │
│                                 │
│  4. 漏桶（Leaky Bucket）        │
│     请求进入桶，固定速率流出      │
│     严格平滑，不允许突发          │
└─────────────────────────────────┘
```

```python
import time

class TokenBucket:
    """令牌桶限流器"""

    def __init__(self, rate: float, capacity: int):
        self.rate = rate            # 每秒放入令牌数
        self.capacity = capacity    # 桶容量
        self.tokens = capacity      # 当前令牌数
        self.last_refill = time.time()

    def allow(self) -> bool:
        """是否允许请求通过"""
        now = time.time()
        # 补充令牌
        elapsed = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last_refill = now

        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

# 每秒 100 个请求，允许突发 200
limiter = TokenBucket(rate=100, capacity=200)

if limiter.allow():
    handle_request()
else:
    return_429_too_many_requests()
```

### 10.1 限流算法深入对比

前面第 4 节给出了算法框架，这里补充 2026 年面试常考的**边界问题**与**分布式实现**：

| 算法 | 突发流量 | 边界问题 | 分布式实现 | 典型使用者 |
| ---- | -------- | -------- | ---------- | ---------- |
| 固定窗口（Fixed Window） | 允许 2x 突发 | 跨窗口瞬间翻倍 | Redis INCR + EXPIRE | 简单接口限流 |
| 滑动窗口日志（Sliding Log） | 精确限制 | 内存开销 O(N) | Redis ZSET + ZREMRANGEBYSCORE | 高精度场景 |
| 滑动窗口计数（Sliding Counter） | 接近精确 | 近似估算 | Redis Hash | Cloudflare 默认算法 |
| 令牌桶（Token Bucket）⭐ | 允许桶容量突发 | 需处理令牌补发原子性 | Redis Lua 脚本 | AWS、Stripe |
| 漏桶（Leaky Bucket） | 不允许突发 | 队列积压 | 队列 + 定时器 | 网络整形 |

```python
# 分布式令牌桶：Redis + Lua 保证原子性
# 这是 2026 年大厂（AWS、Stripe）生产环境的标准做法
TOKEN_BUCKET_LUA = """
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])          -- 每秒令牌数
local now = tonumber(ARGV[3])           -- 当前时间戳（毫秒）
local requested = tonumber(ARGV[4])     -- 申请令牌数

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last = tonumber(bucket[2]) or now

-- 补发令牌
local elapsed = math.max(0, now - last) / 1000
tokens = math.min(capacity, tokens + elapsed * rate)

if tokens >= requested then
    tokens = tokens - requested
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, 3600)
    return 1   -- 允许
else
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, 3600)
    return 0   -- 拒绝
end
"""

# 使用 Lua 脚本避免 GET-Modify-SET 竞态
def allow_request(redis_client, user_id: str, capacity=200, rate=100):
    result = redis_client.eval(
        TOKEN_BUCKET_LUA,
        1, f"ratelimit:{user_id}",
        capacity, rate, int(time.time() * 1000), 1
    )
    return bool(result)
```

### 10.2 一致性哈希的虚拟节点细节

面试中常被追问"虚拟节点要设多少个"。业界共识：

```
虚拟节点数量选择：
│
├─ 每个物理节点 100-200 个虚拟节点 → 数据倾斜 <10%
├─ 每个物理节点 1000 个虚拟节点 → 数据倾斜 <2%（DynamoDB 方案）
└─ 过多虚拟节点 → 查找性能下降（二分查找 O(log N)）

实际生产：
├─ Cassandra：默认 256 vnodes
├─ DynamoDB：每节点数千 vnodes（由 AWS 管理）
├─ Redis Cluster：16384 个 hash slot（固定分片数，不是经典一致性哈希）
└─ Ketama（libmemcached）：每节点 160 vnodes
```

来源：[Hello Interview - Consistent Hashing](https://www.hellointerview.com/learn/system-design/core-concepts/consistent-hashing)

### 10.4 缓存与 INP / Core Web Vitals 关联

Google 在 2026-03 更新了 Core Web Vitals 评估方式，从页面级改为**站点级聚合**，受影响站点流量下降 20-35%。INP（Interaction to Next Paint）仍是最常失败的指标：43% 站点未通过 200ms 阈值。系统设计层面的优化方向：

- **CDN 边缘缓存**：静态资源命中率 ≥ 95% 是 LCP 优化基线
- **服务端响应时间 ≤ 200ms**：直接影响 LCP 与 INP
- **Redis / 本地缓存分层**：Cache-Aside + LRU 是 2026 年 API 层默认配置
- **预测性加载**：Speculation Rules API + 预渲染接近 0 延迟导航
