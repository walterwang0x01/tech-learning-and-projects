## 1. 认证 vs 授权

```
认证（Authentication）— "你是谁？"
  └─ 登录、SSO、Passkey、mTLS

授权（Authorization）— "你能干什么？"
  └─ RBAC、ABAC、ReBAC、Policy as Code
```

两者常常混用，但生产系统的设计应当清晰分离。

## 2. OAuth 2.1 完全替代 2.0

2024 年 OAuth 2.1 合并了多年的 BCP（Best Current Practice），正式发布后 2025-2026 年各大平台全面迁移。

```
OAuth 2.0 → OAuth 2.1 的关键变化：
├─ PKCE 对所有客户端强制（不再只是公共客户端）
├─ Implicit Flow 彻底废弃
├─ Resource Owner Password Grant 废弃
├─ Refresh Token 要么绑定客户端，要么一次性（rotation）
├─ Redirect URI 必须精确匹配（不能通配）
└─ 明确推荐使用 OIDC 的 id_token 做用户标识
```

## 3. 授权码流程（Authorization Code + PKCE）

这是 2026 年**唯一推荐**的流程：

```
┌─── OAuth 2.1 Authorization Code + PKCE ───┐
│                                             │
│  1. 客户端生成 code_verifier（随机串）          │
│     code_challenge = SHA256(code_verifier)    │
│                                             │
│  2. 浏览器跳转到 /authorize                    │
│     ?response_type=code                       │
│     &client_id=xxx                            │
│     &redirect_uri=https://app/callback        │
│     &code_challenge=xxx                       │
│     &code_challenge_method=S256               │
│     &state=随机值                              │
│                                             │
│  3. 用户登录、授权                             │
│                                             │
│  4. IdP 回调 redirect_uri?code=xxx&state=xxx  │
│                                             │
│  5. 客户端用 code + code_verifier 换 token     │
│     POST /token                              │
│     code=xxx&code_verifier=原始随机串         │
│                                             │
│  6. 得到 access_token、refresh_token、id_token │
└─────────────────────────────────────────────┘
```

PKCE 的价值：即使中间人截获了 `code`，没有 `code_verifier` 也换不到 Token。

## 4. JWT 使用要点

### 4.1 正确使用

```python
import jwt
from datetime import datetime, timedelta, timezone

# 签发
payload = {
    "sub": "user-123",           # 主体
    "iss": "https://auth.app",   # 签发方
    "aud": "api.app",            # 受众
    "exp": datetime.now(tz=timezone.utc) + timedelta(minutes=15),
    "iat": datetime.now(tz=timezone.utc),
    "jti": str(uuid4()),         # 唯一 ID，便于撤销
}

token = jwt.encode(payload, private_key, algorithm="RS256")

# 验证
payload = jwt.decode(
    token,
    public_key,
    algorithms=["RS256"],         # 必须显式，防 none 算法攻击
    audience="api.app",           # 必须验证
    issuer="https://auth.app",    # 必须验证
)
```

### 4.2 常见 JWT 反模式

```
❌ 用 HS256 签 Token 给公开客户端
   → 共享密钥 = 可伪造
   → 改用 RS256 / ES256（非对称）

❌ 不验证 iss / aud
   → 可能被"偷"其他服务的 Token

❌ 允许 alg=none
   → 历史经典漏洞

❌ 把大量用户数据塞 JWT
   → 每个请求都带这些数据，浪费带宽

❌ JWT 作为 Session Token
   → JWT 无法即时撤销（要么等 exp，要么维护 jti 黑名单）
   → 短期（15 分钟）JWT + Refresh Token 轮换

❌ 在 localStorage 存 JWT
   → XSS 可窃取
   → 改用 httpOnly + Secure + SameSite=Strict Cookie
```

## 5. OIDC：认证身份

OAuth 是授权协议（"给 App 拿我某些数据的权限"），不是认证协议（"告诉 App 我是谁"）。OIDC 在 OAuth 上补齐认证：

```
OAuth 2.1 Access Token
  ├─ 用于 API 调用
  └─ 对客户端不透明（应用不该解析）

OIDC id_token（JWT）
  ├─ 包含用户身份：sub、email、name、picture
  └─ 客户端验证后即可知道"用户是谁"
```

scope 指定需要什么信息：

```
scope=openid                        # 必须，声明用 OIDC
scope=openid email profile          # 常用组合
```

## 6. Passkey / WebAuthn：免密码登录

2026 年 Apple / Google / Microsoft 全面推 Passkey。

> 🔄 更新于 2026-05-14

**2026 年 Passkey 里程碑**（World Passkey Day 2026-05-06）：
- **全球 50 亿 Passkey 在使用**（FIDO Alliance 估算）
- 87% 企业已部署或正在部署 Passkey
- 69% 消费者已使用 Passkey 登录
- Google 报告 25 亿次 Passkey 登录（覆盖 8 亿账户）
- 全球 Top 100 网站中约 50% 支持 Passkey
- Microsoft 对新账户默认启用 Passkey（2026-03 起）

> 来源：[FIDO Alliance State of Passkeys 2026](https://www.businesswire.com/news/home/20260506926067/en/FIDO-Alliance-Reports-Accelerating-Global-Passkey-Adoption-on-World-Passkey-Day-2026)、[Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2026/05/07/world-passkey-day-advancing-passwordless-authentication/)

```
Passkey 原理：
├─ 用户设备生成密钥对（私钥存 TPM / Secure Enclave）
├─ 注册时公钥上传到服务端
├─ 登录时服务端发 challenge，设备用私钥签名
└─ 无需密码，钓鱼免疫

用户体验：
├─ 指纹 / 面容 ID 即可登录
├─ 跨设备同步（iCloud Keychain / Google Password Manager）
└─ 零输入
```

集成示例（SimpleWebAuthn）：

```typescript
// 前端：注册
import { startRegistration } from '@simplewebauthn/browser';

const resp = await fetch('/webauthn/register/options').then(r => r.json());
const cred = await startRegistration(resp);
await fetch('/webauthn/register/verify', { method: 'POST', body: JSON.stringify(cred) });

// 前端：登录
import { startAuthentication } from '@simplewebauthn/browser';

const resp = await fetch('/webauthn/login/options').then(r => r.json());
const cred = await startAuthentication(resp);
await fetch('/webauthn/login/verify', { method: 'POST', body: JSON.stringify(cred) });
```

服务端用 `@simplewebauthn/server`（Node）、`webauthn` Python 包等。

## 8. 授权模型

### 8.1 RBAC（角色为中心）

```
User → Role → Permission

例子：
  Alice is Admin     → 有所有权限
  Bob is Developer   → 能 read/write code
  Charlie is Viewer  → 只能 read
```

简单，90% 场景够用。

### 8.2 ABAC（属性为中心）

```
条件：user.department == resource.department && user.clearance >= resource.level

用属性而非角色决定权限，灵活但复杂
```

### 8.3 ReBAC（关系为中心）

Google Zanzibar 论文衍生：

```
User → Relation → Resource

例子：
  Alice is owner of document-1
  Bob is editor of document-1
  document-1 is in folder-A
  Alice is viewer of folder-A（继承到里面所有文档）

查询：Bob 能编辑 document-1 吗？
  → Yes，有 editor 关系
```

2026 年 **ReBAC** 因为 SpiceDB、OpenFGA 等开源实现而流行，特别适合 SaaS 多租户。

## 9. Policy as Code：OPA / Cedar

### 9.1 OPA（Open Policy Agent）

```rego
# policy.rego
package authz

default allow = false

# 管理员可以做任何事
allow {
    input.user.role == "admin"
}

# 用户可以读自己的文档
allow {
    input.action == "read"
    input.resource.type == "document"
    input.resource.owner == input.user.id
}
```

```python
# 应用端
import requests

def check_access(user, action, resource):
    resp = requests.post("http://opa:8181/v1/data/authz/allow", json={
        "input": {"user": user, "action": action, "resource": resource}
    })
    return resp.json()["result"]
```

### 9.2 Cedar（AWS）

```cedar
// 类似 RBAC + ABAC + ReBAC
permit (
    principal == User::"alice",
    action    == Action::"read",
    resource
)
when { resource.owner == principal };
```

AWS Verified Permissions 托管服务。

## 10. mTLS：服务间认证

微服务之间用 mTLS（Mutual TLS）相互认证：

```
普通 TLS：客户端验证服务端
mTLS：     双方互相验证

服务 A ──mTLS──> 服务 B
  ├─ A 的证书证明它是 A
  └─ B 的证书证明它是 B
```

生产实践：
- **Service Mesh（Istio / Linkerd）自动管理 mTLS**
- **SPIFFE/SPIRE**：为每个工作负载发证书
- **Cert Manager + cert-rotator**：K8s 中自动轮换

## 11. 生产检查清单

```
☐ 所有 OAuth 客户端用 Authorization Code + PKCE
☐ JWT 用 RS256 / ES256，15 分钟有效期
☐ Refresh Token 一次性（rotation）
☐ 不在 localStorage 存 Token
☐ OIDC scope 最小化
☐ MFA 至少对管理员强制
☐ Passkey 作为新注册的默认（可选）
☐ 授权用 OPA / Cedar / OpenFGA 集中管理
☐ 服务间通信用 mTLS
☐ 审计日志：谁、何时、做了什么
☐ 账号锁定 / 速率限制防爆破
☐ 所有认证失败告警
```

### 12.3 OAuth 2.1 当前状态：仍是 IETF Draft

**重要更正**：尽管社区习惯把 OAuth 2.1 当作"已发布"，IETF 数据追踪器显示 OAuth 2.1 仍是 Working Group Draft 状态，最新版本是 **draft-ietf-oauth-v2-1-15**（2026-03 发布，到期日 2026-09-03）。

```
OAuth 2.1 标准化进度
├─ 2024 起：Working Group Draft 持续迭代
├─ draft-14：2025-10（到期 2026-04-23）
├─ draft-15：2026-03（到期 2026-09-03）
└─ 状态：尚未成为 RFC，但 BCP 内容已被各大厂商采纳
```

**实践含义**：仍可放心按 OAuth 2.1 BCP 写代码（PKCE 强制、Implicit/ROPC 弃用、Refresh Token rotation），但写文档时不要说"OAuth 2.1 已正式发布"。来源：[IETF Datatracker - draft-ietf-oauth-v2-1-15](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-15.txt)、[OAuth.net - OAuth 2.1](https://oauth.net/2.1/)

### 12.4 OAuth 2.0 路线图：仍在演进

OAuth 工作组 2026-04 发布 *A Comprehensive Roadmap for OAuth 2.0 Standards and Drafts*（draft-chen-oauth-roadmap-01），关键信号：

- **OAuth 3.0 不会有**：工作组明确声明不启动 3.0 项目，2.1 是简化与最佳实践的整合
- **Token Status List**（draft-ietf-oauth-status-list-20）：标准化 Access Token / 凭证撤销发布机制，对长期凭证场景重要
- **government-content-access-control**（draft-fx-oauth-government-content-access-control-02）：政府 / 内容平台年龄分级访问控制 profile

来源：[OAuth.net - OAuth 3.0 Statement](https://oauth.net/3/)、[IETF - OAuth 2.0 Roadmap](https://www.ietf.org/archive/id/draft-chen-oauth-roadmap-01.html)
