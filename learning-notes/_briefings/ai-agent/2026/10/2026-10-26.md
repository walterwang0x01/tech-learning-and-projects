## 📌 头条

### LangChain 拆解「公司级 harness」的五块基石

LangChain 公布了他们内部跑在营销、销售、工程三条线上的 agent 是怎么搭的，总结出五个共通原语：活在团队已有的工作场所（他们用 Slack）、带身份地行动（有些服务以调用者身份 OBO、有些用 agent 自己的身份）、分全局和用户两层记忆、代码在 sandbox 里跑并通过密钥代理安全访问外部服务、以及一大半运行是定时或事件触发的「环境 agent」而非人工手动唤起。工程 agent OpenSWE 的处理很值得抄：你 @ 它时以你的 GitHub 账号开 PR，它后台自动 review 时则用自己的 GitHub App 身份——身份边界划得清清楚楚。全部建在开源 Deep Agents harness 之上的 Managed Deep Agents。如果你在搭团队内部 agent，这篇基本是一张「别踩的坑」清单，身份和 ambient 触发这两块尤其值得照着对一遍。

→ [原文](https://www.langchain.com/blog/components-building-company-harness)

### Kimi K3.1 Pro 限流翻车，月之暗面全员重置额度道歉

月之暗面 10 月 24 日刚发布 3 万亿级参数、支持 100 万上下文的 K3.1 Pro，两天后就凌晨发文致歉：会员使用时出现限流和「不必要的额度消耗」。官方补偿是给所有有效期内会员重置一次，发放月度总额 25%（约一周用量），当前用量不足 25% 的直接清零。更关键的是官方承认在「减少不必要的子 Agent 调用和输出长度」——这正好印证了 HN 上一位用户的吐槽：用官方 CLI 跑两个小任务，5 小时额度几分钟耗尽，账单显示光缓存输入就吃掉 118 万 token。对重度用 coding agent 的人来说，这是一记提醒：模型越能自主调子 agent，token 账单越容易失控，上线前先把子调用和输出长度的预算卡死。

→ [官方致歉](https://www.ithome.com/1/017/723.htm) / [HN 吐槽](https://news.ycombinator.com/item?id=50222093)

## 📈 趋势

- 🔺 Agent 从独立 App 向 IM/短信等已有渠道下沉——「活在你已经用的地方」正成为产品共识
- 🆕 子 agent 调用带来的 token 失控浮出水面：Kimi 限流事件说明越自主的 agent 越需要预算护栏
- 🔺 身份边界（OBO vs 固定凭据）成为企业级 agent 的核心设计点，LangChain 把它列为五大基石之一
