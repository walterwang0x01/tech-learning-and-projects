### 教皇首份 AI 通谕落地，Anthropic 同台站位

Pope Leo XIV 在 5 月 25 日正式发布首份社会通谕《Magnifica humanitas — On safeguarding the human person in the time of artificial intelligence》，要求「disarm AI」——不是拒绝技术，而是阻止它被极少数人垄断、阻止它压过人。文件 4.23 万词、官方分类是 social encyclical，相当于教廷最权威的训导文件。最戏剧性的是发布会现场：Anthropic 联合创始人、可解释性负责人 Chris Olah 站在教皇旁边代表 AI 行业发言，是 AI 公司第一次以这种方式被纳入梵蒂冈的伦理叙事。对你日常做 agent 的影响在两层：一是欧洲监管会拿这份通谕直接当道德背书去推 AI Act 二轮收紧；二是 Anthropic 的「负责任 AI」品牌定位被钉得更死，企业大单（Wall Street JV、Goldman/Blackstone）跟这次站台是一条线。短期不会改 prompt，但你写产品说明、合规文档时可以参照这套语汇，比硬怼 EU AI Act 条款好用。

### 微软 Webwright：把 web agent 从浏览器会话搬进终端工作区

微软研究院在 5 月 25 日开源 Webwright，定位是 terminal-native web agent harness：传统 web agent 把状态绑在一条长生命周期 browser session 上预测下一次点击，Webwright 反过来——浏览器随用随抛，所有状态（代码、日志、截图、输出）持久化在本地 workspace。配合 Playwright CLI，长任务里通过每 20 步一次的 context 压缩防止上下文爆掉。给的数据是 Odysseys 长程 web 任务上 60.1%，比 GPT-5.4 baseline 33.5% 高出 26.6 个百分点，挂上了 SOTA 标签。这个架构哲学跟 Anthropic 推的 harness engineering、LangChain 写的 Agent Harness 拼图是合上的——agent 的真正护城河不在模型，在 harness 里的状态管理和工具边界。如果你在做 web/computer-use agent，本周值得花半天把 Webwright clone 下来对比下你自己 harness 的 token 占用，特别是 accessibility tree 还在裸塞上下文里的项目。

→ [Webwright 官网](https://microsoft.github.io/Webwright/) / [GitHub](https://github.com/microsoft/Webwright) / [Winbuzzer 报道](https://winbuzzer.com/2026/05/25/microsoft-webwright-turns-web-agents-into-reusable-code-xcxwbn/)

## ⚡ 快讯

- **Hugging Face 给 agent 术语正名**：Hugging Face 发布 agent 词汇表《Harness, Scaffold, and the AI Agent Terms Worth Getting Right》——把过去半年被滥用的 harness、scaffold、context engineering 和 agent 几个概念逐一梳清楚。核心论点：模型只能表达调用工具的意图，要靠 harness 真正执行；裸模型回答一个 prompt 就停，套上 scaffolding + harness 才成 agent。LangChain 在同主题发的《Anatomy of an Agent Harness》和 Hashimoto 的「harness engineering」一起被引用，这套词汇明显在工业界稳定下来。 → [HF Blog](https://huggingface.co/blog/agent-glossary) / [LangChain Anatomy](https://blog.langchain.com/the-anatomy-of-an-agent-harness/) / [Anthropic Harness 设计](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- **SaaS-Bench：Computer-Use Agent 完全通过率仅 3.8%**：UniPat AI 的 SaaS-Bench 评测把 Claude、GPT-5、Gemini 等主流 computer-use agent 放进真实办公场景（Notion、Salesforce、Jira 等 SaaS 流程），整链路完全通过率最高 3.8%，意味着「全自动办公」的演示视频跟生产之间还有两个数量级的距离。论文同时指出当前 agent 主要卡在多组件状态同步和长程错误恢复，呼应同档期 SaaSBench/WindowsWorld/SCUBA 三篇论文的一致结论：复杂跨应用工作流的 SOTA 还在 9-19% 区间。 → [量子位中文报道](https://www.qbitai.com/2026/05/424277.html) / [arXiv 原文](https://arxiv.org/abs/2605.15777)
- **Anthropic 盈利公关被拆穿**：Ed Zitron 在 Where's Your Ed At 长文系统拆解 Anthropic 通过 WSJ 释放的「首次盈利」消息，指出这是用两个月成本折扣窗口、人为压低披露口径加上时机选择拼出来的公关叙事，公司商业基本面没变。结合此前 Microsoft 取消内部 Claude Code 授权、Uber 四个月烧光全年 AI 预算的报道，「打折型盈利」正在动摇买方对 AI 厂商定价的长期预期。Arnon Shimoni 同期博文从定价决策者视角佐证——AI 固定费率模式正在系统性崩解。 → [盈利戏码拆解](https://www.oschina.net/news/445810/anthropics-profitability-swindle) / [AI 定价模式复盘](https://www.oschina.net/news/445834)
- **商汤开源「会改算法代码」的智能知识底座**：商汤在 OSChina 公开自家研发的智能知识底座，主打卖点是 RAG 系统能自己改算法代码、自己跑 A/B 测试、自己进化——10 人维护上百项目的能力被归功于这套底座的自进化能力。原文叙述偏宣传，但思路在国内 RAG 实践里是少见公开的：把代码生成 + 评测闭环纳入 RAG 自身的运维，而不是停在传统的「人工造问答对、调 topK」阶段。 → [商汤博客](https://my.oschina.net/u/8690838/blog/19681712)
- **ClickHouse 实战 Agentic Coding 复盘**：InfoQ 中文发出 ClickHouse 团队的一线复盘，主题是 Agentic Coding 在大型 OLAP 引擎开发里的真实价值——既有「神」的部分（多线程死锁定位、SIMD 重构提速 30%），也有「坑」（架构级改动经常被 agent 越权改坏，回退成本高）。结论跟昨天「Claude is not your architect」的争论吻合：agent 适合做 reviewer/implementer，不适合做 designer。 → [InfoQ 中文](https://www.infoq.cn/article/OLEDsNifw48YdleTAZDg)
- **Memory Poisoning Misattribution Gap**：arXiv 新论文指出多 agent 流水线的失败诊断有结构性盲点——记忆投毒（poisoning）在表象上跟模型对齐失败几乎不可区分，被误归因成「模型问题」从而错过补救窗口。这跟 RAG-Pull 论文（Unicode 隐形扰动把检索变成代码注入通道）和 Through the Stealth Lens（attention-aware 防御）一起，构成今天 arXiv 上 agent 安全主题的连发：攻击面在变深，防御从「检测毒数据」走向「定位归因」。 → [Misattribution Gap](https://arxiv.org/abs/2605.22842) / [RAG-Pull](https://arxiv.org/abs/2510.11195) / [Stealth Lens](https://arxiv.org/abs/2506.04390)
- **Skill Retrieval Augmentation：把 RAG 从知识扩到技能**：arXiv 论文把检索对象从文档扩到「可复用 skill」——agent 在新任务里先检索匹配的工具/操作模板，再用 LLM 做组合执行。配合同期发的 SUDP（Secret-Use Delegation Protocol，给 agent 用密钥这件事做出明确委托协议），思路上是把 agent runtime 从「装一堆 tools 凭 LLM 自由调度」转向「按需检索 + 显式权限」。对常踩 tool schema 爆上下文的团队是直接的方法论。 → [Skill Retrieval](https://arxiv.org/abs/2604.24594) / [SUDP 协议](https://arxiv.org/abs/2604.24920)
