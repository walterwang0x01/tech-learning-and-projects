## 📌 头条

### 智谱 ZCode 被曝静默打包上传整个工作区

多个技术社区（linux.do、Tom's Hardware）本周实测：ZCode 客户端登录后会在后台把整个工作区连同完整 .git 历史打包加密后上传到云端对象存储，且解密私钥只存在服务端。一份取证报告给出的具体数字是：某开发者的工作区被打成 313MB 加密包、共 42,411 个文件，客户端尝试上传 564 次。完整 git 历史的杀伤力在于它会连带泄露旧密钥、内网仓库地址和主机名，比只传当前文件敏感得多。Z.ai 随后开源了 ZCode 作为回应，据社区消息 GLM-5.5 也因此延期。对你意味着什么：用任何 AI 编程 agent 前，先确认它的「长程任务 / 端到端」功能到底读什么、传什么——最稳妥的是在敏感仓库里默认断网或用文件系统只读锁挡住上传路径。

→ [开源中国报道](https://www.oschina.net/news/502625) / [Tom's Hardware（英文汇总）](https://aiweekly.co/alerts/zai-open-sources-zcode-after-silent-313mb-workspace-upload)

### Jev 判断模型进驻 LangSmith Evals

LangChain 官方博客宣布，把 TypeSafe 上周开源的 Jev 接进 LangSmith 作为评估用的 judge。Jev 是个「只做判断不生成文本」的 System One 模型：输入非结构化状态和一组类型化问题，输出概率、打分或从你定义的选项里选一个，一次请求约 100ms。TypeSafe 自己给的口径是在分类任务上比同级 LLM 快 20–200 倍、便宜 40–400 倍（这是厂商数据，未见独立复测）。放进 LangSmith 后可以用它来批量评估 agent 轨迹，替代传统的 LLM-as-judge。对你意味着什么：如果你在用 LangSmith 跑 agent 回归测试，值得拿自己的 trace 数据集试一把 Jev-as-judge，对比它和现有 LLM judge 的一致性和成本——但结论要用集合比较验证，别直接信厂商的加速倍数。

→ [LangChain 官方博客](https://www.langchain.com/blog/jev-is-now-available-in-langsmith-evals) / [开源中国：Jev 解析](https://www.oschina.net/news/502633)

## 📈 趋势

- 🆕 「判断模型」独立成类：Jev 这种只做分类 / 路由 / 打分、不生成文本的 System One 模型开始被主流评估平台（LangSmith）吸纳，冲击 LLM-as-judge
- 🔺 AI 编程 agent 的数据边界成焦点：ZCode 静默上传 git 全历史事件把「agent 到底读什么传什么」推上台面，本地代码隐私 > 效率成新共识
- 🔺 agent 评估从「任务成功率」转向「轨迹可审计 + 成本」：多篇论文（Verify Don't Trust、LogicTrack、生产环境高效 benchmark）都在做轨迹级验证而非只看输出
- 🆕 Agentic 计算下沉到基础设施：华为、OceanBase 都在从算力 / 数据库层重新设计以承接长程 agent 的时延和通信压力，而非只在模型层竞争
