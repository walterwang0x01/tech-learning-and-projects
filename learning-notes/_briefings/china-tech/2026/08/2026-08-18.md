### 阿里千问办公开源 MyContext：给 Agent 补上企业上下文层

阿里千问办公团队开源了 MyContext，目标是把散在钉钉聊天、企业文档、会议记录和本地数据源里的工作信息，持续加工成 Agent 能直接消费的上下文。仓库 openTrinity/mycontext 建于 8 月 3 日，TypeScript 实现，现在 1.3k star 出头——注意仓库自述把它定位成「local-first desktop app for everyday communication and knowledge work」，而量子位那篇讲的是「上下文基础设施」，两个口径不完全一致，想集成的话先按桌面端应用的边界去读代码。技术上真正值得抄的是三个取舍：幂等性绑在数据源的稳定标识而不是时间戳上（迟到消息只要没消费过照样进链路），Session 边界用对话空闲间隔切而不是固定 token 数，事实冲突走「三态合并」——一致就加置信度、互补就并入、真冲突就同时保留多条并下调置信度显式暴露给人，用户人工确认过的结论禁止模型自动覆盖。成本侧靠增量计算兜住：能用本地规则判断的不进模型，算过的结果复用，多次更新攒批。产业视角上这是阿里拿钉钉的组织数据入口去对标 Palantir 的 Ontology、Glean 的 Enterprise Graph 和 Microsoft Graph + Copilot Connector——同一条路线，但入口在国内。如果你在做 LangGraph 或 MCP 侧的记忆层，这套「时序 + 冲突 + 增量」的处理思路比它的产品形态更值得读。

→ [量子位](https://www.qbitai.com/2026/08/474647.html) / [GitHub](https://github.com/openTrinity/mycontext)

### GitHub 宕机七小时，代码托管的单点依赖被当场点名

8 月 17 日 13:40 UTC（北京时间 21:40）起 GitHub 大面积故障，到 8 月 18 日凌晨 5:15 才完全恢复，全程超过七小时。受影响面几乎覆盖核心功能：网站与 API 错误率约 20%，archive 下载和 raw 内容抓取失败率约 50%，Actions、Pull Request、Webhooks 全线受累；GitHub 宣布八项受影响服务中七项缓解时，Copilot 的认证问题还挂着。根因至今没有公开说明，但 The Register 引用了 GitHub 自己 5 月的可用性报告——AI 辅助编码和 agentic workflow 正在加重平台负载，这已经是 8 月的第二次事故。巧的是同一天上午 Cursor 上线了 Origin，一个内建在编辑器里的代码托管 + PR 平台，beta 面向付费用户，仓库地址形如 cursor.com/codebase/<name>；TNW 报道称它对付费用户默认开启且数据条款尚未公布，这是媒体口径，介意的人先自己去设置里确认。别急着信「GitHub 完了」那套叙事——Origin 还是早期 beta，规模、可靠性和生态深度都没有公开证据。对国内团队更实际的动作是查一遍 CI：依赖拉取和镜像有没有单点走 raw.githubusercontent，Actions 挂了之后有没有别的发布路径。

→ [开源中国](https://www.oschina.net/news/501978/github-outage-disrupts-developers-worldwide) / [The Register](https://www.theregister.com/ai-and-ml/2026/08/17/github-has-issues-as-repo-downloads-hit-50-error-rate/5288543) / [Cursor Origin 报道](https://thenextweb.com/news/cursor-origin-opt-out-data-terms-spacex-github-outage)
