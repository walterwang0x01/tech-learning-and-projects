### Netflix 迁移到开源 Flink Autoscaler，年省百万美元

Netflix 正把 3 万多个 Flink 流式作业迁到开源的 Apache Flink Autoscaler（覆盖多个 AWS 区域）。以前它用的是集群级扩缩容，整个作业的所有算子共享一个决策，对带分支、连接、数 TB 状态的复杂管道很吃亏；新方案按 FLIP-271 逐算子估算真实处理速率、再遍历作业图给每个顶点单独定并行度。官方给了具体数字：某团队 Flink 计算支出年化降了 58%，一年省约 110 万美元。落地细节值得抄作业——它没有直接用 Flink Kubernetes Operator，而是用一个 Spring Boot 服务 + Temporal 工作流来隔离每个作业的扩缩容决策，并把利用率目标设到 0.45（低于社区默认 0.7）以减少大状态作业的激进重扩。如果你在做有状态流处理或用 Temporal 编排，这篇 Netflix 博客的工程取舍很有参考价值。

→ [InfoQ 中文](https://www.infoq.cn/article/8JZ9IdSIxo18dcz6pZG6) / [英文原文](https://www.infoq.com/news/2026/09/netflix-flink-autoscaler/)

### Kubernetes v1.37：原生直方图进入 Beta 并默认开启

Kubernetes v1.37 把 Prometheus Native Histograms（KEP-5808，v1.36 时是 Alpha）升级到 Beta 且默认开启。传统 classic histogram 要作者预先猜好一组静态桶边界，猜不准就丢可见性，而且每个桶是一条独立时间序列、成本高，分位数还靠线性插值有误差。原生直方图改成动态指数桶存进单条时间序列，官方说时间序列数最多减少 90%，分位数在默认设置下最坏相对误差约 5%，且支持任意量级（纳秒到小时）自动调分辨率。为了不破坏现有栈，开了 feature gate 后走 dual exposition——同一份 Protobuf 里同时带 classic 桶和 native span，老的 Prometheus/看板/告警规则不用改照常跑。如果你在管自己的 K8s 可观测性，这是个能省存储又提精度、且平滑升级的改动。

→ [Kubernetes 官方博客](https://kubernetes.io/blog/2026/09/11/kubernetes-v1-37-native-histograms-beta)
