### GitHub 宕机 7h47m 复盘：不是改配置，是没扩容

GitHub CTO Vlad Fedorov 亲自写了 8 月 17 日那次 7 小时 47 分钟宕机的复盘，github.com、认证、Actions、API、PR/Issue 和 Copilot 全线受影响。官方结论跟中文转载普遍写的「负载均衡配置错误」不一样：故障起点是流量创新高时 Central US 数据中心一个关键基础组件没能跟着扩容，容量压力扩散引发认证失败；重试风暴出现在恢复阶段——部分 Copilot 服务报错触发了客户端重试循环，反过来把恢复期流量顶上去，必须先压住这个行为才能安全放量。复盘里有一句写得很明确：8 月 6 日和 8 月 17 日两次事故都不是代码或配置变更引起的，本质都是容量失败。规模数字解释了压力来源：4 月以来月度 commit 从 14 亿涨到 29 亿，GitHub 为此加了 300 万+ CPU 核心、120PB 高速存储，Azure 承载的平台负载从 5 月的 12% 升到约 58%。落到自己系统上可抄的只有两条即时整改：给所有服务间调用统一 retry 上限、retry 预算和可变超时，以及把之前被当作低优先级的 CPU/内存告警重新过一遍。

### Rust 生态被 build-time 恶意 crate 打穿

8 月 20 日，crates.io 上同一个维护者账号下的三个正常 crate 被发布了投毒版本：arrayref@0.3.10、internment@0.8.7、append-only-vec@0.1.9。手法值得记住——投毒版本没改原始源码，只是新增了一个 typosquat 依赖 proc-macro1（冒充广泛使用的 proc-macro2），由它的 build script 在编译期下载并执行远程二进制。也就是说 cargo build 就中招，不需要你调用任何 API。影响面看下载量很吓人：arrayref 历史下载约 2.44 亿次，近 90 天约 5370 万次，403 个 crate 直接依赖它，而绝大多数团队是通过密码学、图形、区块链库间接引进来的。官方 RUSTSEC-2026-0260 的说法是恶意版本上线约 86 分钟后被移除，暂无实际被使用的证据；Wiz 单方面报告称该攻击与朝鲜相关组织的活动有重叠，这一归因目前只有它一家。现在该做的是搜一遍所有 Cargo.lock 里有没有 proc-macro1，并把 CI 构建切到 --locked / --offline，别让 cargo update 自己去解析新依赖。

→ [Rust 官方公告](https://blog.rust-lang.org/2026/08/20/supply-chain-attack-on-arrayref/) / [SafeDep 技术分析](https://safedep.io/arrayref-proc-macro1-rust-build-time-malware/) / [下载量与依赖统计](https://thehackernews.com/2026/08/rust-supply-chain-attack-puts-build.html)
