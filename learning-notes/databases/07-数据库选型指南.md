│    │                              │
│    ├─ 全文检索 → Elasticsearch / OpenSearch │

## 2. 主流数据库能力对比（2026 版）

| 数据库 | 类型 | 强项 | 弱项 | 典型场景 |
|--------|------|------|------|----------|
| **PostgreSQL 18** | OLTP 关系型 | 功能最全、扩展性强 | 横向扩展需要中间件 | 通用业务 |
| **MySQL 8.4 LTS** | OLTP 关系型 | 生态广、云厂商支持 | 功能比 PG 弱 | 互联网通用 |
| **Redis 8.6** | KV + 多模 | 性能极高、功能全（JSON/Search/TimeSeries/Stream） | 单机内存昂贵 | 缓存、限流、计数 |
| **MongoDB 8.x** | 文档 | 模型灵活、横向扩展好 | 事务弱、关联差 | Schema 多变的业务 |
| **Elasticsearch 9.x** | 搜索 + 分析 | 全文检索、复杂聚合 | 写放大、内存需求大 | 日志、搜索、APM |
| **ClickHouse 26.5** | OLAP 列存 | 亿级行秒级聚合 | 更新慢、并发低 | 日志、BI、大数据分析 |
| **DuckDB 1.5** | 嵌入式 OLAP | 单机分析极强、零运维 | 单用户、无分布式 | 本地分析、ETL |
| **TimescaleDB** | 时序（基于 PG） | 连续聚合、压缩、兼容 SQL | 超大规模需集群版 | IoT、金融、监控 |
| **Neo4j** | 图 | Cypher 表达力强 | 商业授权、硬件要求 | 社交、反欺诈、知识图谱 |
| **Qdrant / Milvus** | 向量 | 亿级向量、低延迟 | 专用，不能当通用库 | 大规模 RAG |
| **CockroachDB 24+** | 分布式 SQL | 全局事务、自动分片 | 成本高、延迟比单机高 | 全球部署、强一致 |
| **TiDB 8.x** | HTAP | 兼容 MySQL + 分布式 OLAP | 运维复杂 | 规模化互联网 |

## 3. 典型组合

### 3.1 小团队 / MVP

```
PostgreSQL + Redis

覆盖 90% 业务：
  ├─ PG 存所有业务数据 + JSONB + pgvector
  ├─ Redis 做缓存 + 限流 + Session
  └─ 单机可以跑到千万用户
```

### 3.2 中等规模 SaaS

```
PostgreSQL (Primary + Read Replica) + Redis + ClickHouse + S3

  ├─ PG 主备：业务数据
  ├─ Redis：缓存、队列
  ├─ ClickHouse：日志、用户行为分析
  └─ S3：文件存储、归档日志
```

### 3.3 大规模互联网

```
MySQL 分库分表 / CockroachDB + Redis Cluster +
Kafka + ClickHouse + Elasticsearch + Qdrant + 对象存储

  按业务领域拆分数据库，每个服务一个
```

### 3.4 AI Agent 应用

```
PostgreSQL (业务 + pgvector) + Redis (会话 + 限流) + ClickHouse (Trace + 评估)

  ├─ PG：用户、订单、Agent 配置、向量
  ├─ Redis：会话状态、速率限制、Token 缓存
  └─ ClickHouse：Trace、LLM 调用日志、评估结果
```

## 4. CAP 定理的 2026 版理解

```
CAP 原始：C/A/P 三选二（网络分区时，一致性和可用性不可兼得）

现代理解：
  在云时代，网络分区总会发生（P 必选）
  所以真正的选择是"分区时选 C 还是 A"

CP 系统：
  ├─ PostgreSQL 同步复制
  ├─ CockroachDB、Spanner
  └─ 分区时拒绝服务，保证数据正确

AP 系统：
  ├─ Cassandra、DynamoDB
  ├─ Redis Cluster（默认）
  └─ 分区时继续服务，事后解决冲突

混合：
  ├─ 大多数系统都支持可调一致性
  └─ Cassandra 的 QUORUM、DynamoDB 的 Strongly Consistent Read
```

## 5. 数据库 + AI 的新趋势

### 5.1 数据库里做 Embedding

```
传统：应用层调 OpenAI 做 embedding → 存向量到 PG

新趋势：
  ├─ pg_vectorize（Tembo）：PG 扩展直接调 embedding API
  ├─ Neon RAG：托管服务，内置 embedding
  └─ Supabase Vector：同理
```

### 5.2 数据库作为 Agent Memory

```
Agent 长期记忆层首选：
  ├─ PostgreSQL + pgvector（轻量、自建）
  ├─ Zep（托管，Graphiti 引擎）
  └─ Mem0（云服务 + 自托管）
```

### 5.3 GraphQL / REST 自动生成

```
Postgres → API 的零代码方案：
  ├─ Supabase：Postgres + PostgREST + Realtime
  ├─ Hasura：GraphQL over Postgres
  ├─ PostgREST：纯 Postgres → REST
  └─ 2026 年 Supabase 成为"BaaS 默认选择"
```

### 5.4 MCP Server for Database

```
让 AI Agent 直接查数据库：
  ├─ Postgres MCP Server
  ├─ MongoDB MCP Server
  └─ ClickHouse MCP Server

警告：生产数据库不要无限制暴露给 Agent
  ├─ 只读用户 + RLS + 查询超时
  └─ 见 [security/06-LLM与Agent安全.md](../security/06-LLM与Agent安全.md)
```

## 7. 反模式

```
常见选型错误：
├─ "大家都在用 MongoDB 所以我也用"
│   → 业务是关系型的，硬塞文档模型会很痛
├─ 所有缓存都用 Redis
│   → 本地内存缓存 + Caffeine 比 Redis 快 100 倍
├─ 日志存关系型 DB
│   → ClickHouse / Loki / Elasticsearch
├─ 为了可能的未来引入分布式 DB
│   → 单机 PG 能撑几千万用户，不要过度设计
├─ 用 Redis 做持久化主存储
│   → 单机内存贵、RDB 恢复慢，用真正的 DB
└─ 向量存 Redis（没版本控制、无混合检索）
    → 专用向量 DB 或 pgvector
```

## 8. 迁移注意事项

```
从 MySQL 迁到 PostgreSQL 常见坑：
├─ AUTO_INCREMENT → SERIAL / IDENTITY
├─ utf8mb4 → UTF8（PG 默认就是完整 UTF-8）
├─ 时区：DATETIME → TIMESTAMPTZ
├─ GROUP BY 严格模式：PG 不允许 SELECT 非聚合列
├─ LIMIT x, y → LIMIT y OFFSET x
├─ 双引号和单引号：PG 双引号是标识符，单引号才是字符串
└─ ON DUPLICATE KEY UPDATE → ON CONFLICT DO UPDATE

工具：
  ├─ pgloader（MySQL → PG 自动迁移）
  ├─ AWS DMS
  └─ 字节开源的 DataEx
```
