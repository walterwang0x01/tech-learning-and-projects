## 1. 从数据仓库到 Lakehouse

```
┌──── 十年数据架构演进 ────┐
│                           │
│  2010s：传统数据仓库         │
│  ├─ Teradata / Oracle     │
│  ├─ ETL（昂贵、缓慢）        │
│  └─ 只支持结构化数据         │
│         ↓                 │
│  2015s：Data Lake           │
│  ├─ HDFS / S3 + Parquet   │
│  ├─ Schema on Read         │
│  ├─ 便宜，但质量差（沼泽）    │
│         ↓                 │
│  2020s：Lakehouse           │
│  ├─ S3 + 表格式（Iceberg/Delta/Hudi）│
│  ├─ ACID 事务 + 时间旅行     │
│  ├─ 开放标准，计算引擎解耦     │
│  └─ 一份数据支撑 BI + AI + ML│
└───────────────────────────┘
```

**2026 年新共识**：数据基础设施的"最终形态"是开放表格式（Iceberg 胜出）+ 任何计算引擎。

## 3. ELT vs ETL

```
ETL（老派）：
  Extract → Transform（复杂 ETL 工具）→ Load（数仓）
  问题：
  ├─ 转换逻辑在 ETL 工具，难版本化
  ├─ 改 Schema 要重做整个管道
  └─ 只能走预定路径

ELT（现代）：
  Extract → Load（原始数据入湖）→ Transform（在数仓做）
  优势：
  ├─ 原始数据永远保留，可重算
  ├─ 转换用 SQL + dbt，Git 管理
  ├─ 新需求只要加一层转换
  └─ 调试和数据回填容易
```

**2026 年几乎所有新数据平台都是 ELT。**

> 🔄 更新于 2026-07-08：**dbt Core v2.0 进入 alpha**（6 月 1 日 alpha.1 → 6 月 29 日 alpha.3）。v2 基于 Rust 重写（与 Fusion 引擎同源），单二进制分发、解析/编译速度大幅提升，产出 Parquet 元数据产物（`manifest.json` 仍保留兼容），语言规范更严格。v1.12 仍是生产主线——可用 `dbt parse --use-v2-parser` 预检迁移。编排层（Airflow 3.3 / Dagster 1.13）已跟进 dbt Fusion 结果格式兼容。来源：[dbt Core v2 公告](https://docs.getdbt.com/blog/dbt-core-v2-is-here)、[CHANGELOG alpha.3](https://github.com/dbt-labs/dbt-core/blob/HEAD/CHANGELOG.md)、[v2 路线图](https://github.com/dbt-labs/dbt-core/blob/main/docs/roadmap/2026-06-announcing-v2.md)

## 4. 分层建模（Medallion Architecture）

```
Bronze（铜）：原始数据
  ├─ 源系统 schema 保留
  ├─ 只做必要清洗
  └─ 1-3 年保留

Silver（银）：清洁数据
  ├─ 去重、类型规范、字段统一命名
  ├─ 业务实体层（users、orders、events）
  └─ 供下游 100% 复用

Gold（金）：业务聚合
  ├─ 给 BI / 业务使用的宽表
  ├─ 按主题组织（Marketing、Finance）
  └─ 可能是物化视图或预计算表
```

dbt 项目结构天然贴合这个分层：

```
models/
├── bronze/     # staging models（一对一对应源表）
├── silver/     # intermediate models
└── gold/       # marts (fact / dimension / aggregate)
```

## 5. Data Contract：治理的关键

```
传统：下游依赖上游 DB 表
  → 上游改字段，下游崩溃
  → 上游不敢改，技术债堆积

Data Contract：上下游签"接口"
  ├─ 明确字段、类型、SLA、Owner
  ├─ Schema 变更走 PR 流程
  ├─ 违反契约的数据在管道里被拒绝
  └─ 工具：Soda Cloud、dbt Contract、Datahub
```

<!-- 修复于 2026-05-30: 补充 Data Contract 标准收敛提示，与 07-数据质量与契约.md 第 7 节保持一致 -->
> 🔄 更新于 2026-05-30：数据契约标准已收敛——随 ODCS 3.1 发布，datacontract.com 的 Data Contract Specification 已 sunset，官方推荐迁移到 [ODCS（Open Data Contract Standard，bitol-io）](https://bitol-io.github.io/open-data-contract-standard/)。详见 → [数据质量与契约](07-数据质量与契约.md) 第 7 节。

```yaml
# dbt 模型契约示例
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: string
        constraints:
          - type: not_null
          - type: primary_key
      - name: user_id
        data_type: bigint
        tests:
          - not_null
          - relationships:
              to: ref('dim_users')
              field: user_id
      - name: amount_cents
        data_type: bigint
```

## 6. Data Mesh 与中心化的权衡

```
Data Mesh（2020 年提出）：
  ├─ 去中心化：每个业务域负责自己的数据产品
  ├─ Self-serve 平台
  └─ 联邦治理

中心化（传统）：
  ├─ 数据平台团队承担所有 pipeline
  └─ 规模变大后团队成为瓶颈

2026 年共识：
  ├─ 中小公司：中心化够用
  ├─ 大公司：Mesh + 中心平台的混合
  ├─ "数据平台"提供工具链和标准
  └─ "业务域"生产并维护自己的数据产品
```

## 9.5 表格式新趋势：DuckLake 1.0

> 🔄 更新于 2026-05-20

DuckDB 团队在 2026-04-13 发布 DuckLake v1.0 标准，给"Iceberg / Delta / Hudi 三足鼎立"加了第四个选项。核心想法是：**lakehouse metadata 本来就该放在 SQL 数据库里**，而不是分散成成千上万个 JSON 文件存在对象存储。

```
传统 Lakehouse 表格式（Iceberg/Delta/Hudi）：
└─ 对象存储里：metadata.json + manifests + data.parquet
   + REST Catalog 服务（Polaris/Glue/Unity）

DuckLake 1.0：
└─ SQL 数据库（Postgres / SQLite / DuckDB）：几张表保存元数据
   + 对象存储里：只放 Parquet 数据文件
   + 不需要单独的 catalog 服务
```

**v1.0 已生产可用**：sorted tables、bucket partitioning、data inlining（小表数据直接进元数据库）、geometry 支持、Iceberg 兼容的 deletion vectors。

**适合场景**：

- Agentic Analytics——Agent 几秒拉起一个 lakehouse
- 多人多写的"multiplayer DuckDB"
- GB ~ 中 TB 数据规模、不想维护 Polaris/Glue 的团队

**不适合**：PB 级数据 + 跨 Spark/Flink/Trino 共享场景，仍然要选 Iceberg。

详见 → [Lakehouse 表格式：Iceberg / Delta / Hudi](04-Iceberg-Delta-Hudi对比.md) 第 14 节。来源：[DuckDB Blog — DuckLake 1.0](https://duckdb.org/2026/04/13/ducklake-10.html)、[InfoQ — DuckLake 1.0](https://www.infoq.com/news/2026/05/ducklake-sql-catalog/)

## 10. 成本模型

```
现代数据栈的成本结构：
├─ Storage：S3，单位成本极低（~$0.02/GB/月）
├─ Compute：按查询 / 按实例（主要支出）
├─ Ingest：按 GB 或按 row
└─ People：数据工程师工资（最大成本）

优化方向：
├─ 分区 + 文件格式优化（Parquet + 列裁剪）
├─ 查询缓存 + Materialized View
├─ 分层：热数据 Snowflake，冷数据 Iceberg
└─ 为"查询速度 vs 成本"明确分级 SLO
```

## 11. 反模式

```
数据架构常见失败：
├─ 把 OLTP 数据库当数仓用
│   → 分析查询锁住业务库
├─ 把数据湖变成数据沼泽
│   → 原始文件堆积、无 Schema、查不到、无人用
├─ 一个巨型 Airflow DAG
│   → 维护地狱，一处失败全线停
├─ 无 Data Contract 的跨团队依赖
│   → 上游一改全线崩
├─ 没有数据质量监控
│   → Dashboard 展示"好看的错数据"
├─ 上线即遗忘
│   → 模型产出没人看，成本持续爬升
└─ 用 Excel 做 single source of truth
    → 多人改、版本失控
```
