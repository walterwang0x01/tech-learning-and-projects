## 1. 为什么要数据质量

```
"垃圾进，垃圾出"：
├─ Dashboard 数据错误 → 错误决策
├─ ML 模型输入偏差 → 模型效果不可靠
├─ 下游服务依赖脏数据 → 雪崩式故障
└─ 数据消费者失去信任 → 自己"重做一套"

数据质量是数据团队的"SLA"
```

## 2. 数据质量的六个维度

```
完整性（Completeness）
  └─ 不该是 NULL 的字段不为 NULL
     用户表的 email 不能缺失

唯一性（Uniqueness）
  └─ 主键、唯一约束
     没有重复用户（同 email）

及时性（Timeliness）
  └─ 数据按时到达
     每日报表数据应该早上 8 点可用

准确性（Accuracy）
  └─ 数据反映真实
     订单金额等于 items 总和

一致性（Consistency）
  └─ 不同系统中的同一实体一致
     CRM 的用户和 BI 的用户对得上

合理性（Validity）
  └─ 符合业务规则
     年龄在 0-150，邮箱格式合法
```

## 3. 测试 vs 质量 vs 契约

```
数据测试（Data Testing）
  └─ 在管道里检查（dbt tests、GE）
     失败 → Pipeline 失败

数据质量监控（DQ Monitoring）
  └─ 持续监控已有数据
     失败 → 告警，不阻塞

数据契约（Data Contract）
  └─ 上下游约定"接口"
     违反 → 上游不能合并 PR
```

三者互补，不可替代。

## 4. dbt 内置测试

最轻量、零成本：

```yaml
# models/schema.yml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: user_id
        tests:
          - not_null
          - relationships: {to: ref('dim_users'), field: user_id}
      - name: status
        tests:
          - accepted_values: {values: [pending, paid, cancelled]}
      - name: amount
        tests:
          - dbt_utils.expression_is_true: {expression: ">= 0"}

    tests:
      # 表级测试
      - dbt_utils.equal_rowcount: {compare_model: ref('stg_orders')}
```

运行：`dbt test --select fct_orders`。

详见 [03-dbt数据建模.md](./03-dbt数据建模.md)。

## 5. Great Expectations（GE）

最流行的数据质量框架。

> 🔄 更新于 2026-05-30
>
> **API 重大变更警告**：下面的代码示例使用的是 **GX 0.x 旧 API**（`context.sources.add_sql`、`get_validator`、`add_or_update_checkpoint`），在 **GX Core 1.x（当前 1.18.2）中已废弃**。GX 1.0 重构了核心工作流，改为 **Data Source → Batch Definition → Expectation Suite → Validation Definition → run()** 模型。新项目请参考下方 1.x 写法。
<!-- 修复于 2026-07-08: GX Core 最新版 1.18.2（PyPI 2026-06-26），原文写 1.17.2 -->
> 另：**Fivetran 已于 2026-05 成为 GX 开源社区和 GX Core 项目的 steward**。
> 来源：[GX Core 1.x 文档](https://docs.greatexpectations.io/docs/core/introduction/gx_overview)、[Run a Validation Definition](https://docs.greatexpectations.io/docs/core/run_validations/run_a_validation_definition)

**GX Core 1.x 推荐写法**：

```python
import great_expectations as gx
import great_expectations.expectations as gxe

context = gx.get_context()

# 1. Data Source（1.x：context.data_sources，不再是 context.sources）
data_source = context.data_sources.add_postgres(
    name="my_db",
    connection_string="postgresql://user:pass@host/db",
)

# 2. Data Asset + Batch Definition
asset = data_source.add_query_asset(
    name="orders",
    query="SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days'",
)
batch_definition = asset.add_batch_definition_whole_table("orders_batch")

# 3. Expectation Suite
suite = context.suites.add(gx.ExpectationSuite(name="orders_suite"))
suite.add_expectation(gxe.ExpectColumnValuesToNotBeNull(column="order_id"))
suite.add_expectation(gxe.ExpectColumnValuesToBeUnique(column="order_id"))
suite.add_expectation(
    gxe.ExpectColumnValuesToBeBetween(column="amount", min_value=0, max_value=1_000_000)
)
suite.add_expectation(
    gxe.ExpectColumnValuesToBeInSet(column="status", value_set=["pending", "paid", "cancelled"])
)

# 4. Validation Definition + 运行
validation_definition = context.validation_definitions.add(
    gx.ValidationDefinition(
        name="orders_validation",
        data=batch_definition,
        suite=suite,
    )
)
result = validation_definition.run()
print(result.success)
```

## 6. Soda：SQL-first 的替代

相比 GE，Soda 用 YAML + SQL 表达，更轻量：

```yaml
# checks.yml
checks for orders:
  - missing_count(email) = 0
  - duplicate_count(order_id) = 0
  - amount between 0 and 1000000
  - values in status must be in ["pending", "paid", "cancelled"]
  - row_count > 1000
  - freshness(created_at) < 24h
  - failed_rows:
      name: amount consistency
      fail query: |
        SELECT order_id, amount, items_total
        FROM orders
        WHERE amount != items_total
```

```bash
soda scan -d my_db -c configuration.yml checks.yml
```

## 7. Data Contract 规范

> 🔄 更新于 2026-05-30
>
> **重要：datacontract.com 的 Data Contract Specification 已于 ODCS 3.1 发布时宣布 sunset（弃用）**。官方推荐迁移到 **ODCS（Open Data Contract Standard，bitol-io，当前 v3.x）**。Data Contract CLI 和 Entropy Data 会支持旧规范到 2026 年底，之后可用工具自动转换为 ODCS。
> 新项目建议直接采用 ODCS 3.x，下面的 `dataContractSpecification: 1.2.0` 示例仅作迁移期参考。
> 来源：[ODCS 3.1 sunset 公告](https://datacontract-specification.com/)、[ODCS v3 规范](https://bitol-io.github.io/open-data-contract-standard/)

2024-2026 年标准化的 Open Data Contract Standard：

```yaml
# contracts/orders-v1.yaml
# ⚠️ 以下为旧版 Data Contract Specification（已 sunset），新项目请用 ODCS 3.x
dataContractSpecification: 1.2.0
id: orders
info:
  title: Orders Table
  version: 1.0.0
  owner: team-ecommerce
  contact:
    email: ecommerce@company.com

terms:
  usage: |
    Used for BI dashboards and ML feature pipelines.
  limitations: |
    Contains PII (email). Must be masked in non-prod environments.
  billing: N/A
  noticePeriod: P30D  # 变更要提前 30 天通知

servicelevels:
  availability:
    description: Available 99.9% of the time
    percentage: 99.9
  retention:
    period: P7Y         # 保留 7 年
  latency:
    threshold: 1h       # 数据延迟 < 1 小时
  freshness:
    threshold: 1d       # 数据每天更新
  frequency:
    type: batch
    interval: daily
    cron: 0 2 * * *

schema:
  type: dbt            # 用 dbt 模型定义 schema
  specification: |
    version: 2
    models:
      - name: orders
        columns:
          - name: order_id
            data_type: string
            constraints: [primary_key, not_null]
          - name: user_id
            data_type: bigint
            constraints: [not_null]
          - name: amount
            data_type: decimal(18, 2)
            constraints: [not_null]

quality:
  type: SodaCL
  specification: |
    checks for orders:
      - row_count > 1000
      - missing_count(email) = 0
      - freshness(created_at) < 24h
```

## 8. 工具生态

| 工具 | 类型 | 特点 |
|------|------|------|
| **Great Expectations** | 开源 | 最流行、Python 生态 |

- 商业化成熟团队：**Monte Carlo** 或 **Datafold**

## 9. Data Observability：五个维度

Monte Carlo 等工具的核心理念：

```
像软件可观测性一样监控数据：

1. Freshness（新鲜度）
   表多久没更新了？

2. Volume（体积）
   行数突然变化？

3. Schema（Schema 变更）
   新增/删除字段？

4. Distribution（数据分布）
   空值率、基数、均值异常？

5. Lineage（血缘）
   上下游是谁、谁影响谁？
```

## 11. 告警策略

```
分级：
├─ P0（紧急）：核心指标失败，立即告警
│   └─ Slack + PagerDuty
├─ P1（重要）：非核心指标，工作时间告警
│   └─ Slack
└─ P2（一般）：异常趋势，只在 Dashboard 显示
    └─ 定期 Review

避免告警疲劳：
├─ 同一告警合并
├─ 对已知的 flaky 检查降级
├─ 告警有 Runbook
└─ 定期回顾哪些告警实际可操作
```

## 12. 失败处理

```
流程：
1. 检测：数据质量检查失败
2. 分类：
   ├─ 上游问题（源系统异常）→ 上游修
   ├─ Pipeline 问题（代码 bug）→ 回滚
   └─ 业务变化（数据本身变了）→ 更新期望
3. 隔离：标记"不可信"，下游暂时用上一个版本
4. 修复 + 回填
5. 复盘
```

## 13. 组织实践

```
数据质量文化：
├─ 每个数据产品有明确 Owner
├─ 数据契约签署（上游 + 下游）
├─ 定期"Data Quality Review"（每月）
├─ 有 Data SRE / Data Platform 角色
└─ 失败有学习机制（无责 Postmortem）

反模式：
├─ "我只负责 Pipeline 跑通，质量不关我事"
├─ 业务投诉了才开始查
├─ 告警没人看
└─ 数据质量团队和业务脱节
```

## 14. 生产检查清单

```
☐ 核心数据产品有明确 SLA（Freshness、Completeness）
☐ 每张事实表 / 核心维度表有 dbt test
☐ 关键管道有 GE / Soda 检查
☐ 告警分级（P0-P2）+ Runbook
☐ 异常指标监控（Volume / Distribution）
☐ Schema 变更有通知流程
☐ 关键数据产品有 Data Contract
☐ 失败不传染（隔离坏数据）
☐ 数据目录（DataHub / OpenMetadata）中心化
☐ 定期回顾质量趋势
```
