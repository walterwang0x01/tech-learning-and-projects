# 为 Agent 设计 Install

> Author: Walter Wang

> **读完你能回答的 3 个问题**
>
> 1. 一份写得很好的人类向 README，直接甩给 Agent 用会出什么问题？根源是人和 Agent 的什么差异？
> 2. "确定性命令"和"幂等"这两个要求，分别在防什么样的失败？
> 3. AGENTS.md/CLAUDE.md 和"安装文档"应该各自负责什么，为什么不能揉进同一份文件？

> ⚠️ 说明：本文讨论的是"面向 Agent 的安装/环境配置文档该怎么写"这一实践问题，
> 目前没有权威机构给出正式规范。AGENTS.md 这类文件近期在部分 Agent 工具生态中
> 被作为约定俗成的项目级说明文件使用，但具体的字段规范、是否成为跨工具通用标准，
> 仍在演变中，本文不对其未来标准化程度做断言。

## 1. 为什么人类向 README 不适合 Agent

README 写给人看的时候，作者会不自觉地依赖几个"人类特有的容错能力"，这些能力 Agent 都没有：

```
人类读 README 时的隐藏能力              Agent 读同一份 README 时
──────────────────────────────────────────────────────────────
遇到步骤模糊，能靠经验猜出意图           只能严格按字面执行，猜不出"大概是这个意思"
执行报错时，能判断"这个错误是否致命"     报错就是报错,是否继续往往需要明确规则,不能靠直觉
能看截图/GUI 提示确认状态是否正确        大多只能看文本输出，截图和视觉线索基本无效
遇到不确定的地方，能停下来问同事         默认没有人随时待命解答，问不到人就只能猜或卡住
能容忍"大概装上了就行"的模糊验收标准     需要明确的、程序可判定的"成功"信号才能继续下一步
知道"这条命令在 Mac 和 Linux 下不一样"  除非文档写明，否则不会自动补上环境差异的处理
```

这些差异汇总成一句话：**人类读文档是"理解意图后自主补全细节"，Agent 执行文档是"按字面逐条执行，缺什么就卡在哪"。** 因此，面向 Agent 的安装文档，本质要求是**把人类隐式补全的部分,显式地写出来**。

## 2. Agent 友好的安装文档要素

```
□ 确定性命令（Deterministic Commands）
  给出可以直接复制执行的完整命令，不给"大概是这样做"式的描述
  ❌ "安装一下依赖就行"
  ✅ "pip install -r requirements.txt"

□ 前置条件可检测（Detectable Preconditions）
  每个前置条件都配一条能自动判断是否满足的命令，不能只是文字要求
  ❌ "需要 Python 3.11+"
  ✅ "python3 --version  # 要求输出 >= 3.11，否则先安装对应版本"

□ 失败信号明确（Explicit Failure Signals）
  写清楚"这一步失败大概会报什么错、该怎么处理"，而不是假设不会失败
  ❌ 只写成功路径
  ✅ "如果报错 ModuleNotFoundError: xxx，说明虚拟环境未激活，先执行 source .venv/bin/activate"

□ 幂等（Idempotent）
  同一条命令重复执行多次，结果应该一致，不应该因为"已经执行过一次"而报错或产生副作用
  ❌ mkdir output（第二次执行会报"目录已存在"而中断）
  ✅ mkdir -p output（重复执行安全）

□ 无交互等待（Non-Interactive）
  命令不能停在等待人工输入的地方（确认提示、交互式选择菜单）
  ❌ npm init（默认会进入交互式问答）
  ✅ npm init -y
```

这五条里，**幂等**和**无交互**最容易被人类作者忽略，因为人类执行时会自然地按提示回答或者跳过重复步骤，而 Agent 面对交互提示大概率会卡住或做出不可预期的选择。

## 3. 应该写什么，不应该写什么

```
应该写：
├── 完整的、可直接执行的命令序列（不是命令片段+"以此类推"）
├── 每一步之后"如何确认这一步成功了"的判定方法
├── 已知会出错的场景和对应的处理方式（FAQ 式，但是给 Agent 用的）
├── 环境差异的分支处理（操作系统、CPU 架构、是否已有某个全局工具）
└── 明确的"完成"信号——整套流程跑完，用什么命令验证环境已经就绪

不应该写：
├── 需要人工判断"看起来对不对"的步骤（比如"打开浏览器看看页面是否正常"）
│   → 如果必须验证 UI，要换成能程序判断的等价物（健康检查接口、状态码）
├── 依赖外部登录态但没写清楚怎么获取的步骤（比如"用你的账号登录一下"）
│   → 要写清楚 token/密钥从哪来、怎么设置为环境变量
├── 冗长的背景介绍和"为什么这么设计"的说明
│   → 这类内容属于架构文档/ADR，不属于安装文档，混进来会稀释可执行信息的密度
└── "通常应该没问题"这类不构成可执行判断依据的软性描述
```

## 4. 验证步骤的设计：每步后如何自检

安装文档的核心不是"教会怎么装"，是"让 Agent 能自主判断装没装对"。每个关键步骤后面都应该跟一个自检动作：

```bash
# 步骤：安装依赖
pip install -r requirements.txt

# 自检：依赖是否真的装好了（不是靠 pip install 的退出码，
# 因为部分失败场景下退出码仍是 0）
python3 -c "import fastapi, sqlalchemy" && echo "OK: 依赖校验通过" || echo "FAIL: 关键依赖缺失"
```

```bash
# 步骤：启动本地数据库
docker compose up -d db

# 自检：服务是否真正就绪，而不是"容器状态是 running"就当作成功
# （容器 running 不代表数据库已经能接受连接）
for i in $(seq 1 10); do
  pg_isready -h localhost -p 5432 && echo "OK: 数据库已就绪" && break
  sleep 2
done
```

```bash
# 步骤：整体环境就绪检查（放在文档末尾，作为"全部完成"的唯一判定标准）
make check-env
# 期望输出： "ENVIRONMENT READY"
# 若输出包含 "MISSING:"，按提示逐条处理后重新运行本命令
```

设计原则是：**自检命令的输出必须是可以用简单文本匹配判断成功/失败的，不能是需要人工解读的自然语言描述。** "看起来装好了"不是自检结果，`echo "OK"` 或非零退出码才是。

## 5. 环境差异的处理

Agent 执行环境的差异（本地开发机、CI 容器、云端 sandbox）比人类想象的更容易导致文档"在这台机器上失效"。处理方式是显式分支，而不是假设单一环境：

```bash
# 显式检测操作系统，而不是假设都是 Linux
OS_TYPE="$(uname -s)"
case "$OS_TYPE" in
  Darwin)
    brew install postgresql@16
    ;;
  Linux)
    sudo apt-get update && sudo apt-get install -y postgresql-16
    ;;
  *)
    echo "FAIL: 未适配的操作系统 $OS_TYPE，需要人工介入安装 PostgreSQL 16"
    exit 1
    ;;
esac
```

```bash
# 显式检测是否已存在，避免在已配置好的环境里重复执行有副作用的操作
if [ -f ".env" ]; then
  echo "SKIP: .env 已存在，不覆盖"
else
  cp .env.example .env
  echo "OK: 已生成 .env，请检查并填入必要的密钥"
fi
```

第三种未适配情况直接失败退出并说明需要人工介入，比"尝试用一个可能不对的命令硬跑"更安全——**明确失败比静默产生错误状态更容易恢复**。

## 6. 与 AGENTS.md / CLAUDE.md 的分工

这是容易搞混的一点：AGENTS.md/CLAUDE.md（或 Kiro 的 Steering 文件）与"安装文档"目的不同，不应该合并成一份文件。

```
文件类型          回答的问题                  更新频率
────────────────────────────────────────────────────────
安装文档          "怎么把环境装起来，
                   装好了怎么验证"             环境/依赖变化时更新（低频）
AGENTS.md/        "在这个仓库里写代码要
Steering          遵循什么规范和约束"          架构/规范变化时更新（中频）
Spec/任务文档      "当前这个具体任务要
                   做什么、怎么验收"           每个任务都不同（高频）
```

安装文档解决的是"能不能跑起来"（环境层），Steering 解决的是"跑起来之后怎么写代码"（规范层），两者混在一起的坏处是：**每次环境有个小变化（比如换了个依赖版本），都要去改一份同时承载编码规范的大文件，增加了误改规范的风险；也会让 Agent 在读取编码规范时被大段与当前任务无关的安装步骤稀释了注意力。** 保持文件职责单一，各自按自己的更新节奏演进。

## 7. 可直接套用的模板

```markdown
# INSTALL.md（面向 Agent，不是面向人类的完整文档）

## 前置条件检测
- [ ] `python3 --version` 输出 >= 3.11，否则先装对应版本
- [ ] `docker --version` 能正常输出，否则先安装 Docker
- [ ] `.env` 文件存在（若不存在，见下方"生成配置"步骤）

## 安装步骤

### 1. 安装依赖
\`\`\`bash
pip install -r requirements.txt
python3 -c "import fastapi, sqlalchemy" && echo "OK" || echo "FAIL: 依赖缺失"
\`\`\`
若 FAIL：检查 requirements.txt 是否与当前 Python 版本兼容，重新执行安装命令。

### 2. 生成配置
\`\`\`bash
[ -f .env ] || cp .env.example .env
echo "请检查 .env 中的 DATABASE_URL 和 API_KEY 字段是否已填入有效值"
\`\`\`

### 3. 启动依赖服务
\`\`\`bash
docker compose up -d
for i in $(seq 1 10); do pg_isready -h localhost -p 5432 && break; sleep 2; done
\`\`\`

### 4. 环境就绪校验（全部完成的唯一判定标准）
\`\`\`bash
make check-env
# 期望输出包含: ENVIRONMENT READY
\`\`\`

## 已知失败场景
| 报错 | 原因 | 处理 |
|------|------|------|
| `ModuleNotFoundError` | 虚拟环境未激活 | `source .venv/bin/activate` 后重试 |
| `pg_isready` 一直失败 | 端口被占用 | `lsof -i :5432` 排查冲突进程 |
```

## 8. 小结

| 要点 | 内容 |
| --- | --- |
| 根本原因 | Agent 无法像人一样容错、问人、看截图，隐式细节必须显式写出 |
| 五要素 | 确定性命令、前置条件可检测、失败信号明确、幂等、无交互 |
| 该写的 | 完整命令、每步自检方法、已知失败场景、环境分支处理 |
| 不该写的 | 需人工目测判断的步骤、缺少获取方式的登录态要求、背景介绍 |
| 验证设计 | 自检结果必须是可文本匹配的确定性输出，不是自然语言描述 |
| 分工原则 | 安装文档（环境层）与 AGENTS.md/Steering（规范层）职责分离，更新频率不同 |
