# Context Offloading 机制

> Author: Walter Wang

> **读完你能回答的 3 个问题**
>
> 1. Context Offloading 和 Context Compaction（压缩）解决的是同一个问题吗？为什么不能互相替代？
> 2. 一个 Agent 把状态写入了文件，但下一轮任务失败了，可能是卸载机制里的哪一个环节出的问题？
> 3. Kiro 里 Spec 文件、Steering 文件、Todo 列表，分别对应卸载的哪一种形式？

> ⚠️ 说明：Context Offloading 目前不是任何厂商正式定义的技术名词，是社区在讨论
> Agent 长时间运行、上下文管理时逐渐形成的说法（常见于 Claude Code、Manus 等团队的博客和访谈中）。
> 本文中"卸载"的分类方式是作者基于多个 Agent 系统（Claude Code、Kiro、Manus 类架构）的实践归纳，
> 不代表某个厂商的官方术语表。涉及具体产品机制的地方会标注依据。

## 1. 前提：上下文窗口是有限资源

无论模型的上下文窗口做到多大，对一个需要长时间运行、多轮交互的 Agent 来说，它始终是**有限且会被消耗完的资源**，原因不是"不够大"，而是三个更根本的限制：

```
上下文窗口的三重限制
├── 硬限制：Token 数上限，超过就要截断或报错
├── 成本限制：输入 Token 越多，每轮调用越贵，且是线性甚至更差的增长
└── 质量限制：上下文越长，模型对中间信息的注意力越容易变差
              （这不是"容量"问题，是"有效利用率"问题）
```

第三点是最容易被忽视的。即使模型技术上能塞入 20 万 token，也不代表它能均匀地"记住"和"用好"这 20 万 token 里的每一条信息。这就是为什么"上下文管理"不是等窗口做得更大就能解决的问题——它是一个需要工程手段持续应对的常态。

Context Offloading 就是应对这个常态的核心手段之一：**把当前不需要放在模型输入里、但未来可能还需要的信息，转移到外部存储，只在需要时再取回**。

## 2. 为什么要卸载，而不是一直带着

不卸载的 Agent 会呈现一种典型退化模式：

```
任务开始 → 上下文很干净，表现好
   │
   ▼ （执行了 20 步工具调用，历史全部留在上下文里）
中期 → 上下文里塞满了过程性信息（读过的文件全文、
       中间失败的尝试、无关的日志输出）
   │
   ▼
后期 → 关键信息被过程噪音"淹没"，模型开始：
       - 忘记最初的任务目标
       - 重复读取已经读过的文件
       - 对早期做出的决策"失忆"，与自己打架
```

卸载的价值不是省 token（省 token 只是副产品），而是**保持上下文的信噪比**。一个只保留"当前必须知道的东西"的上下文，比一个塞满历史但信息密度低的上下文，能让模型做出更一致、更少矛盾的决策。

这与 [Context Engineering 详解](./02-Context%20Engineering详解.md) 里"上下文质量 > 上下文数量"的原则是同一个道理的延伸：压缩和卸载都是提升信噪比的手段，只是操作对象不同。

## 3. 卸载的四种形式

### 3.1 写入文件系统

最基础也最通用的形式：把中间结果、大段输出、长文档直接写成文件，上下文里只留文件路径和一句摘要。

```
❌ 不卸载：把 grep 出的 200 行匹配结果整段塞进对话历史
✅ 卸载：把结果写入 /tmp/search-results.txt，
        上下文里只留一句"已找到 47 处匹配，存于 search-results.txt"
```

Agent 后续需要细节时，主动用读取工具去查那个文件——这一步就是"取回"（retrieval）。

### 3.2 外部笔记 / 待办列表

Todo 列表本质上是"任务状态"的卸载：把"接下来要做什么、已经做完什么"从模型脆弱的隐式记忆，转移成显式的、结构化的外部记录。

```markdown
<!-- 待办状态卸载到独立结构，而不是靠模型在长对话里"记住" -->
- [x] 读取现有两篇 Harness 笔记，确认不重复
- [x] 读取样板笔记，提取风格要素
- [ ] 撰写 06-Context Offloading机制.md
- [ ] 撰写 07-Agent Version Drifting.md
```

好处很直接：即使模型在第 30 轮"忘了"第 3 轮做过什么，只要它重新读一次这份列表，状态就能对齐。任务进度不再依赖模型的注意力质量。

### 3.3 结构化状态文件

比 Todo 更进一步：把整个任务的关键状态（不只是"做了什么"，还包括"决定了什么、依赖了什么、约束是什么"）写成一份结构化文件，作为任务期间唯一的事实来源（source of truth）。

```json
{
  "task": "重构用户认证模块",
  "decisions": [
    "使用 JWT，不用 Session（已与用户确认）",
    "密码哈希继续用 bcrypt，不引入新依赖"
  ],
  "constraints": [
    "不修改 src/common/ 下的公共类型",
    "保持向后兼容 v1 API"
  ],
  "files_touched": ["src/auth/service.py", "src/auth/routes.py"],
  "status": "implementing"
}
```

这类文件与 Kiro 的 Spec 文件（`requirements.md` / `design.md` / `tasks.md`）是同一思路：把容易在长对话中漂移的"决策"和"约束"锚定在外部文件里，每次读取都是同一份权威版本。

### 3.4 子 Agent 隔离上下文

前三种卸载的是"信息"，这一种卸载的是"上下文空间本身"。让子 Agent（sub-agent）在自己独立的上下文窗口里完成一个子任务，只把**结论**返回给主 Agent，过程中的探索、试错、大量中间输出都留在子 Agent 的上下文里，不污染主线。

```
主 Agent 上下文：
  "调用子 Agent 去分析这个 50 万行的日志文件，找出错误模式"
       │
       ▼（子 Agent 在独立上下文中读日志、试正则、反复调整）
       │  ← 这些过程完全不进入主 Agent 的上下文
       ▼
  子 Agent 返回："发现 3 类错误模式：超时(62%)、连接拒绝(31%)、其他(7%)"
       │
主 Agent 上下文：只多了这一句结论
```

这是四种形式里"卸载力度"最大的，代价是子 Agent 与主 Agent 之间协调、调度的复杂度上升（详见 [Agent 工作流编排模式](../01-Agentic设计模式/03-Agent工作流编排模式.md)）。

## 4. 何时卸载，何时取回

判断标准不是"信息大不大"，而是两个问题：

```
问题1：这条信息在接下来几步里还会被直接用到吗？
  会 → 留在上下文里
  不会，但未来可能需要 → 卸载

问题2：卸载后，取回的触发条件明确吗？
  明确（比如"进入下一阶段前重新读一次 tasks.md"）→ 可以安全卸载
  不明确（"以后可能需要就自己想起来查"）→ 大概率会被遗忘，不要卸载
```

第二点是关键,也是卸载最容易失败的地方——见第 6 节。一个实用的经验规则：**能被明确的检查点（checkpoint）触发重新读取的信息，才适合卸载；只能靠模型"想起来"的，本质上还是留在上下文里更可靠。**

## 5. 卸载 ≠ 压缩：无损外存 vs 有损摘要

这两者经常被混为一谈，但机制完全不同：

| 维度 | Context Compaction（压缩） | Context Offloading（卸载） |
|------|---------------------------|---------------------------|
| 操作方式 | 对历史内容做摘要，替换原文 | 把原文整体移出，只留指针/摘要行 |
| 信息损失 | 有损，摘要必然丢细节 | 无损，原始信息完整保留在外部 |
| 取回方式 | 无法取回原文（已被替换） | 可以按需重新读取完整原文 |
| 典型场景 | 对话历史太长，滑动窗口装不下 | 中间产物太大，暂时不需要但以后可能要 |
| 风险点 | 摘要丢掉了后续关键的细节 | 写了但没人读，或读的时候已经过期 |

两者不是竞争关系,是互补的:**能卸载的优先卸载（不损失信息），卸载不掉的（比如确实只需要"大概记得聊过什么"的陈旧对话历史）再压缩。** 先卸载后压缩，比直接压缩保留的信息质量更高。

## 6. 卸载的三种失败模式

```
失败模式 1：写了不读（Write-Only Offload）
  Agent 把状态写入了文件，但后续步骤压根没有读取的动作
  → 状态卸载等于状态丢失，比不卸载还糟（因为连上下文里的痕迹都没了）

失败模式 2：读不到（Retrieval Miss）
  文件确实写了，但路径记错、文件名拼错、或读取时机不对（太早/太晚）
  → 表现为 Agent "看起来"在遵循流程，但读到的是空的或旧的内容

失败模式 3：状态不同步（State Drift）
  多个 Agent/多轮任务同时读写同一份外部状态文件，没有明确的更新时序
  → 后写入的覆盖了先写入的关键决策，或者两边各自为营,谁也不知道对方改了什么
```

三种失败模式的共同根源是：**卸载机制里"写"和"读"是两个独立的动作，中间没有约束保证它们配对发生。** 解决办法不是让模型更聪明地"记得要读"，而是用机械化的触发点（hook、固定的任务模板步骤）把"读"变成流程的强制环节，而不是模型的自选动作——这与 [Harness Engineering 完整指南](./01-Harness%20Engineering完整指南.md) 里"机械化约束优于依赖模型自觉"的思路一致。

## 7. 在 Kiro / Claude Code 里的具体做法

```
卸载形式          Kiro 对应实现                    取回触发点
─────────────────────────────────────────────────────────────
文件系统          工作区任意临时文件（如 /tmp/*.md） Agent 主动 read 该路径
外部笔记/待办      Spec 的 tasks.md                  每次任务切换前重新读取
结构化状态文件     Spec 的 requirements.md/design.md  #[[file:...]] 引用强制带入上下文
Steering 文件      .kiro/steering/*.md               inclusion: auto 自动带入，
                                                      fileMatch 按文件类型条件带入
子 Agent 隔离      （需外部编排，Kiro 原生不内置多      通过工具调用边界隔离，
                    Agent 子上下文机制）               仅返回值进主上下文
```

> ⚠️ 待确认：Kiro 是否有原生的"子 Agent 隔离上下文"机制（类似 Claude Code 的 subagent），
> 目前没有在官方文档中确认到明确细节，本文不做具体机制描述，仅在概念层面讨论子 Agent 隔离的通用价值。

Steering 文件的 `inclusion` 配置本质上是"卸载—取回"的声明式版本：`auto` 相当于"每轮都自动取回"，`fileMatch` 相当于"满足条件时才取回"，`manual` 相当于"需要显式指令才取回"。这三种策略对应第 4 节里"取回触发条件是否明确"的三个档位——`auto` 最保险但最占上下文，`manual` 最省上下文但最依赖调用者主动触发。

Spec 中的 `#[[file:path]]` 引用语法则是结构化状态文件卸载的取回机制：设计文档、类型定义写在独立文件里（卸载），但通过引用语法保证在写代码任务发起时被强制带入上下文（取回），避免"写了不读"的失败模式。

## 8. 小结

| 要点 | 内容 |
| --- | --- |
| 核心前提 | 上下文窗口永远有限（硬限制+成本限制+质量限制），必须主动管理 |
| 卸载目的 | 提升上下文信噪比，不是单纯省 token |
| 四种形式 | 文件系统、外部笔记/待办、结构化状态文件、子 Agent 隔离 |
| 判断标准 | 接下来会不会直接用到 + 取回触发条件是否明确 |
| 与压缩的区别 | 卸载无损可取回，压缩有损不可逆；优先卸载，卸载不掉再压缩 |
| 三种失败模式 | 写了不读、读不到、状态不同步 |
| 根本解法 | 用机械化触发点（hook/流程模板）强制配对"写"和"读"，不依赖模型自觉 |
