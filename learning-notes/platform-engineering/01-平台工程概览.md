## 1. 为什么出现平台工程

```
┌────── DevOps 的问题 ──────┐
│                            │
│  "You build it, you run it"│
│  每个团队要懂：              │
│  ├─ 容器编排                │
│  ├─ 可观测性                │
│  ├─ CI/CD                  │
│  ├─ 安全合规                │
│  ├─ 云资源管理              │
│  ├─ 成本优化                │
│  └─ 网络策略                │
│                            │
│  结果：                      │
│  ├─ 每个团队重新发明轮子      │
│  ├─ 工具链不一致             │
│  ├─ 认知负担超过业务开发      │
│  └─ 中等规模以上就失控        │
└───────────────────────────┘
```

**平台工程的定位**：把共性的运维复杂度收敛到平台团队，通过 "Internal Developer Platform（IDP）" 暴露自助能力。

## 2. Team Topologies

Team Topologies（2019 年 Matthew Skelton 和 Manuel Pais 的书）定义了四种团队类型：

```
Stream-Aligned Team    按业务流对齐，是主力团队
Platform Team         为 Stream 团队提供自助服务能力
Enabling Team         帮助 Stream 团队快速获得某项能力（短期）
Complicated Subsystem  专门处理复杂子系统（如 ML 平台）

交互模式：
├─ Collaboration     紧密合作
├─ X-as-a-Service    平台团队提供服务
└─ Facilitating      Enabling Team 手把手带
```

**核心洞察**：平台团队的产出是"其他团队的认知负担减少多少"，不是"写了多少 YAML"。

## 3. IDP 的核心能力

```
┌──── Internal Developer Platform ────┐
│                                      │
│  Catalog（资产目录）                   │
│  └─ 所有服务、API、资源、Owner         │
│                                      │
│  Scaffold（脚手架）                    │
│  └─ 新服务一键生成 + 接入标准工具链     │
│                                      │
│  Workflows（自助动作）                 │
│  └─ 部署、扩容、回滚、加域名、申请 DB    │
│                                      │
│  Docs（文档）                          │
│  └─ TechDocs、API 文档、Runbook       │
│                                      │
│  Score（记分卡）                        │
│  └─ 每个服务的健康度、合规、安全评分     │
│                                      │
│  Insights（洞察）                      │
│  └─ 成本、性能、DORA 指标              │
└──────────────────────────────────────┘
```

## 4. Golden Paths（金色路径）

Platform 团队的核心产出是 "Golden Path"：为常见场景提供"阻力最小"的路径。

```
示例 Golden Path：新建一个 Go 微服务

1. 在 Backstage 点"Create Service"
2. 选择 "Go Microservice" 模板
3. 填基本信息（服务名、Owner、Team）
4. 自动生成：
   ├─ GitHub Repo（含 Go 代码骨架）
   ├─ CI pipeline（GitHub Actions）
   ├─ Dockerfile（多阶段构建 + distroless）
   ├─ Helm Chart / Kustomize
   ├─ Argo CD Application
   ├─ OpenTelemetry 接入
   ├─ Prometheus ServiceMonitor
   ├─ Grafana Dashboard
   └─ PagerDuty 服务
5. 开发者只要写业务代码
```

**核心原则**：Golden Path 应该比偏离路径更容易走。如果"自助平台"比直接点 AWS 控制台更难用，就没人会用。

## 5. DORA 指标

DORA（DevOps Research and Assessment）的四个关键指标，是平台工程成效的标尺：

```
Deployment Frequency  部署频率
Lead Time for Changes 代码提交到上线的时间
Change Failure Rate   变更失败率
Mean Time to Recover  平均恢复时间

Elite 级别：
├─ 每天多次部署
├─ 小时级 Lead Time
├─ 变更失败率 < 15%
└─ MTTR < 1 小时

平台工程的目标：把团队整体水平拉到 High / Elite
```

## 6. 平台团队的度量

```
平台工程自身的指标：
├─ 采用率：多少业务服务走 Golden Path
├─ NPS：内部开发者满意度
├─ 平台可用性：自身 SLO
├─ 时间节省：Stream 团队省下多少运维时间
├─ 标准化程度：服务符合平台规范的比例
└─ 成本：平台总成本 / Stream 团队数量

反面：
├─ 不应该把平台团队当"运维工单处理台"
└─ 平台团队的首要产出是"Self-service 能力"，不是"帮别人执行命令"
```

## 8. 实施阶段

```
阶段 1：让一个团队爽（3-6 个月）
├─ 选一个 Pilot 团队
├─ 解决他们最痛的 3 件事
└─ 形成可复制模板

阶段 2：推广 + 平台化（6-12 个月）
├─ 搭 Portal（Backstage 或商业产品）
├─ 1-2 个 Golden Path 成熟
└─ 建立 DORA 指标基线

阶段 3：规模化（12+ 个月）
├─ 大多数服务走 Golden Path
├─ 平台自身的 SLO 体系
├─ FinOps、安全治理成体系
└─ 开始 "平台即产品" 运营
```

## 9. 反模式

```
❌ 平台工程 = "把运维工作重命名"
   → 没区别，还是工单驱动

❌ 闭门造车
   → 没业务团队用，平台失败

❌ 追求技术完美，忽视采用
   → Product 思维比 Tech 思维更重要

❌ 把 K8s 原生 YAML 直接扔给业务
   → 认知负担没下降，只是转移

❌ 平台本身是黑盒
   → 业务团队调试时绝望
   → 平台能力要可观测、可调试

❌ 没 SLO / SLA
   → 平台挂了全公司停工
```

## 10. 与 AI Agent 的关系

```
AI Agent 时代平台工程的新任务：
├─ AGENTS.md 标准文件
├─ Golden Path for AI：新 Agent 开发的脚手架
├─ Agent Runtime：Langfuse / LangSmith Fleet 集中观测
├─ AI 开发工具链：Cursor / Kiro / Claude Code 统一接入
├─ Agent 安全治理：权限、审计、成本
└─ AI-Ready Data：数据 + Embedding 的 Self-service
```

平台团队要把"AI 开发"也做成 Golden Path，否则每个业务团队都会在 Agent 这件事上重新踩坑。
