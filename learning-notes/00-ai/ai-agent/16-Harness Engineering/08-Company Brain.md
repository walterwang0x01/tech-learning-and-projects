# Company Brain

> Author: Walter Wang

> **读完你能回答的 3 个问题**
>
> 1. "Company Brain" 和一个普通的企业内部 RAG 知识库，本质区别是什么？
> 2. 为什么"事实层"的知识可以直接检索给 Agent 用，"决策层"和"组织层"的知识却不能这么简单处理？
> 3. 一份三年前的技术方案文档，混进了 Agent 的知识来源，可能造成什么后果？该怎么防？

> ⚠️ 说明："Company Brain"（或 "Org Brain"）是行业里对"让 Agent 能用上组织知识"这一类
> 系统的松散统称，散见于部分 Agent 基础设施厂商的产品叙事和技术博客，**不是学术界或标准组织
> 定义的正式术语**，不同公司对这个词的所指范围也不完全一致。本文的三层结构划分是作者基于
> 组织知识管理（Knowledge Management）领域已有的分层思路（事实/流程/文化）结合 Agent 场景的
> 归纳整理，不代表某个产品的官方架构。

## 1. 概念：组织知识如何变成 Agent 可用的上下文

一个 Agent 要在真实组织里干活（不是玩具任务），它缺的往往不是模型能力，而是**组织特有的、不在公开语料里、也不在当前对话里的知识**。比如：

```
Agent 不知道，但组织里的人"自然就知道"的东西：
├── "这个服务为什么要保留一个看起来多余的重试逻辑"（三个月前的一次事故复盘结论）
├── "这类需求默认走 A 方案不走 B 方案"（团队达成过的技术决策，没写进任何代码注释）
├── "涉及这个客户的改动一定要让某个角色审一遍"（组织流程和权限惯例）
└── "上一次有人这么改，导致了什么后果"（沉淀在事故记录/复盘文档里，而不在代码里）
```

Company Brain 想解决的就是：**把这类分散在代码仓、文档、会议记录、聊天记录、事故复盘里的组织知识，转成 Agent 在执行任务时能够可靠取用的上下文。**

## 2. 与普通 RAG 知识库的区别

如果只是"把文档扔进向量库，问的时候检索几条相关的塞进提示词"，这就是标准 RAG，和 Company Brain 不是一回事。核心区别在于**信息的结构化程度和可信程度分级**，而不只是检索这个动作本身。

```
维度              普通 RAG 知识库              Company Brain
──────────────────────────────────────────────────────────────
信息单位          文档片段（chunk）             结构化的事实/决策/规范条目
是否分层          通常不分层，混在一个索引里     按可信度和时效性分层（见第3节）
时效性处理        很少主动处理，旧文档照样命中    主动标记失效/过期，冲突时有优先级
决策可追溯性       不涉及，只返回文本片段          决策条目关联"谁定的、什么时候、
                                                为什么"，而不只是"结论是什么"
权限/角色         通常全局统一权限                按角色/项目隔离可见范围（见第5节）
消费方式          人工阅读检索结果后自行判断      Agent 直接把结论当作执行依据，
                                                因此对准确性和时效性要求更高
```

最本质的一句话：**普通 RAG 回答的是"文档里写了什么"，Company Brain 要回答的是"组织现在认为什么是对的、该怎么做"——后者需要处理冲突、过期和权威性问题，前者不需要。**

## 3. 三层结构：事实层 / 决策层 / 组织层

```
┌─────────────────────────────────────────────────┐
│  组织层（Organizational Layer）                   │
│  "谁能改这个、改了要通知谁、这类任务归哪个团队"      │
│  来源：组织架构、审批流程、权限系统                 │
├─────────────────────────────────────────────────┤
│  决策层（Decision Layer）                         │
│  "我们为什么选了 A 不选 B，这个决定现在还有效吗"     │
│  来源：ADR、设计评审记录、事故复盘结论              │
├─────────────────────────────────────────────────┤
│  事实层（Factual Layer）                          │
│  "这个函数是干什么的，这个服务依赖哪些下游"          │
│  来源：代码仓、API 文档、系统架构图                 │
└─────────────────────────────────────────────────┘
```

三层对 Agent 的可用性差异很大：

- **事实层**相对静态、客观，可以直接用标准检索方式给 Agent，出错代价较低（顶多检索不准，重新查一次）。
- **决策层**天然带有时间属性和"是否仍然有效"的问题——一个决策可能后来被推翻了，如果 Agent 检索到旧决策当作现在的依据去执行，代价是做出错误的技术选择。
- **组织层**涉及权限和流程，用错的代价往往不是"知识错了"，而是"越权做了不该做的事"（比如 Agent 没意识到某类改动需要审批，直接执行了）。

这也是为什么 Company Brain 不能只是"一个更大的向量库"——**层级越高，对准确性、时效性、权限的要求越严格，纯检索式的做法风险越大。**

## 4. 从各类来源提取组织知识的路径

```
来源            提取到的知识层级        提取方式的特点
────────────────────────────────────────────────────────
代码仓           事实层（主）           结构相对规整，可用代码知识图谱类工具
                                       （比如从仓库结构、依赖关系提取）
文档/Wiki        事实层 + 决策层        需要区分"现行规范"和"历史存档"，
                                       文档系统本身很少显式标记这个区别
会议记录/纪要     决策层（主）           信息密度低，大量闲聊夹杂少量决策，
                                       提取前必须先做"决策点抽取"这一步
事故复盘          决策层（高价值）       通常有相对固定的结构
                                       （现象/根因/修复/后续行动项），
                                       结构化程度天然较高，适合优先提取
```

一个容易被忽视的点：**这四类来源的"知识密度"差异巨大**。一份结构清晰的事故复盘文档，可能比一百条会议聊天记录提供的可执行组织知识更多。提取路径的优先级应该反过来——先啃信息密度高、结构相对固定的来源（事故复盘、ADR），再处理信息密度低、需要大量清洗的来源（会议闲聊记录）。

## 5. 时效性与知识过期的处理

组织知识天然会过期，而且过期不会主动通知任何人。处理这个问题的核心是**让每条知识都带上"有效期判断所需的元信息"，而不是假设检索到的就是当前有效的**。

```json
{
  "id": "decision-2026-03-auth-jwt",
  "layer": "decision",
  "content": "认证模块统一使用 JWT，不使用 Session",
  "decided_at": "2026-03-12",
  "decided_by": "架构评审会",
  "status": "active",
  "superseded_by": null,
  "review_due": "2026-09-12"
}
```

关键字段是 `status` 和 `superseded_by`——当一个新决策推翻旧决策时，旧条目应该被显式标记为失效并指向新条目，而不是留着让检索系统凭"语义相似度"随机命中新旧两个互相矛盾的结论。`review_due` 则是给容易过期的决策设置一个"到期需要人工确认是否仍然有效"的提醒点，而不是让它无限期地被当作现行有效的知识使用。

没有这套元信息，Company Brain 最大的风险就是**用一个三年前的、早已被推翻的决定，去指导 Agent 现在的行动，而且 Agent 和用户都不知道这条知识已经过期**——这比"没有这个知识库"更危险，因为它带来的是自信而错误的判断。

## 6. 权限与隔离

组织知识不是对所有角色都应该等价可见的：

```
按角色隔离的典型例子：
├── 财务/薪酬相关决策 → 仅对应角色的 Agent 可检索
├── 未公开的产品路线图 → 仅内部特定项目组可见，不能被通用助理 Agent 检索到
├── 客户敏感信息相关的技术方案 → 按客户/项目隔离，不能跨客户串用
└── 安全事故复盘中的具体漏洞细节 → 权限收紧，避免被更广范围的 Agent 引用后无意中扩散
```

实现上，这要求 Company Brain 的检索层不能是"一个全局索引，靠 Prompt 提醒 Agent 不要用不该用的内容"——这种做法约等于没有隔离，因为检索本身已经把内容取出来了，再靠模型自觉不使用是不可靠的。**权限判断必须发生在检索这一步之前（谁能查到什么），而不是发生在生成这一步之后（查到了但让模型别用）。**

## 7. 落地难点与价值评估

```
落地难点：
├── 提取成本高：会议记录、聊天记录里的"决策点"密度低，
│              人工标注成本高，自动提取的准确率是持续要解决的问题
├── 维护成本持续存在：知识不是建好就完事，过期判断、冲突处理需要持续运营
├── 权限体系复杂度：多角色、多项目的隔离规则本身就是一套需要维护的系统
└── 信任问题：一旦 Agent 引用过一次过期或错误的组织知识，
              用户对整个系统的信任会大幅下降，且难以恢复

价值评估的角度（不给具体数字，因为高度依赖组织规模和知识密度）：
├── 减少了多少"Agent 因为不知道组织惯例而做出需要人工纠正的决定"
├── 减少了多少"同样的问题被不同的人/Agent 重复排查一遍"
└── 组织知识的沉淀和可检索性，本身对新人/新 Agent 的上手成本也有价值
  （这部分价值即使 Agent 用不上，对人类协作也是正向的）
```

落地难点的共同结论是：**Company Brain 不是一次性建设项目，是持续运营的系统**，这和它经常被拿来对比的"建一个知识库"的心智模型是不一样的——知识库可以静态维护，Company Brain 的时效性和权限要求决定了它必须有持续的运营投入。

## 8. 小结

| 要点 | 内容 |
| --- | --- |
| 核心定位 | 把分散的组织知识转成 Agent 可信赖使用的上下文，而不只是可检索的文本 |
| 与 RAG 的区别 | 分层可信度、显式处理时效性冲突、按角色隔离权限，而不只是相似度检索 |
| 三层结构 | 事实层（客观静态）/ 决策层（有时效性）/ 组织层（涉及权限流程） |
| 提取优先级 | 结构固定、信息密度高的来源（事故复盘、ADR）优先于闲聊类记录 |
| 时效性处理 | 每条知识带 status/supersede 元信息，不能假设检索到的就是当前有效 |
| 权限设计 | 隔离必须发生在检索之前，不能靠提示词提醒模型"别用不该用的" |
| 落地本质 | 持续运营的系统，不是一次性知识库建设项目 |
