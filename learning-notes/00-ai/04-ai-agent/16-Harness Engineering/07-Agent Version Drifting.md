# Agent Version Drifting

> Author: Walter Wang

> **读完你能回答的 3 个问题**
>
> 1. 一套 Harness 半年前跑得很好，什么都没改，为什么现在 Agent 表现变差了？漂移可能发生在哪一层？
> 2. 只看"任务最终是否成功"这一个指标，为什么不足以发现版本漂移？
> 3. 想让 Harness 尽量不受模型版本更迭影响，应该往提示词和工具设计里加什么，去掉什么？

> ⚠️ 说明："Version Drifting" 不是某个厂商定义的标准术语，是本文借用软件工程里
> "配置漂移"（configuration drift）概念，套用到 Agent Harness 场景的类比说法，
> 属于作者的归纳整理。文中涉及具体模型行为差异的地方，均未引用具体版本号或未公开的
> 官方数据，请以你实际使用的模型版本为准自行验证。

## 1. 什么是版本漂移

版本漂移指的是：**Harness 本身的配置文件（提示词、Steering、工具定义）一行没改，但因为它所依赖的外部组件悄悄升级了版本，导致 Agent 的实际表现发生了变化**——通常是变差,但也可能是行为方式改变导致原有的适配失效。

漂移可以发生在四个独立的层：

```
Harness 依赖的四类可漂移版本
├── 模型版本漂移
│   同一个模型名/接口下，厂商替换了底层权重（灰度更新、静默升级）
│   或用户主动升级到新一代模型
├── 提示词版本漂移
│   Steering/CLAUDE.md 被多人协作修改，逐渐偏离最初设计意图
│   没有版本控制，无法追溯"什么时候、为什么改的"
├── 工具 Schema 版本漂移
│   MCP Server / Function Calling 的工具定义升级了参数名、返回结构
│   但调用方的提示词里还在用旧的字段名做示例
└── 依赖库版本漂移
    Agent 生成的代码依赖的第三方库升级了 API
    Agent 的训练知识/示例代码仍停留在旧版本用法
```

四类漂移的共同特点：**触发变化的动作发生在 Harness 外部，Harness 的维护者往往没有主动做任何事，却要承受结果。** 这也是它比普通的"提示词写错了"更难排查的原因——排查者的第一反应往往是"我们最近没改任何东西",而忽略了外部依赖已经变了。

## 2. 为什么同一套 Harness 会随模型换代退化

一套针对特定模型调优过的 Harness，本质上包含了大量对该模型行为特征的隐式假设，比如：

```
隐式假设的例子（不特指某个真实模型，仅作说明）：
├── "这个模型偏保守，需要在提示词里反复强调'主动去做，不要只是提建议'"
│    → 换成一个本身就更主动的模型后，这句强调可能导致过度激进的行为
├── "这个模型工具调用参数经常漏填,所以在描述里加大量示例"
│    → 换成一个工具调用更稳定的模型后，冗余示例反而占用上下文、拖慢速度
├── "这个模型倾向一次只调一个工具,所以流程设计成严格串行"
│    → 换成支持更好并行工具调用的模型后，串行设计变成了性能瓶颈
```

这些假设在写 Harness 时往往是无意识的——工程师是在"调到这个模型能用"的过程中，把针对该模型的补丁一点点嵌入了提示词和流程设计里。[LangChain 的 Harness Profile 实践](./01-Harness%20Engineering完整指南.md#8-langchain-harness-profile按模型定制-harness) 已经证明：同一套任务，换一个模型家族，最优的提示词结构、工具命名、甚至要不要保留某个中间件都会不同。反过来说，**给模型 A 调优的 Harness，天然带着"模型 A 特有的补丁"，这些补丁在模型 B 上可能是无效甚至有害的。**

这不是模型变差了，而是**旧的补丁和新的模型特性打架**——版本漂移的本质是"耦合度"问题，会在第 6 节展开。

## 3. 漂移的可观测信号

版本漂移最危险的地方是：任务"最终是否成功"这个粗粒度指标，往往很久才会明显下降,因为 Agent 可能靠更多轮重试、更长时间勉强达到同样的最终结果。要提前发现,需要看更细粒度的过程信号：

```
信号 1：工具调用成功率
  → 参数格式错误率上升、需要重试的调用比例上升
    往往是工具 schema 或模型的调用习惯变了

信号 2：轮数分布（完成同类任务所需的步骤数）
  → 同一类任务，历史上平均 5 轮完成，现在变成 9 轮
    说明模型需要更多试错才能达到同样效果，效率在退化

信号 3：输出格式遵守率
  → 要求输出 JSON/特定结构，实际输出偶尔夹带解释性文字或格式偏差的比例上升
    模型对格式指令的服从度可能随版本变化

信号 4：首次通过率（不经过修复循环，第一次尝试就通过验证的比例）
  → 这是最敏感的信号，参见 Context Engineering 详解中提到的同一指标
```

这四个信号都需要**基线（baseline）**才有意义——漂移是相对量，不是绝对量。这就引出下一节。

## 4. 固定数据集回归的必要性

没有回归测试集，版本漂移只能靠"感觉最近好像变差了"这种主观印象发现，而主观印象往往滞后且不可量化。

```
Harness 回归测试集的最小构成：
├── 20-50 个代表性任务（覆盖 Harness 实际服务的主要任务类型）
├── 每个任务的验收标准（自动可判定，不依赖人工目测）
├── 记录基线：当前 Harness + 当前模型版本下的通过率、平均轮数、平均耗时
└── 触发时机：
    ├── 每次修改 Steering/提示词后
    ├── 每次升级模型版本前后（先在旧模型上跑一遍留档，再在新模型上跑对比）
    └── 定期（比如每月）跑一次，捕捉厂商静默升级带来的漂移
```

```bash
# 示意：回归测试的最小可行流程（伪代码化的 shell 骨架）
# 1. 跑固定任务集，产出结构化结果
kiro-cli batch-run --tasks ./regression-tasks.yaml --output ./results/$(date +%Y%m%d).json

# 2. 与上一个基线对比关键指标
diff <(jq '.pass_rate, .avg_turns, .format_compliance' ./results/baseline.json) \
     <(jq '.pass_rate, .avg_turns, .format_compliance' ./results/$(date +%Y%m%d).json)
```

```yaml
# regression-tasks.yaml 的示意结构
tasks:
  - id: task-001
    prompt: "在 src/user/ 下新增一个字段校验函数"
    acceptance:
      - "生成的函数必须有类型注解"
      - "pytest tests/test_validation.py 通过"
  - id: task-002
    prompt: "修复 test_orders.py 中失败的测试"
    acceptance:
      - "修复后 pytest -x 全部通过"
      - "diff 中不包含对 test_orders.py 断言逻辑本身的修改"
```

没有这套东西，任何"升级模型后 Agent 变笨了"的讨论都停留在轶事（anecdote）层面，无法定位是提示词的问题还是模型的问题，也无法验证修复是否真的有效。

## 5. 版本固定与回滚策略

对于模型版本漂移，最直接的工程对策是把"能否升级"这个决策从被动变成主动：

```
策略 A：固定版本 + 主动升级
  在能显式指定模型版本号的场景下，锚定到具体版本，
  不自动跟随"最新"，升级前先在回归集上跑一遍再手动切换

策略 B：影子跑（shadow run）
  新旧版本并行跑同一批任务一段时间，对比信号后再切流量

策略 C：可回滚的配置分离
  Harness 里"依赖模型特性的补丁"和"通用的任务约束"分开存放，
  回滚时只需要切换补丁部分,不用整体回退

策略 D（无法固定版本时的兜底）：
  部分平台只暴露"始终指向最新"的接口别名，无法锚定具体版本。
  这种情况下把第 4 节的回归测试集从"升级前"改为"高频定期"运行，
  把发现漂移的延迟降到可接受范围，是唯一可行的兜底手段。
```

> ⚠️ 待确认：不同厂商、不同接入方式（API 直连 / 通过 IDE 内置 / 通过第三方网关）
> 对"是否能锚定具体模型版本"的支持程度不同，请以你实际使用的接入方式的文档为准。

## 6. 提示词与模型的耦合度问题

回到第 2 节的根因——提示词里那些"针对某个模型缺陷写的补丁"，本质上是把 Harness 和一个具体的模型版本**紧耦合**了。耦合度越高，换模型时的漂移就越剧烈。

```
高耦合的提示词写法（危险信号）：
  "记得每次都要仔细检查工具参数,不要漏填"
  "输出前请再三确认格式正确,严格按照下面的 JSON 结构，不要有任何偏差"
  "不要过度谨慎,遇到明确的任务直接执行,不要反复确认"

  → 这些话本质是"哄"某个已知有特定倾向的模型，而不是描述任务本身
```

```
低耦合的提示词写法（更稳健）：
  用工具的类型系统/schema 强制参数格式，而不是靠自然语言提醒"别漏填"
  用结构化输出能力（如强制 JSON mode）而不是靠反复叮嘱"请遵守格式"
  用明确的任务边界和终止条件描述职责，而不是描述"性格调节"式的行为倾向
```

一个实用的自查方法：**读一遍提示词，标出所有"提醒/叮嘱/强调不要"类的句子。这些句子大概率是针对某个模型具体缺陷打的补丁，是耦合度的来源。能用机械化约束（schema、hook、结构化格式）替代的，都应该替代掉。** 这与 [Harness Engineering 完整指南](./01-Harness%20Engineering完整指南.md) 里"机械化约束优于人工/语言提醒"的原则完全一致——对抗版本漂移和对抗模型犯错，用的是同一套工程手段。

## 7. 如何设计对模型版本不敏感的 Harness

综合前几节，几条可执行的设计原则：

```
□ 任务约束用工具 schema/类型系统表达，不用自然语言反复强调
□ 验证环节机械化（CI/lint/测试），不依赖"模型自己说做完了"
□ 提示词中标注哪些段落是"通用任务描述"，哪些是"模型特定补丁"
  （补丁段落集中存放，方便升级模型时定位和清理）
□ 维护固定回归数据集，任何模型/提示词变更都先过一遍再上线
□ 关键指标（工具成功率/轮数/格式遵守率）持续监控，不只看最终任务成功率
□ 升级模型前先在小范围/影子环境验证，不做无监控的直接切换
```

## 8. 小结

| 要点 | 内容 |
| --- | --- |
| 版本漂移的四层 | 模型版本、提示词版本、工具 Schema 版本、依赖库版本 |
| 退化的根因 | Harness 里隐藏了针对旧模型特性的补丁，新模型下补丁失效或起反作用 |
| 关键信号 | 工具调用成功率、轮数分布、格式遵守率，比"最终成功率"更早暴露问题 |
| 必需基础设施 | 固定回归数据集 + 基线记录，否则漂移只能靠主观印象发现 |
| 版本策略 | 能固定版本就固定 + 主动升级；不能固定就提高监控频率兜底 |
| 根本对策 | 降低提示词与模型的耦合度，用机械化约束替代"提醒式"补丁 |
