# 从 for 循环到自治系统

> Author: Walter Wang

> **读完你能回答的 3 个问题**
>
> 1. 从"固定 for 循环"升级到"带终止条件的 while"，本质上多了什么能力？这个能力的代价是什么？
> 2. 为什么"终止条件设计"是自治系统里最核心的问题，而不是"模型能力"？
> 3. 遇到什么样的任务特征时，应该主动选择不上自治循环，而是保留人工在环（human-in-the-loop）？

> ⚠️ 说明：本文的"七级演进"是作者为了讲清楚自治程度递增的脉络而做的归纳分类，
> 不是行业标准分级。ReAct 是有论文依据的公开概念（Reasoning + Acting 交替的
> Agent 循环范式），其余分级名称（固定 for 循环、带反馈信号的自修正循环等）是
> 描述性说法，不是特定框架的专有名词。

## 1. 演进路径总览

```
自治程度递增 ──────────────────────────────────────────────►

单次调用 → 固定for循环 → 带终止条件的while → ReAct循环
  │            │               │                │
  无自治        伪自治           有限自治          初步自治
                                                    │
                                                    ▼
              自主规划 ← 多Agent编排 ← 带反馈信号的自修正循环
                 │            │              │
              高自治        协作自治        反思自治
```

每往右走一级，Agent 获得的自主处理能力更强，但换来的代价（成本、可预测性、调试难度）也随之上升。这条路径的核心不是"越靠右越好"，而是**任务的不确定性和反馈信号的可得性决定了该停在哪一级**——这是全文要论证的核心结论。

## 2. 单次调用（Single Call）

```
输入 → 模型 → 输出，结束
```

没有循环，模型看一次输入产出一次输出。能力上限完全取决于任务能否在一次生成里完成。多数简单的文本生成、分类、改写任务停在这一级就足够——**不需要循环的地方硬上循环，只会增加不必要的延迟和不确定性。**

## 3. 固定 for 循环

```
for i in range(N):
    output = model(input, previous_outputs)
```

典型场景：批量处理一组已知数量的条目（比如"给这 20 个文件各写一段摘要"）。这一级的"自治"是伪自治——循环次数是硬编码的，模型对"要跑几次"完全没有决策权，循环体本身也不判断是否应该提前结束。

多付的代价：几乎没有额外代价，因为行为完全确定,可预测性和调试难度都不会上升。这一级的局限是**无法处理"不知道要跑几次才能完成"的任务**——而这是大多数真实 Agent 任务的常态。

## 4. 带终止条件的 while

```
while not is_done(state):
    state = model(input, state)
    if exceeded_max_iterations(state):
        break  # 兜底退出，防止真的死循环
```

这一级新增的能力是：**循环次数不再固定，由任务状态动态决定"是否已经完成"。** 这是从伪自治走向真自治的第一步——终止不再是外部预先写死的数字，而是运行时判断出来的。

代价开始显现：
```
成本：单次任务消耗的调用次数从确定变为不确定，预算难以精确预估
可预测性：同样的输入，因为中间状态判断的细微差异，可能跑 3 轮也可能跑 8 轮
调试难度：出问题时，"为什么这次跑了 8 轮"需要回放每一轮的状态判断,不再是简单的日志对比
```

`is_done` 的判断逻辑设计得好不好，直接决定了这一级是否可靠——这也是下一节要展开的核心问题的雏形。

## 5. ReAct 循环

```
┌─────────────────────────────────────────┐
│  Reasoning（推理）→ 决定下一步做什么       │
│         │                                │
│         ▼                                │
│  Acting（行动）→ 调用工具/执行动作         │
│         │                                │
│         ▼                                │
│  Observation（观察）→ 拿到工具执行结果     │
│         │                                │
│         └──────► 回到 Reasoning，直到判断任务完成
└─────────────────────────────────────────┘
```

相比上一级"带终止条件的 while"，ReAct 的关键新增能力是：**循环体内部有了显式的"推理-行动-观察"结构，模型能根据每一步的实际观察结果调整下一步策略，而不是执行一个预先规划好的固定动作序列。** 这就是现在绝大多数 Agent 框架（工具调用循环）的基础范式。

多付的代价：
```
成本：每一轮推理本身也要消耗 token，轮数越多单任务成本越高
可预测性：模型可能在某一步选择了一个"合理但不是你预期"的工具调用路径
调试难度：需要能看到每一轮的推理内容（不只是最终动作），
        否则出错时无法判断是"推理错了"还是"工具本身返回错了"
```

## 6. 带反馈信号的自修正循环

```
ReAct 循环基础上，加入外部验证环节：

  Acting → Observation → 【外部验证：测试/lint/类型检查】
                                │
                    ┌───────────┴───────────┐
                    ▼                       ▼
                 验证通过                 验证失败
                    │                       │
                  结束                 把失败信息作为新的
                                       Observation 喂回循环
```

这一级的核心新增能力：**验证环节不再依赖模型自己"觉得做完了"，而是接入外部的、机械化的判定（测试是否通过、lint 是否报错、类型检查是否通过）。** 这是 [Harness Engineering 完整指南](./01-Harness%20Engineering完整指南.md) 中"自主循环"一节描述的核心模式——Agent 写代码、CI 反馈、自动修复,循环往复直到通过或超出重试上限。

多付的代价在前几级基础上更进一步：
```
成本：一次任务可能触发多次完整的验证流程（测试套件本身也有运行成本）
可预测性：不同任务失败后需要的修复轮数差异很大,难以给出统一的 SLA
调试难度：需要分辨"这次失败是任务本身太难"还是"验证信号本身有噪音/不稳定"
        （比如 flaky test 导致的假失败,会让自修正循环白白浪费轮次）
```

## 7. 多 Agent 编排

```
单个 Agent 循环 → 拆解为多个专职 Agent 协作：

  Orchestrator（编排者）
       │
       ├──► Agent A（负责调研/信息收集）
       ├──► Agent B（负责代码实现）
       └──► Agent C（负责验证/审查）
       │
       └──► 汇总各 Agent 结果,决定下一步
```

新增能力：**把单个循环里"一个模型要同时兼顾多种角色（调研、写、审）"的负担拆开，每个子 Agent 只专注一种职责，上下文更干净（这与 [Context Offloading 机制](./06-Context%20Offloading机制.md) 中"子 Agent 隔离上下文"是同一机制）。**

多付的代价：
```
成本：多个 Agent 并行/串行运行，总 token 消耗明显高于单 Agent 循环
可预测性：编排逻辑本身也可能出错（比如 Orchestrator 误判了某个子任务已完成）
调试难度：问题定位要跨多个 Agent 的执行记录，"哪个环节出的错"本身就是排查成本
```

## 8. 自主规划

```
不再有预先定义好的任务分解结构，Agent 自己决定：
├── 要不要拆解任务
├── 拆成几个子任务、分别交给谁（自己做/调子Agent/调工具）
└── 中途根据执行结果重新调整整体计划
```

这是自治程度的顶点：**任务分解和执行策略本身也是 Agent 决策的对象，不再由人预先设计流程。** 代价也在这一级达到最大——成本最不可控（复杂任务可能规划出远超预期的执行路径）、可预测性最低（同样的输入两次运行可能走完全不同的路径）、调试难度最高（连"应该按什么流程排查"这个问题本身都没有固定答案）。

## 9. 终止条件设计是核心问题

七级演进走下来，会发现一个规律：**从第 4 级开始，"什么时候算完成"这件事就不再是外部写死的，而是需要设计出来的判断逻辑——这个判断逻辑的质量，直接决定了整个自治系统是可靠还是失控。**

```
终止条件设计的三个失败方向：

1. 太宽松 → 提前退出，任务实际没做完
   例：is_done() 只检查"模型说完成了"，不做任何外部验证

2. 太严格/不可满足 → 永远判断不通过，陷入无意义的重试
   例：验收标准里混入了模型能力范围之外的要求，
       无论重试多少次都不可能满足

3. 判断信号本身不稳定 → 同样的结果，判断结果时对时错
   例：依赖 flaky 的测试或依赖外部服务的临时性故障作为判断依据
```

好的终止条件应该同时具备：**可判定（不依赖主观解读）、可达成（在任务能力范围内确实存在能满足的结果）、信号稳定（相同输入应给出相同判断）**。这三者缺一，自治循环的行为就会退化成"看起来在运转，实际在空转或者提前放水"。

## 10. 反馈信号从哪来

自修正循环（第 6 级起）依赖外部反馈信号驱动，信号的来源决定了循环的可靠性上限：

```
信号来源           可靠性        适用场景
──────────────────────────────────────────────
自动化测试          高            有明确预期输出的功能性任务
类型检查/lint       高            代码规范性、类型安全
静态分析/架构测试    高            结构性约束（如分层依赖规则）
人工确认            最高但最慢     涉及主观判断、高风险决策
无反馈信号          — 不适用自治   任务本身没有客观对错标准
```

排在最后一行是关键：**当一个任务连"怎么算对"都说不清楚时,不是去设计更复杂的循环让模型"多想想"，而是应该承认这类任务本身不具备自治的前提条件**——这直接引出下一节。

## 11. 何时不应该上自治

```
不适合上自治循环的信号：
├── 低频任务
│   一年做一次的事,花时间搭建自修正循环的投入产出比不成立，
│   直接人工做或用最简单的单次调用即可
│
├── 高风险操作
│   资金转账、生产环境删除、权限变更等不可逆操作，
│   即使反馈信号完备，"循环里出一次错就无法撤销"的风险
│   决定了这类操作应该保留人工确认关卡,不能纯自治
│
└── 反馈信号缺失
    没有客观、稳定、可判定的完成标准时,
    自治循环没有东西可以收敛，会陷入第9节说的"空转或放水"
```

这三类信号可以叠加判断：一个任务越低频、风险越高、反馈信号越模糊，就越应该往演进路径的左边退，而不是不断加码更复杂的编排结构去"硬啃"。**自治程度应该匹配任务特征，不是越高越先进。**

## 12. 循环中的失控模式与熔断设计

```
失控模式 1：无限重试
  验证一直不通过，循环没有上限地跑下去
  → 熔断：设置 max_iterations 硬上限，超过后停止并升级给人处理

失控模式 2：抖动（同一个错误反复"修复"又重新引入）
  修复 A 问题时引入了 B 问题，修复 B 问题时又引入回 A 问题
  → 熔断：检测状态是否在几个固定状态间循环（哈希最近 N 轮的关键状态对比），
         检测到抖动立即停止,不再继续"自修复"

失控模式 3：目标漂移
  多轮修复后，Agent 逐渐偏离了最初的任务目标（比如为了让测试通过
  改了测试断言本身，而不是修复被测代码）
  → 熔断：关键验收条件（比如"不允许修改测试文件"）做成硬约束，
         而不是靠模型自觉遵守

失控模式 4：级联放大（多 Agent 编排场景）
  一个子 Agent 的错误判断被传给下一个子 Agent 当作前提,
  错误沿着编排链条被放大而不是被纠正
  → 熔断：关键节点之间插入独立的验证环节，不能假设"上一个 Agent 说的就是对的"
```

熔断设计的共同原则：**循环的"停止"权力不能完全交给循环内部的判断逻辑，必须有一个外部的、独立的硬上限或独立校验点。** 这与终止条件设计（第 9 节）是互补关系——终止条件解决"正常情况下什么时候算完成"，熔断解决"异常情况下怎么保证不会无限失控"。

## 13. 小结

| 演进级别 | 新增能力 | 主要代价 |
| --- | --- | --- |
| 单次调用 | — | — |
| 固定 for 循环 | 处理已知数量的重复任务 | 几乎无额外代价 |
| 带终止条件的 while | 循环次数动态决定 | 成本/轮数不再可精确预估 |
| ReAct 循环 | 按观察结果动态调整下一步 | 推理本身也消耗成本，路径不完全可控 |
| 带反馈信号的自修正循环 | 接入机械化外部验证 | 信号质量（如 flaky test）直接影响可靠性 |
| 多 Agent 编排 | 职责拆分、上下文更干净 | 总成本上升，跨 Agent 排查成本上升 |
| 自主规划 | 任务分解本身也交给 Agent | 可预测性和调试难度都到达最高点 |

| 核心问题 | 结论 |
| --- | --- |
| 自治的核心设计难点 | 终止条件：可判定、可达成、信号稳定，三者缺一就会空转或放水 |
| 何时不该上自治 | 低频任务、高风险不可逆操作、缺乏客观反馈信号 |
| 失控的通用解法 | 熔断权力必须在循环外部，不能完全依赖循环内部的自我判断 |
