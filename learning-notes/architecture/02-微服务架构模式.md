## 1. 概述

微服务架构将单体应用拆分为一组小型、自治的服务，每个服务围绕业务能力构建，独立部署、独立扩展。

```
┌──────────── 单体 vs 微服务 ────────────┐
│                                         │
│  单体架构：                              │
│  ┌─────────────────────────────┐        │
│  │  用户模块 │ 订单模块 │ 支付模块 │        │
│  │  库存模块 │ 通知模块 │ 报表模块 │        │
│  │         共享数据库            │        │
│  └─────────────────────────────┘        │
│  一个进程，一个部署单元                    │
│                                         │
│  微服务架构：                             │
│  ┌──────┐ ┌──────┐ ┌──────┐            │
│  │用户   │ │订单   │ │支付   │            │
│  │服务   │ │服务   │ │服务   │            │
│  │ DB1  │ │ DB2  │ │ DB3  │            │
│  └──────┘ └──────┘ └──────┘            │
│  独立进程，独立数据库，独立部署             │
└─────────────────────────────────────────┘
```

### 2.3 断路器模式（Circuit Breaker）

```python
import time
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"        # 正常，请求通过
    OPEN = "open"            # 熔断，请求直接失败
    HALF_OPEN = "half_open"  # 半开，放行少量请求试探

class CircuitBreaker:
    """断路器：防止级联故障"""

    def __init__(self, failure_threshold=5, recovery_timeout=30):
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.last_failure_time = 0

    def call(self, func, *args, **kwargs):
        if self.state == CircuitState.OPEN:
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = CircuitState.HALF_OPEN
            else:
                raise CircuitOpenError("断路器已打开，请求被拒绝")

        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise

    def _on_success(self):
        self.failure_count = 0
        self.state = CircuitState.CLOSED

    def _on_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = CircuitState.OPEN

# 使用
breaker = CircuitBreaker(failure_threshold=5, recovery_timeout=30)
try:
    result = breaker.call(requests.get, "http://order-service/api/orders")
except CircuitOpenError:
    result = fallback_response()  # 降级响应
```

## 3. 数据管理模式

```

┌──────┐  ┌──────┐  ┌──────┐
│用户   │  │订单   │  │支付   │
│服务   │  │服务   │  │服务   │
└──┬───┘  └──┬───┘  └──┬───┘
   │         │         │
┌──┴───┐  ┌──┴───┐  ┌──┴───┐
│MySQL │  │Postgres│ │MongoDB│
│用户表 │  │订单表  │  │交易表 │
└──────┘  └──────┘  └──────┘

优点：独立演进，技术异构
缺点：跨服务查询困难，分布式事务复杂
```

### 3.2 跨服务数据查询方案

```
方案对比：
├─ API 组合（API Composition）
│   Gateway 调用多个服务，聚合结果
│   简单，但性能差（多次网络调用）
│
├─ CQRS（命令查询分离）
│   写走各自服务，读走统一查询视图
│   详见 → 04-CQRS与事件溯源.md
│
└─ 事件驱动数据同步
    服务发布事件，下游服务维护本地副本
    最终一致，但延迟可接受
```

## 4. 服务间通信

| 方式 | 协议 | 特点 | 适用场景 |
|------|------|------|----------|
| REST | HTTP/JSON | 简单通用，生态好 | CRUD 接口、对外 API |
| gRPC | HTTP/2 + Protobuf | 高性能，强类型 | 内部服务间高频调用 |
| 消息队列 | Kafka/RabbitMQ | 异步解耦 | 事件通知、任务分发 |
| GraphQL | HTTP/JSON | 灵活查询，减少过度获取 | BFF（Backend for Frontend） |

```python
# gRPC 服务定义示例
# order.proto
"""
syntax = "proto3";

service OrderService {
    rpc CreateOrder (CreateOrderRequest) returns (OrderResponse);
    rpc GetOrder (GetOrderRequest) returns (OrderResponse);
    rpc ListOrders (ListOrdersRequest) returns (stream OrderResponse);
}

message CreateOrderRequest {
    string user_id = 1;
    repeated OrderItem items = 2;
}
"""

# Python gRPC 服务端
import grpc
from concurrent import futures

class OrderServicer(order_pb2_grpc.OrderServiceServicer):
    def CreateOrder(self, request, context):
        order = create_order(request.user_id, request.items)
        return order_pb2.OrderResponse(
            order_id=order.id,
            status="created",
        )

server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
order_pb2_grpc.add_OrderServiceServicer_to_server(OrderServicer(), server)
server.add_insecure_port("[::]:50051")
server.start()
```

## 7. 微服务拆分原则

```
什么时候拆：
├─ 团队超过 10 人，协作成本高
├─ 部署频率不同（订单日更，用户月更）
├─ 扩展需求不同（搜索要 10 实例，用户要 2 个）
└─ 技术栈需求不同（ML 用 Python，交易用 Java）

怎么拆：
├─ 按业务能力（用户、订单、支付、库存）
├─ 按 DDD 限界上下文（Bounded Context）
├─ 单一职责：一个服务只做一件事
└─ 数据自治：服务拥有自己的数据

不要拆的信号：
├─ 团队小于 5 人
├─ 业务逻辑简单
├─ 频繁跨服务事务
└─ 没有独立部署需求
```

根据 CNCF 年度调查（2024）：传统 Sidecar 模式采用率从 2023 年的 50% 降至 2024 年的 42%。Ambient/eBPF 路线正在吸引增量用户。

### 10.4 对新项目的建议

- **默认 Ambient Mode**：除非有特殊的 L7 策略需求，否则不要选 Sidecar
- **AI 流量单独规划**：把 LLM/Embedding 等推理流量放到 Inference Gateway 后面，避免和业务流量互相影响
- **Gateway API 优先**：弃用传统 Ingress 配置，Gateway API 已成为 K8s 流量入口的事实标准

## 11. 2026-05 更新：DDD + 微服务边界的再思考

> 🔄 更新于 2026-05-10

<!-- version-check: Domain-oriented microservices, DDD 2026, checked 2026-05-10 -->

### 11.1 "领域导向"为什么又热起来

2026 年围绕微服务的主流讨论从"要不要拆"转向"按什么拆"。Domain-Oriented Microservice Architecture（DOMA）强调：**把业务领域边界当作服务边界的第一原则，而不是团队边界或技术边界。** 实践反馈是：Code Review 更短、On-call 告警更少、发布频率更快。来源：[Domain-Oriented Microservice Architecture: A Practical Guide for 2026](https://thelinuxcode.com/domain-oriented-microservice-architecture-a-practical-guide-for-2026/)（内容已重写以符合许可）

### 11.2 DDD 和 AI Coding Agent 的新关系

`exploreddd.com` 等社区提出一个新视角：**良好设计的服务边界本身就是 AI Coding Agent 的防护栏。** 当 Agent 修改的代码被限制在一个限界上下文内时，改动的副作用可预测；跨上下文的改动则需要显式经过领域事件或 API，Agent 不会误伤远端模块。

```
┌────── 服务边界对 AI Agent 的双重作用 ──────┐
│                                             │
│  对人类：                                     │
│  ├─ 明确团队所有权                            │
│  └─ 降低认知负担                              │
│                                             │
│  对 AI Agent：                                │
│  ├─ 作为"沙箱"，限制修改的影响半径             │
│  ├─ 限界上下文的公共 API 即"Agent 可用工具"    │
│  └─ 领域事件天然为 Agent 提供可观测信号         │
└─────────────────────────────────────────────┘
```

来源：[Explore DDD: Designing Microservices](http://exploreddd.com/workshops/designing-microservices.html)（内容已重写以符合许可）

### 11.3 实用清单：DDD 驱动微服务拆分

1. **先做事件风暴（Event Storming）** — 用便签或白板把业务事件、命令、聚合画清楚，再决定服务边界
2. **按限界上下文拆分** — 不要按"模块""团队""表"去拆；同一个上下文内的聚合不跨服务
3. **为 Agent 预留标准入口** — 每个服务暴露清晰的 API + 领域事件主题，把 Coding Agent 当作"新同事"对待
4. **服务间只靠领域事件** — 严禁跨限界上下文直接访问数据库；必要时通过防腐层（Anti-Corruption Layer）翻译
5. **把"战略设计文档"作为 Context** — DDD 的 Context Map、Ubiquitous Language 作为 Agent 的 steering 文件，显著提高生成代码的对齐度

### 11.4 什么时候不该用 DDD + 微服务

```
明显不合适的场景：
├─ 业务复杂度低（简单 CRUD、内部工具）
├─ 团队 < 5 人，跨服务协调成本大于收益
├─ 领域模型尚未稳定，每天都在重构
└─ 对延迟极敏感且调用链路固定（单体或模块化单体更合适）
```

对这些场景，"模块化单体 + 清晰边界"往往比"多个小服务"更快也更可靠。
