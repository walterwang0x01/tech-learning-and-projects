## 1. 概述

事件驱动架构（Event-Driven Architecture, EDA）通过事件实现服务间的解耦和异步通信。核心思想：服务之间不直接调用，而是通过发布/订阅事件来协作。

```
┌──────────── 事件驱动 vs 请求驱动 ────────────┐
│                                                │
│  请求驱动（同步）：                             │
│  订单服务 ──HTTP──→ 库存服务 ──HTTP──→ 支付服务 │
│  （强耦合，链式调用，一个挂全挂）                │
│                                                │
│  事件驱动（异步）：                             │
│  订单服务 ──→ [订单已创建] ──→ Event Broker     │
│                                  │    │    │   │
│                              库存服务 支付 通知  │
│  （松耦合，各自独立消费，互不影响）              │
└────────────────────────────────────────────────┘
```

## 2. 核心概念

```
事件驱动四要素：
├─ Event（事件）：已发生的不可变事实，如"订单已创建"
├─ Producer（生产者）：发布事件，不关心谁消费
├─ Consumer（消费者）：订阅事件，做出响应
└─ Broker（消息中间件）：事件的传输和存储
```

### 事件的三种类型

```
┌─────────── 事件类型 ───────────┐
│                                 │
│  1. 通知事件（Notification）     │
│     只告诉你"发生了什么"         │
│     { "type": "order.created",  │
│       "orderId": "123" }        │
│     消费者需要回查获取详情        │
│                                 │
│  2. 状态转移事件（State Transfer）│
│     携带完整数据                  │
│     { "type": "order.created",  │
│       "order": { 全部字段 } }    │
│     消费者无需回查                │
│                                 │
│  3. 领域事件（Domain Event）     │
│     DDD 中的业务事件             │
│     { "type": "OrderPlaced",    │
│       "aggregateId": "123",     │
│       "items": [...] }          │
│     绑定聚合根，有业务语义        │
└─────────────────────────────────┘
```

## 3. 两大架构模式

### 3.1 发布-订阅模式（Pub/Sub）

```
Producer ──→ Topic ──→ Consumer A
                  ├──→ Consumer B
                  └──→ Consumer C

特点：
├─ 一对多广播
├─ 消费者独立消费，互不影响
├─ 适合通知、日志、监控
└─ 消息消费后可能丢失（取决于实现）
```

```python
# Kafka 发布-订阅示例
from confluent_kafka import Producer, Consumer

# --- 生产者 ---
producer = Producer({"bootstrap.servers": "localhost:9092"})

def publish_order_event(order: dict):
    """发布订单事件"""
    event = {
        "type": "order.created",
        "timestamp": datetime.utcnow().isoformat(),
        "data": order,
    }
    producer.produce(
        topic="order-events",
        key=order["order_id"],      # 同一订单的事件发到同一分区，保证顺序
        value=json.dumps(event),
    )
    producer.flush()

# --- 消费者 ---
consumer = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "inventory-service",    # 消费者组
    "auto.offset.reset": "earliest",
})
consumer.subscribe(["order-events"])

while True:
    msg = consumer.poll(1.0)
    if msg is None:
        continue
    event = json.loads(msg.value())
    if event["type"] == "order.created":
        deduct_inventory(event["data"]["items"])
```

### 3.2 事件流模式（Event Streaming）

```
Event Stream（不可变日志）：
┌───┬───┬───┬───┬───┬───┬───┐
│ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ ← offset
└───┴───┴───┴───┴───┴───┴───┘
  ↑               ↑           ↑
Consumer A    Consumer B    最新写入

特点：
├─ 事件持久化，可重放
├─ 多个消费者各自维护消费位置（offset）
├─ 适合事件溯源、数据管道、实时分析
└─ Kafka 是典型实现
```

## 4. 消息中间件对比

| 维度 | Kafka | RabbitMQ | Redis Streams | Pulsar |
|------|-------|----------|---------------|--------|
| 模型 | 分布式日志 | 消息队列 | 内存流 | 分布式日志 |
| 吞吐量 | 百万/秒 | 万级/秒 | 十万/秒 | 百万/秒 |
| 消息持久化 | 磁盘，可配置保留 | 可选持久化 | 内存+AOF | 分层存储 |
| 消息顺序 | 分区内有序 | 队列内有序 | Stream 内有序 | 分区内有序 |
| 消费模式 | Pull | Push/Pull | Pull | Push/Pull |
| 消息回溯 | ✅ 按 offset 回放 | ❌ 消费即删 | ✅ 按 ID 回放 | ✅ 按 offset 回放 |
| 延迟 | 毫秒级 | 微秒级 | 微秒级 | 毫秒级 |
| 适用场景 | 大数据管道、事件溯源 | 任务队列、RPC | 轻量实时、缓存旁路 | 多租户、跨地域 |
| 运维复杂度 | 中（KRaft 模式） | 中 | 低 | 高 |

```
选型建议：
├─ 高吞吐 + 事件回溯 → Kafka
├─ 低延迟 + 灵活路由 → RabbitMQ
├─ 已有 Redis + 轻量需求 → Redis Streams
├─ 多租户 + 跨地域 → Pulsar
└─ 不确定？ → Kafka（生态最大，社区最活跃）
```

## 5. 关键设计模式

### 5.1 幂等消费

消息可能重复投递，消费者必须保证幂等。

```python
class IdempotentConsumer:
    """幂等消费者：同一事件只处理一次"""

    def __init__(self, redis_client):
        self.redis = redis_client

    def process(self, event: dict):
        event_id = event["event_id"]

        # 检查是否已处理（用 Redis SET NX 原子操作）
        if not self.redis.set(f"processed:{event_id}", "1", nx=True, ex=86400):
            return  # 已处理过，跳过

        try:
            self._handle(event)
        except Exception:
            self.redis.delete(f"processed:{event_id}")  # 处理失败，允许重试
            raise

    def _handle(self, event: dict):
        """实际业务处理"""
        if event["type"] == "order.created":
            deduct_inventory(event["data"])
```

### 5.2 死信队列（DLQ）

处理失败的消息进入死信队列，避免阻塞正常消费。

```
正常流程：
Topic ──→ Consumer ──→ 处理成功 ✅

失败流程：
Topic ──→ Consumer ──→ 重试 3 次 ──→ 仍失败 ──→ Dead Letter Queue
                                                      │
                                                  人工排查 / 告警
```

### 5.3 Saga 模式（分布式事务）

跨服务的事务通过事件编排，每步失败触发补偿操作。

```
┌─────────── Saga：订单流程 ───────────┐
│                                       │
│  正常流程：                            │
│  创建订单 → 扣减库存 → 扣款 → 完成    │
│                                       │
│  补偿流程（扣款失败）：                 │
│  创建订单 → 扣减库存 → 扣款失败 ✗      │
│                 ↓                     │
│            恢复库存 → 取消订单          │
│                                       │
│  两种实现：                            │
│  ├─ 编排式（Choreography）             │
│  │   服务间通过事件自协调               │
│  │   简单，但流程分散难追踪             │
│  └─ 协调式（Orchestration）            │
│      中心协调器控制流程                 │
│      清晰，但协调器是单点               │
└───────────────────────────────────────┘
```

```python
# 协调式 Saga 示例
class OrderSaga:
    """订单 Saga 协调器"""

    def __init__(self, event_bus):
        self.event_bus = event_bus
        self.steps = [
            SagaStep("create_order", self.create_order, self.cancel_order),
            SagaStep("reserve_stock", self.reserve_stock, self.release_stock),
            SagaStep("process_payment", self.process_payment, self.refund_payment),
        ]

    async def execute(self, order_data: dict):
        completed = []
        for step in self.steps:
            try:
                await step.action(order_data)
                completed.append(step)
            except Exception as e:
                # 失败：逆序执行补偿
                for s in reversed(completed):
                    await s.compensate(order_data)
                raise SagaFailed(f"{step.name} 失败: {e}")

        await self.event_bus.publish("order.completed", order_data)
```

### 5.4 Outbox 模式

解决"数据库写入 + 事件发布"的原子性问题。

```
问题：
  1. 写数据库 ✅
  2. 发事件 ✗（网络故障）
  → 数据不一致

Outbox 解决方案：
  1. 在同一个数据库事务中：
     ├─ 写业务表
     └─ 写 outbox 表（待发送事件）
  2. 独立进程轮询 outbox 表，发送事件到 Broker
  3. 发送成功后标记已处理

┌─────────────────────────────────┐
│  数据库事务（原子）               │
│  ├─ INSERT INTO orders (...)    │
│  └─ INSERT INTO outbox (...)    │
└──────────────┬──────────────────┘
               │
    ┌──────────┴──────────┐
    │ Outbox Poller（轮询）│
    └──────────┬──────────┘
               │
         Event Broker
```

## 7. 常见陷阱

```
事件驱动的坑：
├─ 事件顺序：跨分区无法保证全局顺序
│   → 用 partition key 保证同一实体的事件有序
├─ 消息丢失：生产者发送失败 / Broker 宕机
│   → 开启 acks=all + 副本同步
├─ 消息重复：网络抖动导致重复投递
│   → 消费者必须幂等
├─ 事件风暴：一个事件触发大量下游事件
│   → 限流 + 背压（backpressure）
├─ 调试困难：异步链路难以追踪
│   → 全链路 Trace ID + 集中日志
└─ 最终一致性：数据不是立即一致的
    → 业务上接受延迟，UI 上给用户预期
```

## 10. 2026 年 EDA + AI Agent 新范式

> 🔄 更新于 2026-05-07

### 10.1 Agentic EDA 的三层架构

2026 年事件驱动架构的主流叙事已经从"微服务解耦"演进为"AI Agent 实时决策基础设施"。RisingWave 等厂商将其总结为三层模型：

```
┌──────────── Agentic EDA 三层架构 ────────────┐
│                                               │
│  应用层（Applications & Agents）                │
│  ├─ LLM Agent 订阅事件流，实时做决策            │
│  └─ 传统应用通过标准数据库接口查询"活状态"        │
│                                               │
│  流处理层（Streaming Compute）                  │
│  ├─ RisingWave / Flink 实时计算派生状态         │
│  ├─ 物化视图：连续更新的查询结果                 │
│  └─ 把"事件流"转化为"可查询的实时状态"           │
│                                               │
│  事件总线层（Durable Event Broker）             │
│  ├─ Kafka 4.x / Redpanda                     │
│  ├─ 领域事件作为 source of truth                │
│  └─ 支持事件回溯、审计和多消费者                 │
└───────────────────────────────────────────────┘
```

来源：[RisingWave: Event-Driven Architecture in 2026](https://risingwave.com/blog/event-driven-architecture-2026/)（内容已重写以符合许可）

### 10.2 AI Agent 作为 Kafka 消费者的关键差异

传统服务消费 Kafka 与 LLM Agent 消费 Kafka 有本质差异：

| 维度 | 传统服务消费 | LLM Agent 消费 |
|------|------------|---------------|
| 处理延迟 | 毫秒级，可预测 | 秒级，受模型推理影响 |
| 失败模式 | 明确的异常码 | 语义错误、幻觉、超时混合 |
| 幂等性 | 基于 event_id 去重 | 需要结合语义判重（相似消息也可能重复） |
| 回压策略 | 消费者组 rebalance | Agent 推理成本高，需要限流 + 队列缓冲 |
| 可观测性 | Metrics + Logs | 需要增加 LLM Trace、Token 消耗追踪 |

来源：[When Your AI Agent Consumes from Kafka](https://tianpan.co/blog/2026-04-16-agents-event-driven-architecture-message-queues)

### 10.3 Confluent 提出的四种 Agentic EDA 模式

```
模式 1：Orchestrator Agent（中心协调）
  一个 Agent 监听所有事件并编排下游动作
  适合：端到端业务流程

模式 2：Reactive Agent Pipeline（反应式链路）
  多个 Agent 按顺序消费上游 Agent 的输出事件
  适合：内容生成流水线（摘要→翻译→发布）

模式 3：Competing Agents（竞争消费）
  同一 topic 多个 Agent 消费组，每组独立处理
  适合：A/B 测试不同模型或策略

模式 4：Event-Sourced Agent Memory（事件溯源记忆）
  Agent 的所有决策作为事件存储，可重放复现
  适合：审计、调试、持续学习
```

来源：[Confluent: Four Design Patterns for Event-Driven Multi-Agent Systems](https://www.confluent.io/blog/event-driven-multi-agent-systems/)

### 10.4 实践建议

- **新项目**：优先采用 Kafka 4.x（KRaft 模式）+ 流处理引擎（RisingWave 或 Flink）
- **引入 Agent**：先以"只读订阅者"身份接入现有 Kafka，再逐步让 Agent 发布事件
- **可观测性**：在 Trace 中增加 Agent 推理耗时、Token 消耗、模型版本字段
- **成本控制**：Agent 推理昂贵，消费者组必须配合限流和降级策略

## 11. 2026-05 更新：Pulsar Oxia 与 Kafka 4 的正面对决

> 🔄 更新于 2026-05-10

<!-- version-check: Kafka 4.x KRaft, Pulsar Oxia, RisingWave, checked 2026-05-10 -->

### 11.1 Pulsar 也告别 ZooKeeper

2026 年事件总线生态的一个关键变化是：Pulsar 引入 **Oxia** 作为新一代元数据层，目标和 Kafka 的 KRaft 一致 — 让分布式日志不再依赖独立的协调集群。这意味着 Kafka 和 Pulsar 的运维复杂度在同一起跑线上，选型重点回到"架构契合度"本身。来源：[Pulsar vs Kafka 2026](https://sanj.dev/post/pulsar-vs-kafka-deep-dive/)（内容已重写以符合许可）

### 11.2 Kafka / Pulsar / Redpanda 快速对比（2026 版）

| 维度 | Kafka 4.x (KRaft) | Pulsar (+ Oxia) | Redpanda |
|------|-------------------|-----------------|----------|
| 元数据层 | KRaft（内置 Raft） | Oxia（新） | 无单独元数据层 |
| 分层存储 | 原生支持（KIP-405） | 原生支持 | 原生支持 |
| 队列语义 | Share Groups（KIP-932） | 原生支持（独享订阅） | 依赖 Kafka 协议 |
| 多租户 | 通过 ACL + Quota | 原生多租户模型 | 企业版 |
| 协议兼容 | Kafka 原生 | 支持 Kafka + MQTT + AMQP | Kafka 原生 |
| 典型场景 | 生态最成熟、通用 | 多租户/多协议 SaaS | 单集群低延迟、无 JVM |

> 选型建议：绝大多数新项目仍然优先 Kafka 4.x；Pulsar 适合多租户 + 多协议的 SaaS；Redpanda 适合对延迟极敏感、希望"单二进制"运维的团队。

### 11.3 AI Agent 时代的新对手：流数据库

在 Kafka/Pulsar 之上，流数据库（Streaming Database）正成为 AI Agent 读取"实时状态"的首选接口：

```
传统链路：
  Producer → Kafka → Consumer → DB → App 查询

AI Agent 链路：
  Producer → Kafka → RisingWave/Flink → 物化视图 → Agent 按标准 SQL 查询
```

RisingWave、Flink SQL、Materialize 等系统把流上的连续查询具化为"持续更新的表"，Agent 不再自己消费 Kafka，而是把流当作数据库用。这一层是 EDA 从"微服务异步解耦"迈向"Agent 实时决策平面"的关键。来源：[Event-Driven Architecture Complete Guide 2026](https://risingwave.com/blog/event-driven-architecture-complete-guide/)（内容已重写以符合许可）

### 11.4 给现有项目的迁移建议

- **仍在 Kafka + ZooKeeper**：优先制定 KRaft 迁移计划，4.x 后再也不支持回退 ZK
- **纯 Kafka 消费者**：把"Agent 要看的派生状态"抽到 RisingWave / Flink 的物化视图中，减少 Agent 重复计算
- **Pulsar 用户**：关注 Oxia 的 GA 时间线，评估从 ZooKeeper 迁移到 Oxia 的窗口
- **新项目**：Kafka 4.x + Schema Registry + 流数据库 是 2026 年的"默认起手式"

### 12.1 Apache Kafka 4.3 发布要点（2026-05-22）

Kafka 4.3 在 4.2 之后三个月发布，包含 25 个 KIP 与 600+ 提交。对架构设计影响最大的几项：

| 改动 | 含义 |
| ---- | ---- |
| **Broker Cordoning** | 把指定 broker 标记为"不接收新分区"，方便滚动升级和退役，无需手工 reassignment |
| **Partition Size Metrics** | 第一次原生暴露每个分区的字节大小指标，容量规划不再靠估算 |
| **Share Group 调优配置** | KIP-1240 增加 share group 级别配置（max records, lock timeout 等），队列语义可在生产环境精细调控 |
| **Tiered Storage 改进** | 多项远端段拷贝、复制、清理优化，让分层存储真正适合 PB 级流 |
| **Classic Protocol 弃用推进** | 进一步推动 KRaft + Group Coordinator V2 成为唯一路径 |

来源：[Apache Kafka 4.3.0 Release Announcement](https://kafka.apache.org/blog/2026/05/22/apache-kafka-4.3.0-release-announcement/)、[Factor House - Apache Kafka 4.3.0 Guide](https://factorhouse.io/de/articles/apache-kafka-4-3-0)（内容已重写以符合许可）

### 12.2 Share Groups（KIP-932）：Kafka 终于有了"队列语义"

KIP-932 在 4.2 转为 production-ready，4.3 进一步补齐工具链。核心区别：

```
传统 Consumer Group（Stream 语义）：
  Topic Partition 0 ──> Consumer A（独占）
  Topic Partition 1 ──> Consumer B（独占）
  └─ 分区数 = 并发上限，rebalance 抖动大

Share Group（Queue 语义）：
  Topic Partition 0 ──> Consumer A / B / C 协作消费
  └─ 单分区可被多个消费者拉取，类似 RabbitMQ 队列
  └─ 支持 ACKNOWLEDGE / RELEASE / REJECT / RENEW
```

Share Group 的意义在于：**Kafka 不再需要把"队列场景"让给 RabbitMQ / SQS**。同一份数据，业务可以根据场景在 Stream 和 Queue 两种语义间切换，运维栈大幅简化。来源：[Factor House - KIP-932 Queues for Kafka Explained](https://factorhouse.io/articles/kip-932-queues-for-kafka-explained)（内容已重写以符合许可）

### 12.3 "无盘 Kafka"：架构方向的下一步

InfoQ 在 2026-05 发表的架构观察文章把 Kafka 演进路径概括为「Tiered → Diskless」：

```
┌──── Kafka 架构演进路径 ────┐
│                             │
│  本地盘 only (经典)            │
│         ↓                    │
│  Tiered Storage (KIP-405)    │
│  本地热数据 + S3/HDFS 冷数据   │
│         ↓                    │
│  Diskless Cloud-Native       │
│  Broker 几乎无本地状态         │
│  弹性 + Per-API FinOps 计费    │
└─────────────────────────────┘
```

业界实践（Confluent KORA、AutoMQ、WarpStream 等）表明：把所有持久化下沉到对象存储后，broker 变成无状态计算层，可以按消费速率秒级伸缩。**架构师层面的影响**：选型不再只是"Kafka vs Pulsar"，还要看部署形态（自管 broker、托管 broker、对象存储原生）。来源：[InfoQ - Architecting Cloud-Native Kafka](https://www.infoq.com/articles/architecting-cloud-native-kafka/)（内容已重写以符合许可）

### 12.4 EventStoreDB 改名 KurrentDB

事件溯源（Event Sourcing）社区里最常用的 EventStoreDB 在 2026 年正式改名为 **KurrentDB**，公司从 Event Store Ltd. 重组为 Kurrent Inc.，仓库迁移到 [github.com/kurrent-io/KurrentDB](https://github.com/kurrent-io/KurrentDB)。版本号采用日期化方案（如 26.1.0、26.2.0 STS），TCP API 在 23.10 后已废弃，gRPC 客户端是唯一路径。来源：[Kurrent Releases](https://www.kurrent.io/releases)、[Release Schedule](https://docs.kurrent.io/server/latest/release-schedule/)（内容已重写以符合许可）

### 12.5 给现有项目的迁移建议（更新版）

- **Kafka 4.x 用户**：开始评估 Share Groups，把"明显是队列语义"的场景（任务派发、外部回调）迁过来，可以用半年节奏退役 RabbitMQ
- **新项目选型**：优先评估"托管 + Diskless"形态，自管 broker 仅在合规或延迟极敏感场景
- **EventStore 用户**：把镜像和包名从 `eventstore/eventstore` 切换到 `kurrentplatform/kurrentdb`，TCP API 已废弃，确保客户端用 gRPC
- **可观测性**：把 4.3 新增的 partition size、share group lag 指标纳入容量看板，避免依赖估算
