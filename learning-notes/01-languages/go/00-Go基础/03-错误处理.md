# Go 错误处理

> Author: Walter Wang

## 1. Go 的错误哲学

```
Go 不用 exception，原因：
├─ 异常控制流不清晰（哪一行会抛？）
├─ 容易被误用（catch-all 吞掉重要错误）
├─ 性能开销
└─ 跨 goroutine 传播复杂

Go 的选择：错误是值
├─ 显式处理
├─ 可以比较、传递、包装
├─ 符合"代码即文档"
└─ 结合 defer 做资源清理
```

## 2. 经典模式

```go
func loadUser(id int) (*User, error) {
    row := db.QueryRow("SELECT * FROM users WHERE id = ?", id)
    var u User
    if err := row.Scan(&u.ID, &u.Name); err != nil {
        return nil, fmt.Errorf("load user %d: %w", id, err)
    }
    return &u, nil
}

// 调用方
user, err := loadUser(1)
if err != nil {
    return fmt.Errorf("get current user: %w", err)
}
```

**`%w` 是关键**：包装错误保留原始信息，后面能用 `errors.Is` / `errors.As` 解构。

## 3. 自定义错误类型

### 3.1 哨兵错误（Sentinel Errors）

```go
var (
    ErrNotFound   = errors.New("not found")
    ErrUnauthorized = errors.New("unauthorized")
    ErrInvalidInput = errors.New("invalid input")
)

func (r *UserRepo) Find(id int) (*User, error) {
    // ...
    return nil, ErrNotFound
}

// 调用方判断
if errors.Is(err, ErrNotFound) {
    return c.JSON(404, gin.H{"error": "user not found"})
}
```

### 3.2 结构化错误

```go
type NotFoundError struct {
    Resource string
    ID       string
}

func (e *NotFoundError) Error() string {
    return fmt.Sprintf("%s with id %s not found", e.Resource, e.ID)
}

// 调用方用 errors.As 提取
var nfErr *NotFoundError
if errors.As(err, &nfErr) {
    log.Printf("resource=%s id=%s", nfErr.Resource, nfErr.ID)
}
```

### 3.3 带 HTTP 状态码的错误

```go
type APIError struct {
    Code    int
    Message string
    Cause   error  // 原因错误
}

func (e *APIError) Error() string {
    return e.Message
}

func (e *APIError) Unwrap() error {
    return e.Cause
}

// 工厂函数
func NotFound(msg string) *APIError {
    return &APIError{Code: 404, Message: msg}
}

func Internal(cause error) *APIError {
    return &APIError{Code: 500, Message: "internal error", Cause: cause}
}

// 统一错误处理中间件
func ErrorHandler(c *gin.Context) {
    c.Next()
    if len(c.Errors) == 0 { return }

    err := c.Errors.Last().Err
    var apiErr *APIError
    if errors.As(err, &apiErr) {
        c.JSON(apiErr.Code, gin.H{"error": apiErr.Message})
        return
    }
    c.JSON(500, gin.H{"error": "internal error"})
}
```

## 4. errors.Is vs errors.As

```go
// errors.Is：判断是否是某个具体错误（哨兵错误）
if errors.Is(err, sql.ErrNoRows) { ... }
if errors.Is(err, context.DeadlineExceeded) { ... }

// errors.As：提取具体错误类型（结构化错误）
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) {
    if pgErr.Code == "23505" {  // unique violation
        return ErrDuplicate
    }
}
```

**不要直接 `err == ErrNotFound`**（包装后等式不成立），用 `errors.Is`。

## 5. errors.Join：合并多个错误

Go 1.20+：

```go
var errs []error
for _, file := range files {
    if err := processFile(file); err != nil {
        errs = append(errs, err)
    }
}
if len(errs) > 0 {
    return errors.Join(errs...)
}

// errors.Is 会自动检查所有 joined 错误
if errors.Is(err, ErrNotFound) { ... }
```

## 6. panic / recover：真正的异常情况

```
什么时候用 panic：
├─ 程序无法继续（比如配置文件缺失）
├─ 真正的"不应该发生"（编程错误）
├─ 初始化时（main 启动前）
└─ 第三方库约定（比如 regexp.MustCompile）

什么时候 recover：
├─ HTTP Server 防止一个 handler 把整个服务搞挂
├─ Goroutine 顶层防护（goroutine 崩溃不会被主 goroutine catch）
└─ 不要用 recover 做常规错误处理
```

```go
// HTTP Server 的典型 middleware
func Recovery() gin.HandlerFunc {
    return func(c *gin.Context) {
        defer func() {
            if r := recover(); r != nil {
                stack := debug.Stack()
                slog.Error("panic recovered", "panic", r, "stack", string(stack))
                c.AbortWithStatusJSON(500, gin.H{"error": "internal error"})
            }
        }()
        c.Next()
    }
}
```

## 7. 错误包装的"栈跟踪"

Go 的 errors 包默认不带 stack trace。生产项目通常用 **pkg/errors**（已归档但仍可用）或 **cockroachdb/errors**：

```go
import "github.com/cockroachdb/errors"

func foo() error {
    return errors.Wrap(bar(), "foo failed")  // 带 stack trace
}

// 打印
fmt.Printf("%+v\n", err)
// 会输出完整堆栈
```

或者 Go 1.20+ 用 `runtime/debug`：

```go
func traceableError(msg string) error {
    return fmt.Errorf("%s\n%s", msg, debug.Stack())
}
```

## 8. 生产级错误处理模式

```go
// 1. 底层：保留原始错误
func (r *UserRepo) Find(ctx context.Context, id int64) (*User, error) {
    var u User
    err := r.db.QueryRowContext(ctx, "SELECT ...", id).Scan(&u.ID, &u.Name)
    if err != nil {
        if errors.Is(err, sql.ErrNoRows) {
            return nil, ErrNotFound
        }
        return nil, fmt.Errorf("query user %d: %w", id, err)
    }
    return &u, nil
}

// 2. 业务层：映射到业务错误
func (s *UserService) Get(ctx context.Context, id int64) (*User, error) {
    u, err := s.repo.Find(ctx, id)
    if err != nil {
        if errors.Is(err, ErrNotFound) {
            return nil, &APIError{Code: 404, Message: "user not found"}
        }
        return nil, fmt.Errorf("get user: %w", err)
    }
    return u, nil
}

// 3. Handler：统一响应
func (h *UserHandler) Get(c *gin.Context) {
    id, _ := strconv.ParseInt(c.Param("id"), 10, 64)
    u, err := h.svc.Get(c.Request.Context(), id)
    if err != nil {
        _ = c.Error(err)
        return
    }
    c.JSON(200, u)
}
```

## 9. 反模式

```
❌ 忽略错误
result, _ := foo()

❌ 只打印不处理
if err != nil { log.Println(err) }

❌ panic 作为常规错误处理
if err != nil { panic(err) }

❌ 用字符串比较错误
if err.Error() == "not found"  // 脆弱，改 errors.Is

❌ 吞掉 context 信息
return err   // 直接往上传，没有上下文
return fmt.Errorf("loading user %d: %w", id, err)  // ✅

❌ 错误链无限包装
return fmt.Errorf("x: %w", fmt.Errorf("y: %w", fmt.Errorf("z: %w", err)))
// 保留 2-3 层就够了

❌ 用 error 做流程控制
for {
    if err := foo(); err == ErrRetry {  // ... 这种用法脆弱
}
```

## 10. 日志和错误的关系

```
❌ 同一个错误打印 10 次
  底层：log.Println(err); return err
  中层：log.Println(err); return err
  顶层：log.Println(err); return err
  → 一个错误在日志里出现 10 次

✅ 只在顶层/处理边界打印
  底层：return fmt.Errorf("context: %w", err)
  中层：return fmt.Errorf("context: %w", err)
  顶层：log.Error(err); return err_response
```
