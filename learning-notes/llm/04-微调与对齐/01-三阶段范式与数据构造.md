## 1. 三阶段范式：各自解决什么问题

现代大模型训练流程通常分成三个阶段，每个阶段解决的问题性质不同：

```
阶段一：预训练 (Pre-training)
  数据: 海量无标注文本（网页、书籍、代码等）
  目标: 学习语言的通用知识——语法、事实、推理模式、世界知识
  产物: 一个"会续写文本"但不知道该怎么与人对话的基座模型

阶段二：SFT (Supervised Fine-Tuning)
  数据: 少量高质量的"指令-回复"对
  目标: 教模型识别指令的格式，学会以"助手"的角色组织回复
  产物: 一个能听懂指令、给出像样回复的模型，但可能有害/啰嗦/不够贴合偏好

阶段三：对齐 (Alignment，RLHF/DPO等)
  数据: 人类偏好比较数据（同一个问题的多个回复，标出哪个更好）
  目标: 让模型的输出更符合人类的具体偏好——更有帮助、更安全、更符合习惯
  产物: 最终对外提供服务的模型
```

**为什么不能合并成一步**：三个阶段依赖的数据规模和数据性质完全不同。预训练需要海量数据但不要求"标注质量"（互联网文本本身就是数据）；SFT 需要少量但精心构造、格式规范的指令数据；对齐需要的是"比较"而不是"标准答案"（人类通常更容易判断"哪个回复更好"，而不是写出一个"完美回复"）。如果一开始就用少量高质量指令数据去做预训练规模的训练，数据量远远不够学会语言的通用知识；如果用海量无标注文本去做需要精细监督信号的对齐，又没有"偏好"这个信号可用。分阶段的本质是**让每个阶段的数据类型匹配它能解决的问题**。

## 2. 指令数据的质量维度与配比策略

SFT 阶段"少量但高质量"的数据具体体现在几个质量维度上：

- **多样性**：指令类型（问答、摘要、代码、创作、多轮对话等）、领域、难度都要覆盖，避免模型只学会某一类任务的套路
- **一致性**：同类指令的回复风格、格式、详略程度应该基本一致，避免模型学到互相矛盾的行为模式
- **正确性**：回复本身的事实、代码、逻辑不能有错误——SFT 阶段模型几乎是"模仿"这些回复，错误的示范会被直接学进去
- **难度分布**：既要有简单任务也要有复杂任务，纯简单任务学不到深层能力，纯复杂任务模型可能学不会（缺少由浅入深的过渡）

**配比策略**：不同能力维度（代码、数学、对话、安全拒答、多语言等）的数据比例需要按目标能力做权重分配，而不是简单地把所有能收集到的数据混在一起。某个能力维度的数据占比过低，模型在这个维度的表现会明显偏弱；某个维度占比过高，可能会挤占其他能力的学习空间，甚至让模型的整体风格被这个维度的数据带偏（比如代码数据占比过高可能导致模型在日常对话里也变得生硬）。实践中配比通常需要多轮迭代调整，根据评估结果反复修正，没有一个通用的固定比例。

## 3. 数据去重与污染检查

**去重**：训练数据里如果存在大量近似重复的样本，模型会对这些重复模式过拟合，浪费训练步数在已经学过的内容上，还可能放大数据里的偏见（如果重复的样本本身带有偏差）。去重不仅要做逐字去重，也要做语义近似去重（同一个意思、不同表达方式的样本）。

**污染检查（contamination check）**：训练数据里如果混入了后续要用来评估模型的测试集内容（哪怕只是相似的题目和答案），会导致评估结果虚高——模型不是真的学会了对应能力，只是"记住了答案"。这在指令数据大量来自公开数据集、网络爬取时尤其容易发生，需要在训练前用字符串匹配、n-gram 重叠度等方式对训练集和已知评估基准做交叉检查，把重叠样本从训练集里剔除。

## 4. 多轮对话数据的 loss mask

多轮对话数据的格式通常是一串 `system / user / assistant / user / assistant / ...` 轮次拼接成的长序列。训练时的关键规则是：**只在 assistant 的回复 token 上计算 loss，user 和 system 部分的 token 不参与 loss 计算**。

```
拼接后的完整序列（简化示意）:
  [SYS] 你是一个助手 [USER] 你好 [ASST] 你好，有什么可以帮你？ [USER] 今天天气如何 [ASST] 我无法访问实时天气...

loss mask（1=计入loss, 0=不计入):
  [SYS] 0 0 0 0    [USER] 0 0    [ASST] 1 1 1 1 1 1 1    [USER] 0 0 0 0    [ASST] 1 1 1 ...
```

**为什么这么做**：训练目标是让模型学会"在给定上下文时，该怎么生成回复"，而不是学会"模仿用户会怎么说话"。如果对 user 部分的 token 也算 loss，等价于让模型去学习预测用户输入的内容——这不仅是浪费训练信号（用户输入的内容并不是我们想让模型学会生成的东西），还可能让模型在推理时错误地倾向于续写"用户接下来可能会说的话"，而不是老老实实给出助手应该给出的回复。

**实现方式**：通常在数据预处理阶段，把每个 token 对应一个标签，assistant 回复部分的标签是真实的 token id，其他部分的标签设为一个约定的忽略值（例如 -100，交叉熵损失函数在计算时会自动跳过这个值对应的位置，这与 [BERT与自编码路线](../03-预训练范式/01-BERT与自编码路线.md) 中 MLM 用 -100 标记非掩码位置的 loss mask 机制是同一套思路）。多轮对话情形下，每一轮的 assistant 回复都单独打开 loss，其余位置全部关闭,一条样本里可能有多段"开-关"交替的 loss mask 区间。

## 5. 灾难性遗忘：成因与缓解

灾难性遗忘（catastrophic forgetting）指的是：模型在 SFT 或对齐阶段针对新数据调整参数后，反而在预训练阶段学到的某些通用能力上出现退化——比如微调后模型在没被覆盖的知识领域、语言、任务类型上表现变差。

**成因**：微调阶段的参数更新方向完全由当前的微调数据决定，梳理不到"这次更新会不会破坏掉预训练阶段学到的某些能力"。当微调数据的分布、任务类型与预训练数据差异较大、且微调的学习率或训练步数偏高时，参数会被拉向一个更适应微调数据、但偏离原始预训练分布的区域，原来依赖那部分参数配置的能力就跟着退化。本质上是**微调数据分布和预训练数据分布之间的差异，加上没有显式约束"别偏离太远"**共同造成的。

**常见缓解手段**：

| 手段 | 思路 |
| --- | --- |
| 降低学习率 / 减少训练步数 | 让参数更新幅度小一些，减少对原有能力的破坏 |
| 混入通用数据 | 微调数据里混入一部分通用/多样化的数据，防止分布过度收窄 |
| 参数高效微调（PEFT） | 冻住大部分原始参数，只更新少量新增参数，天然限制了破坏范围（详见 [PEFT参数高效微调](02-PEFT参数高效微调.md)） |
| KL 惩罚 / 正则化 | 显式约束微调后的模型输出分布不要偏离原模型太远（对齐阶段常用，详见 [RLHF全链路](03-RLHF全链路.md)） |
| 分层评估 | 微调后不仅评估目标任务，也定期评估通用能力基准，及时发现退化 |

## 6. 微调效果评估的常见陷阱

- **只看目标任务指标，不看通用能力**：微调后目标任务分数上升了，但如果不做通用能力回归测试，很难察觉灾难性遗忘已经发生
- **评估数据和训练数据存在隐性重叠**：即使不是逐字重复，如果评估集的题目类型、模板与训练数据高度相似，分数会虚高，无法反映真实泛化能力
- **只做自动指标评估，不做人工抽查**：像 BLEU、ROUGE 这类基于文本重叠的自动指标，无法可靠衡量"回复是否真的有帮助、是否符合人类偏好"，容易出现指标涨了但主观体验没变好甚至变差的情况
- **忽略评估的方差**：小样本评估集上的分数波动可能纯粹是随机性造成的，如果不做多次评估或看置信区间，容易把噪声误判成真实的效果提升或下降
- **过度依赖单一模型当裁判**：用另一个大模型给回复打分（LLM-as-judge）时，裁判模型本身的偏好（比如偏爱更长的回复）会系统性地影响评估结果，需要意识到这种偏差而不是全盘采信分数

## 7. 用 NumPy 演示多轮对话的 loss mask

用 NumPy 模拟一条多轮对话样本的 token 序列，构造 loss mask，并验证只有 assistant 回复段参与损失计算。

```python
import numpy as np

# 用整数模拟角色标记：0=普通词, 100=system标记, 101=user标记, 102=assistant标记
SYS, USER, ASST = 100, 101, 102


def build_conversation_and_mask(turns):
    """
    turns: 列表，每项是 (role, token_list)，role 取 'system'/'user'/'assistant'
    返回:
      input_ids: 拼接后的完整 token 序列（含角色标记）
      labels: 与 input_ids 等长，assistant 回复部分是真实 token，其余为 -100
    """
    input_ids = []
    labels = []
    role_marker = {"system": SYS, "user": USER, "assistant": ASST}

    for role, tokens in turns:
        marker = role_marker[role]
        input_ids.append(marker)          # 角色标记本身也占一个位置，不参与 loss
        labels.append(-100)
        for tok in tokens:
            input_ids.append(tok)
            if role == "assistant":
                labels.append(tok)        # 只有 assistant 的正文 token 参与 loss
            else:
                labels.append(-100)

    return np.array(input_ids), np.array(labels)


def compute_masked_cross_entropy(logits, labels, ignore_index=-100):
    """
    简化版交叉熵：只在 labels != ignore_index 的位置计算，其余位置贡献为 0。
    logits: (seq_len, vocab_size)，这里用随机数模拟模型输出
    """
    seq_len, vocab_size = logits.shape
    probs = np.exp(logits - np.max(logits, axis=-1, keepdims=True))
    probs = probs / np.sum(probs, axis=-1, keepdims=True)

    mask = (labels != ignore_index)
    if not np.any(mask):
        return 0.0, 0

    safe_labels = np.where(mask, labels, 0)  # 被忽略位置填 0 只是为了索引合法，不影响结果
    picked_probs = probs[np.arange(seq_len), safe_labels]
    losses = -np.log(np.clip(picked_probs, 1e-12, 1.0))
    losses = losses * mask  # 非 assistant 位置的 loss 直接清零

    n_valid = np.sum(mask)
    return float(np.sum(losses) / n_valid), int(n_valid)


if __name__ == "__main__":
    conversation = [
        ("system", [1, 2]),          # "你是一个助手"（简化为2个token）
        ("user", [3, 4]),            # "你好"
        ("assistant", [5, 6, 7]),    # "你好，有什么帮助"
        ("user", [8, 9, 10]),        # "今天天气如何"
        ("assistant", [11, 12]),     # "我不知道"
    ]

    input_ids, labels = build_conversation_and_mask(conversation)
    print("input_ids:", input_ids)
    print("labels   :", labels)
    print("参与 loss 的位置数:", np.sum(labels != -100), "/ 总长度:", len(labels))

    # 用随机 logits 模拟模型输出，验证 masked loss 计算逻辑
    rng = np.random.default_rng(0)
    vocab_size = 20
    fake_logits = rng.normal(size=(len(input_ids), vocab_size))
    loss, n_valid = compute_masked_cross_entropy(fake_logits, labels)
    print(f"\n模拟 loss = {loss:.4f}, 实际参与计算的 token 数 = {n_valid}")

    # 对照：如果不加 mask，所有 assistant token 的位置数应等于两轮回复长度之和
    expected = sum(len(toks) for role, toks in conversation if role == "assistant")
    print(f"预期 assistant 正文 token 数 = {expected}, 实际统计一致: {n_valid == expected}")
```

实测输出（numpy 2.4.4）：

```
input_ids: [100   1   2 101   3   4 102   5   6   7 101   8   9  10 102  11  12]
labels   : [-100 -100 -100 -100 -100 -100 -100    5    6    7 -100 -100 -100 -100
 -100   11   12]
参与 loss 的位置数: 5 / 总长度: 17

模拟 loss = 2.9689, 实际参与计算的 token 数 = 5
预期 assistant 正文 token 数 = 5, 实际统计一致: True
```

验证了两点：一是 labels 数组只在 assistant 正文 token 的位置保留真实标签，角色标记本身、system/user 内容全部是 -100；二是最终参与 loss 计算的 token 数（5）精确等于两轮 assistant 回复的正文长度之和（3+2=5），说明 mask 逻辑正确地把非 assistant 部分排除在了损失计算之外。

## 8. 小结

| 概念 | 一句话总结 |
| --- | --- |
| 预训练 | 海量无标注文本学通用知识，产出基座模型 |
| SFT | 少量高质量指令数据，教模型学会助手角色的回复格式 |
| 对齐 | 偏好比较数据，让输出更贴合人类具体偏好 |
| 数据质量维度 | 多样性、一致性、正确性、难度分布，配比需按目标能力迭代调整 |
| 去重与污染检查 | 防止过拟合重复样本、防止评估结果因数据泄漏而虚高 |
| loss mask | 只在 assistant 回复 token 上计算 loss，其余位置设为忽略值 |
| 灾难性遗忘 | 微调数据分布偏离预训练分布 + 无约束更新，导致原有能力退化 |
| 评估陷阱 | 只看目标任务、评估数据隐性重叠、依赖单一自动指标或单一裁判模型 |
