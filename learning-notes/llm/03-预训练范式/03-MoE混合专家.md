## 1. 稀疏激活的动机：参数量与计算量解耦

一个稠密（dense）Transformer 里，每一层的前馈网络（FFN）对每个 token 都要完整算一遍——参数量越大，每个 token 消耗的计算量也线性增大。这意味着"想要更强的模型"和"想要更便宜的推理"是天然矛盾的：加参数就要加计算。

MoE（Mixture of Experts，混合专家）打破了这个绑定关系。核心思路：把一层 FFN 换成**多个并行的 FFN（称为专家，expert）**，但对每个 token，只挑选其中**一小部分**专家来计算，其余专家完全不参与这个 token 的前向传播。

```
稠密 FFN:
  token → [唯一的大 FFN，全部参数都参与计算] → 输出

MoE 层（N 个专家，每次只选 Top-K 个）:
  token → 路由器（Router）→ 从 N 个专家里选出 K 个
       → 只有被选中的 K 个专家参与计算 → 加权求和 → 输出
```

假设一层有 8 个专家，每次只激活 2 个，那么**总参数量**是 8 个专家参数之和（决定了模型能装多少知识），但**单个 token 的计算量**只相当于 2 个专家（决定了推理有多贵）。这就是"参数量与计算量解耦"——想要更大的知识容量，加专家数量即可，不需要相应地增加每个 token 的计算成本。这也是为什么 MoE 模型常被描述为"总参数量很大，但激活参数量小得多"。

## 2. 路由器设计与 Top-K 选择

路由器（router / gate）负责决定"这个 token 该交给哪些专家处理"。最常见的实现是一个小型线性层，把 token 的表示映射成对每个专家的打分，再取分数最高的 `K` 个：

```
gate_logits = x · W_gate          # (N 个专家的打分)
gate_probs  = softmax(gate_logits)
top_k_experts, top_k_weights = TopK(gate_probs, k=K)

输出 = Σ_{i in top_k_experts} top_k_weights[i] · Expert_i(x)
```

`K` 通常取一个较小的值（比如每次只选 1 或 2 个专家），`K` 越小，计算越省，但每个 token 能利用到的"专业知识"越有限；`K` 越大，计算成本上升，但和稠密模型的差距缩小。这是 MoE 设计里最基础的一个权衡。

**为什么用 Top-K 而不是让所有专家都按权重参与**：如果不做硬选择，所有专家都参与计算（只是权重不同），那计算量又变回了和稠密模型一样，MoE 稀疏激活的意义就没有了。Top-K 的"硬"选择才是稀疏性的来源——没被选中的专家在这个 token 上完全不参与计算,不产生任何计算开销。

## 3. 负载均衡损失：为什么必须有

路由器是从数据中学出来的，如果不加约束，训练过程中大概率会出现**路由坍塌**：路由器发现某几个专家在早期训练中表现稍好（哪怕只是随机的初始化差异），就倾向于把更多 token 路由给它们，这些专家因为拿到更多训练信号会变得更强，从而进一步吸引更多路由——这是一个自我强化的正反馈循环。最终结果是少数专家过载、大多数专家几乎没有被训练过，模型退化成事实上的稠密小模型，浪费了大部分参数容量。

负载均衡损失（load balancing loss / auxiliary loss）的作用就是在训练目标里加一个惩罚项，鼓励 token 在专家间**尽量均匀分布**：

```
辅助损失 ∝ N · Σ_i (f_i · P_i)

其中：
  f_i = 实际被路由到专家 i 的 token 比例
  P_i = 路由器给专家 i 的平均概率（softmax 概率的均值）
  N   = 专家总数
```

这个损失在专家负载完全均匀时取得最小值，在负载高度集中于少数专家时变大，直接把它加到主训练损失上，用总损失做反向传播，就能持续给路由器施加"别偏心"的压力。**没有这个损失几乎必然出现路由坍塌**——路由器没有任何天然理由保持均衡，均衡只能靠额外的约束项换来。

## 4. 专家崩塌问题

即使有负载均衡损失，MoE 训练仍然可能出现更微妙的**专家崩塌（expert collapse）**：多个专家在参数空间上趋同，学到几乎相同的功能，等价于"名义上有 N 个专家，实际上只有更少数量的、有区分度的功能模块"。表现上负载可能是均衡的（token 均匀分布到各个专家），但专家之间没有真正分化出各自的专长,模型没有从"更多专家"里获得应有的收益。

这类问题没有单一根因，通常和路由器初始化、训练早期的随机性、辅助损失系数设置不当等因素相关。缓解手段包括更谨慎的初始化、引入正则化鼓励专家表示多样性、调整辅助损失权重等，但这仍是 MoE 训练里需要持续监控的问题，不是一次配置就能保证万无一失。

## 5. 共享专家与细粒度专家：改进思路

后续工作在基础 MoE 结构上提出了两个方向的改进：

**共享专家（shared expert）**：把专家分成两类——一类是所有 token 都必须经过的"共享专家"，负责学习通用、任务无关的知识；另一类是路由器按 Top-K 挑选的"路由专家"，负责学习更专精的知识。动机是：如果完全依赖路由决定每个 token 该学什么，那些"放哪都行"的通用模式（比如基础语法规律）可能会被冗余地在多个路由专家里重复学习，浪费容量。让共享专家统一兜底这部分通用知识，路由专家就能更专注于差异化的专长。

**细粒度专家（fine-grained experts）**：把每个专家的规模变小、数量变多（例如把原来 8 个大专家拆分成 64 个小专家，每次路由选择更多个但更小的专家）。动机是：更细的粒度让路由器有更精细的组合空间——不同 token 组合出的"专家子集"数量呈组合爆炸式增长，理论上能表达更丰富的专精分工，而不是被限定在少数几个粗粒度的专家之间做选择。

这两个思路可以叠加使用：既有负责通用知识的共享专家，又有大量细粒度的路由专家供路由器精细组合。

## 6. 显存与通信代价

MoE 的"参数量与计算量解耦"不是没有代价的，代价主要体现在两方面：

**显存**：MoE 层的全部专家参数都需要常驻显存（哪怕某个专家在这一批数据里一次都没被路由到），因为下一个 token、下一个 batch 随时可能路由到它。所以 MoE 模型的显存占用大致对应**总参数量**，而不是激活参数量——这和"计算量只对应激活参数量"形成了反差:计算便宜了,但显存没有相应地便宜。

**通信**：在分布式训练/推理中，不同专家常常分布在不同设备上（专家并行,expert parallelism）。一个 token 具体会路由到哪个专家，是运行时才能确定的，这意味着 token 需要被动态地"发送"到对应专家所在的设备上计算，再把结果"收集"回来——这两步都是 All-to-All 通信，通信量和模式随批次内的路由结果变化而变化，比稠密模型里规整的通信模式（比如固定的张量并行通信）更难优化，也更容易因为负载不均衡（某些设备上的专家被路由到的 token 特别多）产生计算等待。

## 7. 为何 MoE 适合预训练，部署需要技巧

把以上几点串起来看：

**预训练阶段**：目标是用给定计算预算学到尽可能多的知识。MoE 用同样计算量换来更大参数容量（知识容量），只要负载均衡控制得住，预训练阶段是纯粹净收益——用更少计算学到更多。

**部署阶段**：推理请求往往是单条或小批量到达的，不像训练那样有海量数据把路由"摊匀"。这带来几个实际问题：小批量下路由到各个专家的 token 数目可能很不均衡，如果专家分布在多设备上,某些设备可能大部分时间在空闲等待；全部专家参数常驻显存的要求，让 MoE 模型的显存门槛几乎看齐同等总参数量的稠密模型,即使推理时只用到一小部分;专家并行引入的动态通信在单条请求延迟敏感的在线服务场景下会放大延迟的不确定性。

因此实际部署 MoE 模型通常需要额外工程手段：合理批处理策略把小请求攒批以让路由更均衡、专家放置和设备拓扑的精细调优以减少通信开销、必要时对专家参数做量化或剪裁以降低显存门槛等。这些技巧不是 MoE 架构本身自带的，而是"训练时的稀疏优势"和"部署时的现实约束"之间的落差，需要靠系统工程去填。

## 8. 用 NumPy 实现 Top-K 路由与负载均衡损失

用 NumPy 实现一个简化的 MoE 路由过程：计算路由概率、执行 Top-K 选择、计算负载均衡损失，并对比"无约束路由"与"加了均衡损失梯度信号"两种情况下专家负载的分布差异。

```python
import numpy as np


def softmax(x, axis=-1):
    """数值稳定的 softmax"""
    x_max = np.max(x, axis=axis, keepdims=True)
    exp_x = np.exp(x - x_max)
    return exp_x / np.sum(exp_x, axis=axis, keepdims=True)


def route_tokens(gate_logits, top_k):
    """
    对一批 token 做 Top-K 路由。
    gate_logits: (n_tokens, n_experts)
    返回：
      top_k_idx     (n_tokens, top_k) 每个 token 选中的专家编号
      top_k_weight  (n_tokens, top_k) 对应的路由权重（选中专家概率重新归一化）
      full_probs    (n_tokens, n_experts) 路由器对全部专家的原始概率，用于算均衡损失
    """
    full_probs = softmax(gate_logits, axis=-1)
    # argsort 从大到小取前 top_k 个专家索引
    top_k_idx = np.argsort(-full_probs, axis=-1)[:, :top_k]
    # 取出被选中专家的概率，重新归一化，作为组合专家输出时的权重
    selected_probs = np.take_along_axis(full_probs, top_k_idx, axis=-1)
    top_k_weight = selected_probs / np.sum(selected_probs, axis=-1, keepdims=True)
    return top_k_idx, top_k_weight, full_probs


def load_balancing_loss(top_k_idx, full_probs, n_experts):
    """
    计算负载均衡损失：N * sum_i (f_i * P_i)
    f_i: 专家 i 实际被选中的 token 比例（基于 Top-K 硬选择的统计）
    P_i: 路由器给专家 i 的平均概率（软概率，用于让损失可微）
    """
    n_tokens, top_k = top_k_idx.shape

    # f_i：统计每个专家被选中的次数，除以（token数 * top_k）得到比例
    f = np.zeros(n_experts)
    for expert_id in range(n_experts):
        f[expert_id] = np.sum(top_k_idx == expert_id) / (n_tokens * top_k)

    # P_i：路由器软概率在 batch 内的平均值
    P = np.mean(full_probs, axis=0)

    loss = n_experts * np.sum(f * P)
    return loss, f, P


def simulate_biased_router(n_tokens, n_experts, bias_strength, rng):
    """
    模拟一个"偏心"的路由器：给前几个专家的 logits 加上额外偏置，
    模拟训练早期路由坍塌的场景（少数专家因随机优势被过度路由）。
    bias_strength=0 时是无偏路由；越大越偏向低编号专家。
    """
    base_logits = rng.normal(0, 1, size=(n_tokens, n_experts))
    bias = np.linspace(bias_strength, 0, n_experts)  # 专家 0 偏置最大，依次递减
    return base_logits + bias


if __name__ == "__main__":
    rng = np.random.default_rng(2024)
    n_tokens, n_experts, top_k = 2000, 8, 2

    print(f"设置: {n_tokens} 个 token, {n_experts} 个专家, 每次选 Top-{top_k}\n")

    for bias_strength, label in [(0.0, "无偏路由（模拟均衡良好的情况）"),
                                   (3.0, "偏心路由（模拟路由坍塌风险）")]:
        logits = simulate_biased_router(n_tokens, n_experts, bias_strength, rng)
        top_k_idx, top_k_weight, full_probs = route_tokens(logits, top_k)
        loss, f, P = load_balancing_loss(top_k_idx, full_probs, n_experts)

        print(f"--- {label} ---")
        print(f"各专家实际负载占比 f_i: {np.round(f, 3)}")
        print(f"理想均衡时每个专家应占: {1.0 / n_experts:.3f}")
        print(f"负载均衡损失: {loss:.4f}  (越接近 1.0 越均衡，越大表示越集中)")
        print(f"负载标准差: {np.std(f):.4f}  (越小越均衡)\n")
```

实测输出（numpy 2.4.4）：

```
设置: 2000 个 token, 8 个专家, 每次选 Top-2

--- 无偏路由（模拟均衡良好的情况） ---
各专家实际负载占比 f_i: [0.122 0.126 0.125 0.124 0.12  0.126 0.13  0.126]
理想均衡时每个专家应占: 0.125
负载均衡损失: 1.0005  (越接近 1.0 越均衡，越大表示越集中)
负载标准差: 0.0029  (越小越均衡)

--- 偏心路由（模拟路由坍塌风险） ---
各专家实际负载占比 f_i: [0.354 0.276 0.173 0.106 0.056 0.023 0.009 0.004]
负载均衡损失: 1.7650  (越接近 1.0 越均衡，越大表示越集中)
负载标准差: 0.1230  (越小越均衡)
```

结果符合机制预期：无偏路由下 8 个专家的负载几乎均匀（都接近理论值 0.125），均衡损失接近其最小值 1.0；引入偏置后负载明显向低编号专家倾斜（从 0.354 递减到 0.004），均衡损失和标准差都明显上升。这正是负载均衡损失要压制的现象——训练时把这个损失加到主损失上参与反向传播，就是在持续修正这种失衡倾向。

## 9. 小结

| 概念 | 一句话总结 |
| --- | --- |
| 稀疏激活 | 只让 Top-K 个专家参与每个 token 的计算，参数量与计算量解耦 |
| 路由器 | 给 token 对每个专家打分，Top-K 硬选择才是稀疏性的来源 |
| 负载均衡损失 | 惩罚负载集中，防止路由坍塌导致大部分专家闲置 |
| 专家崩塌 | 负载均衡不代表专家真正分化，多个专家可能学到雷同功能 |
| 共享专家 | 兜底通用知识，减少路由专家之间的重复学习 |
| 细粒度专家 | 更小更多的专家，扩大路由组合空间 |
| 显存代价 | 全部专家常驻显存，显存对应总参数量而非激活参数量 |
| 通信代价 | 专家并行下的 All-to-All 通信随路由结果动态变化，难以规整优化 |
| 训练 vs 部署 | 训练时纯收益，部署时批处理、放置、量化等工程手段缺一不可 |
